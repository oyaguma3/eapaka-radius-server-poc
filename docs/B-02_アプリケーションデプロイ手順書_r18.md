# B-02 アプリケーションデプロイ手順書 (r18)

## 1. 概要

### 1.1 目的

本ドキュメントは、B-01「ホストOS構築手順書」で構築したホストOS上にアプリケーションをデプロイし、EAP-AKA RADIUS PoC環境を運用可能な状態にするまでの手順を提供する。

> **注記（r18）:** VPS（AWS Lightsail 等）にデプロイする場合は、B-03「VPSデプロイ手順書」を参照すること。B-03 は本書の手順をもとに、VPS で変わる点（SSH ポート、Admin TUI のビルド、イメージのビルド、RADIUS の公開範囲等）を示している。

### 1.2 スコープ

**本書で扱う範囲：**

- リポジトリのクローン（`git clone`）
- 環境変数ファイル（`.env`）の作成
- ログ出力ディレクトリの準備
- `docker compose up -d` による起動
- Admin TUIバイナリの配置
- logrotate設定ファイルの配置
- バックアップスクリプトの配置
- lnavフォーマットファイルの配置
- aka-only-server（接続方式01）への接続（任意）

**B-01「ホストOS構築手順書」で扱う範囲（本書の前提）：**

- Ubuntu Server 24.04 LTSのインストール
- ホストOS初期設定（タイムゾーン、NTP同期）
- セキュリティ設定（SSH、UFW）
- Docker Engine / Docker Compose導入
- 運用ツール導入（lnav、jq、git）
- systemdサービス登録（アプリケーション自動起動）

## 4. 環境変数ファイル（.env）の作成

### 4.1 テンプレートからコピー

```bash
cd ~/eapaka-radius-server-poc/deployments
cp .env.example .env
```

### 4.2 必須項目の設定

`.env` ファイルを編集し、必須項目を設定する。

```bash
vi ~/eapaka-radius-server-poc/deployments/.env
```

**必須項目：**

| 変数名 | 説明 | 設定例 |
|--------|------|-------|
| `VALKEY_PASSWORD` | Valkey接続パスワード | 後述のコマンドで生成 |

パスワードの生成には以下のコマンドを使用する。

```bash
# パスワード生成（32バイト、Base64エンコード）
openssl rand -base64 32
```

生成した値を `.env` ファイルの対応する変数に設定する。

```
VALKEY_PASSWORD=<生成したパスワード>
```

> **注記（RADIUS_SECRET は任意。空を推奨）:** `RADIUS_SECRET` はフォールバックの共有シークレットであり、必須ではない（`.env.example` では既定でコメントアウトしている）。RADIUS の共有シークレットは、AP の送信元IPごとに Admin TUI のクライアント登録（`client:{IP}`）で設定する（§7.4）。`RADIUS_SECRET` が空なら、登録のない送信元IPからのパケットは破棄される（応答しない。auth-server / acct-server が `RADIUS_NO_SECRET` を出力）。値を設定すると、登録のない送信元IPからのパケットもそのシークレットで受け付けるため、**インターネットに公開するサーバー（VPS 等）では空のままにすること**。閉じた LAN で、AP の送信元IPを登録せずに試す場合にだけ設定する。設定した場合、auth-server / acct-server は起動時に WARN を出す（§11 No.19）。

> **⚠️ 警告:** `TEST_VECTOR_ENABLED` は本番環境では絶対に `true` に設定しないこと。テストベクターモードが有効な場合、対象IMSIの認証ベクターが公開済みのテスト用鍵（固定の Ki/OPc/AMF）で計算され、セキュリティリスクが生じる。

### 4.3 オプション項目の説明

必要に応じて以下のオプション項目を設定する。

| 変数名 | デフォルト値 | 説明 |
|--------|------------|------|
| `RADIUS_SECRET` | （空） | フォールバックの共有シークレット。クライアント登録のない送信元IPからのパケットをこのシークレットで受け付ける。**空を推奨**（インターネットに公開する場合は必ず空にする。§4.2 の注記） |
| `VECTOR_GATEWAY_MODE` | `gateway` | Vector Gatewayの動作モード（`gateway` または `passthrough`） |
| `VECTOR_GATEWAY_PLMN_MAP` | （空） | PLMNマッピング（`PLMN:接続方式ID` のカンマ区切り、例: `44010:01`）。接続方式ID `00`=内部Vector API（未一致PLMNも00）、`01`=aka-only-server、`02`〜`99`=将来実装（501） |
| `VECTOR_GATEWAY_INTERNAL_TIMEOUT` | `3s` | 内部API呼び出しタイムアウト。auth-server の Vector Gateway 呼び出しタイムアウト（5秒）より短くすること（下記注記） |
| `VECTOR_GATEWAY_AKAONLY_URL` | （空） | aka-only-serverのベースURL（`https://`=mTLS、`http://`=平文HTTP）。空なら接続方式01は無効（§14参照） |
| `VECTOR_GATEWAY_AKAONLY_CLIENT_CERT` | （空） | クライアント証明書PEMのコンテナ内パス（例: `/certs/av-client.pem`）。証明書と秘密鍵が1ファイルでよい。`https://` の場合必須 |
| `VECTOR_GATEWAY_AKAONLY_CLIENT_KEY` | （空） | 秘密鍵PEMのコンテナ内パス。空なら `CLIENT_CERT` のファイルから読む |
| `VECTOR_GATEWAY_AKAONLY_SERVER_CERT` | （空） | aka-only-serverのAV用サーバー証明書のコンテナ内パス（例: `/certs/av-server.pem`）。`https://` の場合必須 |
| `VECTOR_GATEWAY_AKAONLY_TIMEOUT` | `3s` | aka-only-server呼び出しタイムアウト。`VECTOR_GATEWAY_INTERNAL_TIMEOUT` と同じく5秒より短くすること |
| `AKA_SHARED_NETWORK` | `aka-av` | aka-only-serverのcomposeが作る共有ネットワーク名（`docker-compose.aka-av.yml` 用） |
| `LOG_MASK_IMSI` | `true` | IMSIマスキング有効化（本番環境では `true` を推奨） |
| `LOG_LEVEL` | `INFO` | ログレベル（`DEBUG` / `INFO` / `WARN` / `ERROR`）。対象は auth-server・acct-server・vector-gateway・vector-api。運用時は `INFO` とし、調査時のみ一時的に `DEBUG` にする |
| `TEST_VECTOR_ENABLED` | `false` | テストベクターモード（**本番環境では設定しないこと**） |
| `TEST_VECTOR_IMSI_PREFIX` | `00101` | テストベクター対象IMSIプレフィックス |

> **注記（タイムアウト）:** vector-gateway のタイムアウトを5秒以上にすると、vector-api / aka-only-server の障害時に vector-gateway が 502 を返す前に auth-server がタイムアウトし、auth-server のログが `VECTOR_API_ERR`（502）ではなく `VECTOR_CONN_ERR` になることがある。この場合、vector-gateway は起動時に WARN `backend timeout should be shorter than the auth-server timeout; auth-server may time out before receiving 502`（`setting` に該当する環境変数名）を出す。通常は既定値（`3s`）のまま設定しなくてよい。

> **注意:** `LOG_MASK_IMSI=false` の設定は、ログファイルへのアクセス制御が適切に行われている環境でのみ使用すること。デバッグ目的で一時的に無効化した場合は、調査完了後に速やかに `true` に戻すこと。

全サービスの状態を確認する。

```bash
cd ~/eapaka-radius-server-poc/deployments

```

期待される出力（全6サービスが起動していること）：

NAME                           STATUS              PORTS
deployments-auth-server-1      Up (healthy)        0.0.0.0:1812->1812/udp, [::]:1812->1812/udp
deployments-acct-server-1      Up (healthy)        0.0.0.0:1813->1813/udp, [::]:1813->1813/udp

### 7.4 RADIUSクライアントの登録

RADIUS の共有シークレットは、AP（RADIUSクライアント）の送信元IPごとに Admin TUI で登録する（RADIUSクライアント管理。操作は O-01 §4.2 を参照）。`RADIUS_SECRET` が空（推奨）の場合、登録のない送信元IPからのパケットには応答しない。

共有シークレットは十分に長いランダムな値とし、AP 側の設定と一致させる。

```bash
# 共有シークレット生成（24バイト、Base64エンコード）
openssl rand -base64 24
```

登録する IP Address は、**サーバーから見た** AP の送信元IPである。

| 環境 | 登録する送信元IP |
|------|----------------|
| AP と同じ LAN | AP のIPアドレス |
| インターネット越し（VPS 等） | AP がつながるルーターのグローバルIP（NAT の内側の AP の場合） |
| 同じホスト上から 127.0.0.1 宛てに試験 | Docker ブリッジ（compose ネットワーク `deployments_default`）のゲートウェイIP（例: `172.18.0.1`。確認方法は T-03 §2.2） |

> **注記（インターネット越しに RADIUS を受ける場合）:** RADIUS（UDP）は共有シークレットだけで守られる（RadSec は本PoCのスコープ外）。同じ NAT の内側の複数の AP は同じ送信元IPとして扱われ、同じクライアント登録・同じ共有シークレットになる（認可ポリシーの `nas_id` 判定は NAS-Identifier 属性で行うため AP ごとに分けられる）。グローバルIPが動的に変わる回線では、変わるたびに登録をやり直す必要がある（固定IPが望ましい）。1812/1813/udp の送信元は、UFW ではなくクラウド側のファイアウォールで AP のグローバルIPに絞ることを推奨する（D-08 §5.4、§5.7）。

> **注記（応答がない場合）:** 送信元IPが登録されておらず `RADIUS_SECRET` も空の場合、auth-server / acct-server は WARN `RADIUS Secret不明`（`event_id`=`RADIUS_NO_SECRET`、`src_ip` に実際の送信元IP）を出してパケットを破棄する。`docker compose logs auth-server | grep RADIUS_NO_SECRET` で `src_ip` を確認し、そのIPを登録する。

# 失敗したときに書きかけの一時ファイルを残さない

# エラーが表示されないことを確認

### 13.7 lnavカスタムフォーマットが適用されない場合

**症状:** `lnav -C` でエラーは出ないが、ログファイルを開いてもカスタムフォーマット（`aka_radius_log`）が適用されず、生JSONまたはbunyanフォーマットで表示される。

**原因と対処:**

本プロジェクトの調査で判明した3つの根本原因と、それぞれの回避策を以下に示す。

#### 原因1: bunyan組み込みフォーマットとの競合

lnav v0.11.2 はフォーマット定義をアルファベット順にスキャンし、最初にマッチしたフォーマットを適用する。lnavに組み込まれている `bunyan_log` フォーマットは、JSONで5フィールド以上を持つログ行に広くマッチするため、カスタムフォーマット名がアルファベット順で `bunyan_log`（`b` 始まり）より後にスキャンされると、bunyanが先にマッチしてしまう。

**回避策:** フォーマット名を `a` 始まりにする（本プロジェクトでは `aka_radius_log` を採用）。これによりアルファベット順で `bunyan_log` より先にスキャンされる。

**確認手順:**

```bash
# 適用されているフォーマット名を確認（lnav起動後）
# ステータスバーで確認するか、SQLモードで次を実行して aka_radius_log が表示されることを確認
#   ;SELECT log_format, count(*) FROM all_logs GROUP BY log_format
lnav ~/eapaka-radius-server-poc/deployments/logs_on_host/auth-server.log
```

#### 原因2: timestamp-format の %N 9桁固定問題

lnavの `timestamp-format` で使用される `%N` は **常に9桁のナノ秒** を期待する。しかし、Go `slog` の `time.RFC3339Nano` 形式は末尾のゼロを削除するため、ナノ秒部分が3桁〜9桁の可変長になる。この不一致により、`timestamp-format` を明示指定するとパースに失敗する場合がある。

**回避策:** `timestamp-format` を定義から削除し、lnavのISO 8601自動検出に委任する。lnavはJSONフォーマットのタイムスタンプフィールドに対してISO 8601形式を自動認識でき、可変長のナノ秒にも対応する。

#### 原因3: file-pattern未設定

`file-pattern` が未設定の場合、lnavはすべてのファイルに対してフォーマットのマッチングを試みる。`file-pattern` を設定することで、対象ファイルを限定し、不要なマッチング試行を回避できる。

**本プロジェクトの設定:**

```
"file-pattern": "(?:auth-server|acct-server|vector-api|vector-gateway)\\.log"
```

**総合的な確認手順:**

1. フォーマットファイルの構文検証を行う。
   ```bash
   lnav -C
   ```

2. フォーマット名が `aka_radius_log` であることを確認する。
   ```bash
   cat ~/.lnav/formats/installed/eap_aka_log.json | grep -o '"aka_radius_log"'
   ```

3. `timestamp-format` が定義に含まれていないことを確認する。
   ```bash
   grep 'timestamp-format' ~/.lnav/formats/installed/eap_aka_log.json
   # 出力がないことを確認
   ```

## 14. aka-only-serverへの接続（接続方式01、任意）

Vector Gatewayの接続方式01を使い、指定したPLMNの認証ベクターを外部の aka-only-server（https://github.com/oyaguma3/aka-only-server 、管理GUI: https://github.com/oyaguma3/web-gui-for-aka-only-server ）から取得する場合の手順を示す。接続方式01を使わない場合、本章の作業は不要である（既定ではすべてのPLMNが内部Vector API（00）に向く）。

- 振り分けは `VECTOR_GATEWAY_PLMN_MAP` によるPLMN単位で行う。同じPLMNのIMSIを00と01に分けることはできない。
- 接続は mTLS（証明書ピン留め）を推奨する。平文HTTPは同一ホスト内に限る（§14.7）。
- 設定や配置の詳細は D-08 §4.5、接続方式01の仕様は D-12 を参照。

### 14.1 前提

- aka-only-server が aka-only-server のリポジトリの手順で起動済みであること。
- 同一ホストで動かす場合、aka-only-server の compose が共有ネットワーク（既定名 `aka-av`）を作成していること。
- 01に向けたPLMNの加入者は、Ki/OPc を **aka-only-server** に登録し、認可ポリシー（`policy:{IMSI}`）とRADIUSクライアントは従来どおり **Admin TUI で PoC の Valkey** に登録する。auth-server はポリシー未登録だと Reject するため両方の登録が必要（詳細は O-01 参照）。

### 14.2 aka-only-server側の作業

aka-only-server のリポジトリのディレクトリで以下を実行し、クライアント証明書の発行・登録、AV用サーバー証明書の取得、加入者の登録を行う。

```bash
# 1. クライアント証明書（証明書＋秘密鍵）を発行
docker compose exec -T aka-only-server /aka-only-server client gen-cert -name radius-gw > av-client.pem

# 2. クライアントとして登録（発番されたクライアントIDが表示される）
docker compose exec -T aka-only-server /aka-only-server client add -name radius-gw -cert - < av-client.pem
# 出力例: client 1 added (name=radius-gw fingerprint=... not-after=...)

# 3. AV用サーバー証明書を取得
docker compose exec -T aka-only-server /aka-only-server av-cert > av-server.pem

# 4. 加入者を登録（-clients に手順2で発番されたクライアントIDを指定）
docker compose exec -T aka-only-server /aka-only-server subscriber add -imsi <IMSI> -ki <Ki> -opc <OPc> -clients <発番されたクライアントID>
```

`subscriber add` の主なオプション：

| オプション | 既定値 | 説明 |
|-----------|-------|------|
| `-sqn` | `000000000000` | SQN初期値 |
| `-amf` | `8000` | AMF |
| `-sqn-type` | `inc32` | SQN増加タイプ（`inc1` / `inc32` / `inc33`）。内部Vector APIと同じ挙動にするには `inc32` |
| `-allow-plain` | （なし） | 平文HTTPでの払い出しを許可する |
| `-clients` | （なし） | 許可クライアントID（カンマ区切り） |

> **注記:** クライアントと加入者の登録は Web GUI（web-gui-for-aka-only-server）からも行える。

> **注記:** クライアント証明書の有効期限は既定で825日である（`client add` の `not-after` で確認できる）。期限管理は D-08 §6.5 を参照。

### 14.3 証明書の配置（PoC側）

手順14.2で作成した2つのPEMファイルを、PoCホストの `deployments/certs/` に配置する。

```bash
# 別ホストで作成した場合は転送する（SSHポートは10022）
scp -P 10022 av-client.pem av-server.pem admin@<ミニPCのIPアドレス>:~/eapaka-radius-server-poc/deployments/certs/

# 秘密鍵を含むためパーミッションを制限
chmod 600 ~/eapaka-radius-server-poc/deployments/certs/av-client.pem
ls -la ~/eapaka-radius-server-poc/deployments/certs/
```

> **注記:** `deployments/certs/` の中身は `.gitignore` で除外されている（`.gitkeep` のみコミット）。証明書・秘密鍵をコミットしないこと。vector-gateway コンテナは root で動作し、`./certs` を `/certs` に読み取り専用でマウントするため、パーミッション `600` でも読み込める。

### 14.4 .envの設定

`.env` に以下を追記する（例: PLMN `44010` を aka-only-server に向ける場合）。

```
VECTOR_GATEWAY_AKAONLY_URL=https://aka-only-server:8443
VECTOR_GATEWAY_AKAONLY_CLIENT_CERT=/certs/av-client.pem
VECTOR_GATEWAY_AKAONLY_SERVER_CERT=/certs/av-server.pem
VECTOR_GATEWAY_PLMN_MAP=44010:01
```

- 証明書のパスはコンテナ内のパス（`/certs/...`）で指定する。
- `VECTOR_GATEWAY_AKAONLY_CLIENT_KEY` は、秘密鍵を別ファイルにした場合のみ指定する。
- 共有ネットワーク名を変更している場合は `AKA_SHARED_NETWORK` も設定する。
- 同一ホストでオーバーレイを常用する場合は、`COMPOSE_FILE=docker-compose.yml:docker-compose.aka-av.yml` も追記しておくとよい（§14.5の注意参照）。

### 14.5 起動（同一ホスト）

共有ネットワークは aka-only-server 側が作成するため、**aka-only-server を先に起動** しておく。そのうえで、オーバーレイ `docker-compose.aka-av.yml` を重ねて PoC を起動する。

```bash
cd ~/eapaka-radius-server-poc/deployments
docker compose -f docker-compose.yml -f docker-compose.aka-av.yml up -d
```

オーバーレイにより、vector-gateway だけが共有ネットワークに参加し、`aka-only-server` という名前で aka-only-server に届くようになる。

> **注意:** オーバーレイを重ねた後に `-f` なしで `docker compose up -d` を実行すると、vector-gateway が共有ネットワークなしで作り直され、aka-only-server に届かなくなる。systemd サービス（`ExecStart=/usr/bin/docker compose up -d`）経由の起動も同様のため、`.env` に `COMPOSE_FILE=docker-compose.yml:docker-compose.aka-av.yml` を設定しておくこと（設定後は `-f` の指定が不要になる）。

### 14.6 起動確認

vector-gateway の起動ログで、接続方式01が有効になっていることを確認する。

```bash
cd ~/eapaka-radius-server-poc/deployments
grep 'starting vector-gateway' logs_on_host/vector-gateway.log | tail -1
```

```
# 期待される出力（例、一部省略）
{"time":"...","level":"INFO","msg":"starting vector-gateway","app":"vector-gateway",...,"mode":"gateway","plmn_map_entries":1,"akaonly_enabled":true,"akaonly_transport":"mtls"}
```

| 項目 | 期待値 |
|------|-------|
| `akaonly_enabled` | `true` |
| `akaonly_transport` | `mtls`（平文HTTPの場合は `plain`、URL未設定の場合は `disabled`） |

あわせて `docker compose ps vector-gateway` で `Up (healthy)` であることを確認する。設定や証明書に不備があると vector-gateway は起動せず再起動を繰り返し、ログに `failed to load config` または `failed to initialize backends` が出る。

> **注記:** URLを設定せずに `VECTOR_GATEWAY_PLMN_MAP` で01を指定した場合、起動時に `PLMN map refers to a backend that is not configured; requests will fail with 501` のWARNが出る（該当PLMNの認証は501で失敗する）。

認証の確認は、01に向けたPLMNのIMSIで認証を行い、vector-gateway のログに `BACKEND_EXTERNAL_CALL`（`http_status=200`）が出ることで確認する。

### 14.7 平文HTTPで接続する場合

平文HTTPは CK/IK が暗号化されずに流れるため、**同一ホスト内に限る**。

1. aka-only-server 側で `AKA_AV_PLAIN_ADDR=:8080` を設定して起動する。
2. 対象の加入者に平文HTTP許可を立てる（`subscriber add` の `-allow-plain`）。許可がない加入者は403で拒否される。
3. PoC の `.env` を以下のように設定する（証明書の設定は不要。設定しても無視される）。

```
VECTOR_GATEWAY_AKAONLY_URL=http://aka-only-server:8080
VECTOR_GATEWAY_PLMN_MAP=44010:01
```

4. §14.5と同様にオーバーレイを重ねて起動する。起動ログに `akaonly_transport` が `plain` と出るほか、`aka-only-server is connected over plain HTTP; CK/IK are transmitted unencrypted` のWARNが出る。

### 14.8 別ホストの aka-only-server に接続する場合

- オーバーレイ `docker-compose.aka-av.yml` は重ねず、通常どおり `docker compose up -d` で起動する。
- `VECTOR_GATEWAY_AKAONLY_URL` を相手ホストのアドレスにする（例: `https://192.0.2.10:8443`）。
- サーバー証明書のホスト名検証が有効なため、そのアドレスを aka-only-server 側の `AKA_AV_TLS_HOSTS` に入れておく必要がある（サーバー証明書のSANに含めるため）。これによりサーバー証明書が作り直された場合は `av-server.pem` を取り直す。
- PoCホストから aka-only-server のAV用ポート（既定 8443）に到達できること（aka-only-server 側のポート公開・ファイアウォール設定を確認する）。
- 平文HTTPは使用しない。

### 14.9 接続できない場合

vector-gateway のログの `BACKEND_EXTERNAL_ERR`（`http_status` / `cause` / `error`）で原因を切り分ける。主な症状と対処は D-08 §6.4、詳細な手順は O-03 を参照。
