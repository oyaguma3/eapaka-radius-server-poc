# O-03 障害対応手順書 (r3)

## 1. 概要

### 1.1 目的

本手順書は、EAP-AKA RADIUS PoC環境の**サービス運用中**に発生する障害について、検知・切り分け・復旧・エスカレーションの手順を体系的にまとめたものである。

デプロイ時の問題についてはB-02 §13「トラブルシューティング」を参照すること。

### 1.2 対象読者

- 運用担当者（一次対応）
- 開発担当者（二次対応・エスカレーション先）

### 1.3 前提条件

- B-02に基づくデプロイが完了し、全サービスが正常稼働していること
- O-05「ログ解析ガイド」の基本操作（lnavの使い方、event_idの意味）を理解していること
- ホストOSへのSSHアクセスが可能であること

## 2. 障害検知

### 2.1 障害レベル定義

D-06 §2.2に基づく4段階の重大度レベルを定義する。

| レベル | 定義 | ログレベル | 対応方針 |
|--------|------|-----------|---------|
| **Critical** | サービス継続不可 | ERROR | 即座に復旧手順を実行 |
| **Error** | 個別リクエスト失敗 | ERROR / WARN | ログ記録、原因調査 |
| **Warning** | 潜在的問題 | WARN | ログ記録、頻度監視 |
| **Info** | 正常範囲内の注目イベント | INFO | ログ記録 |

### 2.2 監視対象event_id一覧

D-04 §3で定義されるevent_idを、運用上の対応アクション有無で3段階に分類する（主なものを掲載。全量はO-05 §5を参照）。

#### 即対応（Critical） — 復旧手順を即実行

| event_id | ノード | 説明 | 参照 |
|----------|--------|------|------|
| VALKEY_CONN_ERR | Auth / Acct / Vector API | Valkey接続失敗（Auth Serverは起動時のみ、Acct Serverは起動時・実行時、Vector APIは実行時（500応答）） | §4.1 |
| EAP_CTX_CREATE_ERR / EAP_CTX_UPDATE_ERR / SESSION_CREATE_ERR | Auth Server | EAPコンテキスト・セッションのValkey保存失敗（Auth Serverの実行時のValkey障害はこれらで現れる） | §4.1 |
| VECTOR_API_ERR | Auth Server | Vector Gatewayが404以外のエラー（400, 403, 501, 502等）を返却 | §4.2 |
| VECTOR_CONN_ERR | Auth Server | Vector Gatewayへの接続失敗・タイムアウト | §4.2 |
| VECTOR_UNKNOWN_ERR | Auth Server | その他のVector呼び出しエラー | §4.2 |
| DB_WRITE_ERR | Acct Server | Valkey書き込み失敗 | §4.3 |
| GW_ERR（ERROR） | Vector Gateway | バックエンド通信エラー・5xx（msg `backend communication error`、502応答）、想定外エラー（`routing error` / `unexpected backend error`、500応答） | §4.4.1 |
| BACKEND_EXTERNAL_ERR（ERROR） | Vector Gateway | aka-only-server 呼び出し失敗（通信失敗・5xx・不正応答） | §4.4.3 |
| SYS_ERR | Acct Server | Accounting処理のエラー（現行の処理は常に正常終了を返すため、通常は出力されない） | §6.2 |

#### 監視（Warning） — 原因調査・頻度監視

| event_id | ノード | 説明 | 参照 |
|----------|--------|------|------|
| CB_OPEN | Auth Server | Circuit Breaker Open遷移 | §4.2 |
| VECTOR_CB_OPEN | Auth Server | Circuit Breaker Open中のためVector Gatewayを呼び出さずに拒否（ERROR） | §4.2 |
| AUTH_RES_MISMATCH | Auth Server | AT_RESとXRES不一致 | §4.2 |
| AUTH_MAC_INVALID | Auth Server | AT_MAC検証失敗 | §4.2 |
| AUTH_VERIFY_FAIL | Auth Server | 上記以外のChallenge応答検証失敗（AT_RESなし、RES長不一致） | §4.2 |
| EAP_CTX_NOT_FOUND | Auth Server | EAPコンテキスト取得失敗（State不正、コンテキストTTL超過、Valkeyエラー等） | §4.2 |
| AUTH_RESYNC_LIMIT | Auth Server | 再同期リトライ上限超過 | §4.2 |
| ACCT_SESSION_NOT_FOUND | Acct Server | Accounting-StartでClass属性なし、またはAccounting-Start / Interimでセッション不在（セッションTTL超過を含む） | §4.3.1 |
| ACCT_DUPLICATE_START | Acct Server | 重複Start受信・重複Interim受信（msgで区別） | §4.3.3 |
| ACCT_SEQUENCE_ERR | Acct Server | 順序異常（Stop後のStart、StartなしのInterim、Stop後のInterim。`reason` で区別） | §4.3.3 |
| GW_ERR（WARN） | Vector Gateway | リクエスト不正（msg `invalid request body` / `invalid IMSI format`、400応答）、未実装・未設定の接続方式（`backend not implemented`、501応答）、バックエンドの4xx（`backend returned error`） | §4.4.2 |
| BACKEND_EXTERNAL_ERR（WARN） | Vector Gateway | aka-only-server が 4xx で拒否（加入者・クライアント起因） | §4.4.4 |
| SQN_CONFLICT_ERR | Vector API | SQN更新競合リトライ上限超過（**設計済み・未実装。現行では出力されない**） | §4.5 |
| SQN_RESYNC_MAC_ERR | Vector API | AUTS MAC検証失敗 | §4.5 |
| CALC_ERR | Vector API | 計算エラー | §4.5 |

#### 情報（Info） — 運用上の正常ケースを含む

| event_id | ノード | 説明 |
|----------|--------|------|
| VECTOR_IMSI_NOT_FOUND | Auth Server | IMSI未登録（Vector Gatewayが404を返却。ログレベルはERROR） |
| AUTH_POLICY_NOT_FOUND | Auth Server | ポリシー未設定、またはポリシー取得時のValkeyエラー（ログレベルはWARN） |
| AUTH_POLICY_DENIED | Auth Server | ポリシールール不一致（ログレベルはWARN） |
| EAP_UNSUPPORTED_TYPE | Auth Server | 非対応のIdentity種別（EAP-SIM等）検出（ログレベルはWARN） |
| CB_HALF_OPEN | Auth Server | Circuit Breaker Half-Open遷移 |
| CB_CLOSE | Auth Server | Circuit Breaker Close復帰 |
| SQN_RESYNC | Vector API | SQN再同期実行成功 |
| SQN_CONFLICT_RETRY | Vector API | SQN更新競合検出、リトライ実行（**設計済み・未実装。現行では出力されない**） |

> **注記:**
> - Vector Gatewayの `GW_ERR` は複数の状況で共通のevent_idのため、`msg` で状況を区別する（msgの一覧はO-05 §5.3を参照）。Vector Gatewayの正常系は `GW_ROUTE`（バックエンド選択）と `GW_OK`（ベクター取得成功）で、PLMN一致/未一致や内部Vector API（`00`）呼び出しを個別に示すevent_idはない。
> - Valkey接続の復旧を示すevent_idはない。復旧はValkeyエラーのログの出力が止まったことで判断する（§4.1.1）。Valkeyの認証失敗（パスワード不一致）専用のevent_idもなく、Auth Server / Acct Serverでは起動時の `VALKEY_CONN_ERR`、Vector APIではevent_idなしの `failed to connect to Valkey` として出力される（§4.1.2）。
> - Auth Serverにはpanicを捕捉してログに出力する処理はない（§4.2.6）。仮名/高速再認証IDからフル認証への誘導はログを出力しない。
> - SQN競合制御（`SQN_CONFLICT_RETRY` / `SQN_CONFLICT_ERR`、HTTP 409）はD-11 §13.6で設計済みだが、現行のVector APIは単純なHSETでSQNを書き戻すため未実装であり、これらのevent_idは出力されない（§4.5.1）。
> - Admin TUIが出力するevent_idは監査ログの `AUDIT_LOG` のみで、操作失敗を表すevent_idはない（O-05 §11）。

### 2.3 lnavによるリアルタイム監視手順

lnavを使用してログをリアルタイム監視する。詳細な操作方法はO-05 §4を参照。

```bash
# 全サービスのログをリアルタイム監視
lnav ~/eapaka-radius-server-poc/deployments/logs_on_host/*.log

# ERRORレベルのみフィルタリング（lnav内で実行）
:filter-expr :log_level = 'error'

# 特定のevent_idでフィルタリング
:filter-expr :event_id = 'VALKEY_CONN_ERR'

# フィルタの解除
:reset-session
```

> **注記:** `:filter-in` / `:filter-out` は表示行のテキストに対する正規表現のため、`:filter-in event_id = "..."` のような式は書けない。フィールドの値で絞り込む場合は `:filter-expr`（列は `:event_id` のように `:` を付けて参照）を使う。`:filter-expr` は1つだけ設定でき、再実行すると置き換わる。`log_level` の値は小文字（`error` / `warning` / `info` / `debug`）で、`:filter-expr` では `'ERROR'` のような大文字は一致しない。詳細はO-05 §4.3を参照。

ERROR/WARNレベルのイベント発生頻度をSQLで確認する（lnav内で `;` キーでSQLモードに入る）。`event_id` を参照するクエリは、フォーマット名のテーブル `aka_radius_log` を使う（`all_logs` には `event_id` 列がない。テーブルの使い分けはO-05 §4.5を参照）。

```sql
;SELECT event_id, count(*) as cnt
  FROM aka_radius_log
  WHERE log_level IN ('error', 'warning')
    AND log_time > datetime('now', 'localtime', '-1 hour')
  GROUP BY event_id
  ORDER BY cnt DESC
```

## 4. コンポーネント別障害対応

### 4.1 Valkey障害

#### 4.1.1 VALKEY_CONN_ERR — Valkey接続断

**症状:** Valkeyに接続できず、認証・課金・ベクター生成が失敗する。ノードごとに以下のログが出力される（D-04 §4.3）。

| ノード | 起動時の接続失敗 | 実行時のValkeyエラー |
|--------|------------------|----------------------|
| Auth Server | `VALKEY_CONN_ERR`（プロセス終了。コンテナが再起動を繰り返す） | 専用のevent_idなし。`EAP_CTX_CREATE_ERR` / `EAP_CTX_UPDATE_ERR` / `SESSION_CREATE_ERR`（ERROR）、`EAP_CTX_NOT_FOUND` / `AUTH_POLICY_NOT_FOUND` / `RADIUS_SECRET_ERR` / `SESSION_INDEX_ERR`（WARN）の `error` にValkeyの接続エラーが出る。認証はAccess-Rejectとなる |
| Acct Server | `VALKEY_CONN_ERR`（プロセス終了） | `VALKEY_CONN_ERR`（msg `duplicate check failed` / `valkey error`）、`DB_WRITE_ERR`。Accounting-Responseは返すが、セッションデータが更新されない |
| Vector API | `failed to connect to Valkey`（event_idなし。プロセス終了） | `VALKEY_CONN_ERR`（500応答。`error` 属性なし）。Vector Gatewayは502を返し、Auth Serverは `VECTOR_API_ERR`（`http_status=502`）を出力する |

Valkey接続の復旧を示すログはない。Valkeyクライアントは次のコマンド実行時に接続を張り直すため、復旧は上記のエラーログの出力が止まったことで判断する。

**確認手順:**

```bash
# Valkeyコンテナの状態確認
cd ~/eapaka-radius-server-poc/deployments
docker compose ps valkey

# Valkeyログの確認
docker compose logs --tail 50 valkey

# 手動接続テスト
docker compose exec valkey valkey-cli -a "${VALKEY_PASSWORD}" ping
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| Valkeyコンテナが停止している | `docker compose up -d valkey` で再起動 |
| メモリ不足でValkeyがOOM Killed | `docker stats --no-stream` でメモリ確認後、§4.1.3参照 |
| AOFファイル破損 | §4.1.4参照 |

> **参考:** D-06 §4.4（Graceful Degradation）、O-05 §8.2（接続障害の調査）

#### 4.1.2 Valkey認証失敗（パスワード不一致）

**症状:** Valkey自体は稼働しているが、パスワード不一致で接続が拒否される。認証失敗専用のevent_id（旧記載の `VALKEY_AUTH_ERR`）はなく、起動時の接続確認で失敗するため、Auth Server / Acct Serverは `VALKEY_CONN_ERR`、Vector APIはevent_idなしの `failed to connect to Valkey` を出力して終了する（コンテナが再起動を繰り返す）。`error` にValkeyの応答（`WRONGPASS` / `NOAUTH` 等）が含まれる。

**確認手順:**

```bash
# Valkeyの応答確認（パスワードなし）
docker compose exec valkey valkey-cli ping

# .envのパスワード確認
grep VALKEY_PASSWORD ~/eapaka-radius-server-poc/deployments/.env
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| `.env` のパスワードとValkey設定が不一致 | `.env` の `VALKEY_PASSWORD` を確認し、全サービスを再起動 |
| コンテナ再ビルド時に環境変数が反映されていない | `docker compose down && docker compose up -d` で再起動 |

> **参考:** D-08 §2.1（Valkey設定）、B-02 §13.2

#### 4.1.3 メモリ超過

**症状:** Valkeyが応答しない、またはOOM Killedでコンテナが停止する。

**確認手順:**

```bash
# Valkeyメモリ使用量の確認
docker compose exec valkey valkey-cli -a "${VALKEY_PASSWORD}" info memory

# コンテナのメモリ使用状況
docker stats --no-stream valkey

# OOM Killedの確認
docker inspect valkey --format='{{.State.OOMKilled}}'
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| セッションデータの蓄積 | 期限切れセッションの確認: `valkey-cli -a "${VALKEY_PASSWORD}" dbsize` |
| maxmemory設定が不適切 | D-08 §2.2のメモリ設定を確認し、必要に応じて調整 |

> **参考:** D-08 §2.2（メモリ設定）

#### 4.1.4 AOFファイル破損

**症状:** Valkeyが起動時にエラーで停止する。ログに `Bad file format reading the append only file` 等が出力される。

**確認手順:**

```bash
# Valkeyログの確認
docker compose logs --tail 50 valkey
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| 予期しないシャットダウンによるAOF破損 | AOF修復を試行: `docker compose exec valkey valkey-check-aof --fix /data/appendonly.aof` |
| AOF修復が不可能 | §5.3のバックアップリストア手順を実行 |

> **参考:** D-08 §2.4（バックアップ・リストア）

#### 4.1.5 Valkey復旧手順まとめ

```
[Valkey障害検知]
      │
      ├─ コンテナ停止 ──▶ docker compose up -d valkey
      │                       │
      │                  起動成功？
      │                  ├─ Yes ──▶ 復旧完了
      │                  └─ No ───▶ AOF破損？
      │                              ├─ Yes ──▶ valkey-check-aof --fix
      │                              │              │
      │                              │         修復成功？
      │                              │         ├─ Yes ──▶ 再起動
      │                              │         └─ No ───▶ バックアップリストア（§5.3）
      │                              └─ No ───▶ ログ確認・エスカレーション（§6）
      │
      └─ 接続エラー ──▶ パスワード確認 → 全サービス再起動（§5.2）
```

### 4.2 Auth Server障害

#### 4.2.1 VECTOR_API_ERR / VECTOR_CONN_ERR — Vector Gateway呼び出しエラー

**症状:** Auth Serverのログに `VECTOR_API_ERR`（Vector Gatewayが404以外のエラーを返却）または `VECTOR_CONN_ERR`（Vector Gatewayへの接続失敗・タイムアウト）が出力され、認証ベクターの取得に失敗する。該当する認証はAccess-Rejectとなる。

`VECTOR_API_ERR` はHTTPクライアント層（msg `vector api error`、`trace_id` なし）と認証フロー層（msg `Vector APIエラー`、`trace_id` あり）の2行が出る。404の場合は認証フロー層が `VECTOR_IMSI_NOT_FOUND`（加入者未登録）になる。

**確認手順:**

```bash
# Vector Gatewayの状態確認
curl -fsS http://localhost:8080/health

# Auth Serverのログでエラー詳細を確認（http_status を確認）
cd ~/eapaka-radius-server-poc/deployments
docker compose logs --tail 30 auth-server | grep -E '"event_id":"(VECTOR_API_ERR|VECTOR_CONN_ERR|VECTOR_IMSI_NOT_FOUND|VECTOR_UNKNOWN_ERR)"'

# 対応するVector Gateway側のエラー（msg で状況を区別）
docker compose logs --tail 30 vector-gateway | grep '"event_id":"GW_ERR"'
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| Vector Gatewayが停止している（`VECTOR_CONN_ERR`） | `docker compose up -d vector-gateway` で再起動 |
| Vector APIが停止している（`VECTOR_API_ERR` の `http_status=502`、Vector Gatewayに `GW_ERR` / `backend communication error`） | `docker compose up -d vector-api` で再起動（§4.4.1） |
| リクエスト不正・未実装の接続方式（`http_status=400` / `501`） | §4.4.2 |
| ネットワーク（Docker内部）の問題 | `docker compose down && docker compose up -d` で全サービス再起動 |
| aka-only-server（接続方式01）の通信障害 | `http_status=502` が該当 PLMN の加入者で出ている場合は §4.4.5 |

> **参考:** D-06 §3.1（Auth Serverエラー処理）、D-06 §4.1（タイムアウト設定）

#### 4.2.2 CB_OPEN — Circuit Breaker Open状態

**症状:** Auth Serverのログに `CB_OPEN` が出力される。Vector Gateway障害が継続し、Circuit BreakerがOpen状態に遷移したことを示す。Open状態中は全認証がAccess-Rejectとなり、Vector Gatewayを呼び出さずに拒否したリクエストごとに `VECTOR_CB_OPEN` が出力される。Circuit Breakerの失敗回数に数えられるのは `VECTOR_CONN_ERR` と、`http_status` が5xx（501を除く）の `VECTOR_API_ERR` のみ。

**確認手順:**

```bash

cd ~/eapaka-radius-server-poc/deployments
docker compose logs auth-server | grep -E "CB_OPEN|CB_HALF_OPEN|CB_CLOSE"
```

lnavで状態遷移を時系列で確認:

```sql
;SELECT log_time, event_id
  FROM aka_radius_log
  WHERE event_id LIKE 'CB_%'
  ORDER BY log_time DESC
  LIMIT 20
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| Vector Gateway/APIの一時的障害 | Vector Gateway/APIの復旧を確認（§4.4, §4.5）。30秒後にHalf-Openに自動遷移 |
| Vector Gateway/APIの永続的障害 | §4.4, §4.5の復旧手順を実行後、§5.4でCB復旧を確認 |

**注意:** Circuit Breaker は接続方式ごとに分かれていない。接続方式01（aka-only-server）の通信障害でOpenになると、内部Vector API（`00`）向けの PLMN の認証も止まる。

> **参考:** D-06 §4.3（Circuit Breaker設定: 失敗5回/10秒でOpen、30秒後Half-Open、成功2回でClose）

#### 4.2.6 パニック・異常終了

**症状:** Auth Serverのコンテナが停止・再起動を繰り返す、またはプロセスが異常終了する。

Auth Serverにはpanicを捕捉してログに出力する処理はない（`SYS_ERR` はAuth Serverでは出力されない）。panicした場合はプロセスが終了し、Goのスタックトレースがコンテナの標準エラー出力に出る。RADIUSサーバーの異常終了はevent_idなしのERRORログ `サーバーエラー`、起動時のValkey接続失敗は `VALKEY_CONN_ERR`（§4.1）で出力される。

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments

# コンテナの状態確認
docker compose ps auth-server

# スタックトレース・異常終了時のログの確認
docker compose logs --tail 100 auth-server | grep -E 'panic:|goroutine |"msg":"サーバーエラー"|VALKEY_CONN_ERR'
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| Panic（プログラムバグ） | コンテナを再起動（§5.1）。ログを保全し開発担当者へエスカレーション（§6） |
| メモリ不足 | `docker stats --no-stream` でリソース確認。必要に応じてコンテナのリソース制限を調整 |
| 起動時のValkey接続失敗（`VALKEY_CONN_ERR`） | §4.1の手順を実行 |

> **参考:** D-06 §2.2（重大度レベル定義）

### 4.3 Acct Server障害

#### 4.3.1 ACCT_SESSION_NOT_FOUND — セッション不在

**症状:** Acct Serverのログに `ACCT_SESSION_NOT_FOUND` が出力される。次のいずれかである。

- Accounting-Start受信時に、Class属性（セッションUUID）がない（msg `class attribute missing or invalid`、`acct_session_id` 付き）
- Accounting-Start / Interim受信時に、Class属性のセッションUUIDに対応するセッション `sess:{UUID}` が存在しない（msg `session not found`、`class_uuid` 付き）

セッションの不在とTTL超過は区別できないため、いずれもこのevent_idになる（旧記載の `ACCT_SESSION_EXPIRED` は出力されない）。課金ログ（`ACCT_START` / `ACCT_INTERIM`）は出力されるが、セッションデータは更新されない（不在のセッションを新たに作成することもない）。Class属性のないInterimはセッションを更新せず、このログも出力しない。Stopではセッションの存在を確認しない（不在でもログは出力しない）。

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments
docker compose logs --tail 30 acct-server | grep ACCT_SESSION_NOT_FOUND
```

`class_uuid` はAuth Serverの `AUTH_SUCCESS` の `session_id` と一致する。対応する認証成功ログがあるかを確認する（O-05 §8.4）。

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| Class属性なし（`class attribute missing or invalid`） | NAS側でAccess-AcceptのClass属性をAccounting-Requestに付与する設定を確認 |
| セッションTTL超過（24h経過で自動削除） | 正常動作。認証から長時間経過後にStartが送信されていないか、Interimの送信間隔が24hを超えていないかNAS側を確認（Start / Interimを受信するとTTLは24hにリセットされる） |
| Valkey再起動によるセッション消失 | Valkey復旧後、端末が再接続すれば新セッションが作成される。再接続までの間、既存セッションのInterimで `session not found` が出力される |
| 認証なしの課金リクエスト | NAS側の設定を確認。Auth成功（`AUTH_SUCCESS`）後にStartが送信されているかログで確認 |

> **参考:** O-05 §8.4（課金データ不整合の調査）

#### 4.3.3 ACCT_DUPLICATE_START / ACCT_SEQUENCE_ERR — 重複・順序異常

**症状:** Acct Serverのログに `ACCT_DUPLICATE_START` または `ACCT_SEQUENCE_ERR` が出力される。どちらもWARNで、Accounting-Responseは返却される。`msg` と `reason` で次のように区別する（D-04 §3.2.3）。

| event_id | msg | reason | 意味 | 以降の処理 |
|----------|-----|--------|------|-----------|
| ACCT_DUPLICATE_START | `duplicate accounting start` | - | 同一Acct-Session-IdのStartを再受信（Start / Interim受信済み） | 処理を終了（`ACCT_START` は出力しない） |
| ACCT_DUPLICATE_START | `duplicate accounting interim` | - | 直前に受信したInterimと同一オクテット値のInterim（再送） | 処理を終了（`ACCT_INTERIM` は出力しない） |
| ACCT_SEQUENCE_ERR | `sequence error` | `start_after_stop` | Stop受信後に同一Acct-Session-IdでStart | 新規セッションとして処理を継続 |
| ACCT_SEQUENCE_ERR | `interim sequence error` | `no_start_received` | Startを受信していないAcct-Session-IdのInterim | 処理を継続（`ACCT_INTERIM` を出力し、セッションが存在すれば更新） |
| ACCT_SEQUENCE_ERR | `interim sequence error` | `interim_after_stop` | Stop受信後に同一Acct-Session-IdでInterim | 処理を継続（Stop済みのためセッションは通常存在せず、`ACCT_SESSION_NOT_FOUND` も出力されうる） |

重複・順序の判定には `acct:seen:{Acct-Session-Id}`（TTL 24h）を使う（D-02 §3.G）。

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments
docker compose logs acct-server | grep -E "ACCT_DUPLICATE_START|ACCT_SEQUENCE_ERR" | tail -20

# 順序異常の理由別件数
docker compose logs acct-server | grep ACCT_SEQUENCE_ERR | grep -oE '"reason":"[a-z_]+"' | sort | uniq -c

# 特定のAcct-Session-Idの受信順序を確認（値は実際のIDに置き換える）
docker compose logs acct-server | grep '"acct_session_id":"sess-abc123"'
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| NASからの重複リクエスト送信 | 通常は一時的。NAS側のリトライ設定を確認 |
| ネットワーク遅延による再送 | 通常は一時的。頻発する場合はネットワーク品質を確認 |
| NAS側のAccounting設定不備 | NAS側のAccounting設定（Start/Interim/Stop送信順序）を確認 |
| Startの欠落・未送信（`no_start_received`） | NASがStartを送信しているか、Startがパケットロスしていないかを確認。Acct Serverの停止中・Valkeyデータ消失（`acct:seen` も消える）・`acct:seen` のTTL（24h）超過の後に届いたInterimでも出力される |
| Stop後のInterim（`interim_after_stop`） | パケットの順序入れ替わり（遅延したInterimがStopの後に到着）か、NASがStop後もInterimを送信していないかを確認。単発なら通常は一時的 |
| Acct-Session-Idの再利用（`start_after_stop`） | NASがAcct-Session-Idを再利用していないか確認 |

> **参考:** O-05 §8.4（課金データ不整合の調査）

### 4.4 Vector Gateway障害

#### 4.4.1 GW_ERR（backend communication error ほか）— バックエンド呼び出し失敗

| Vector APIの内部エラー | §4.5の手順で原因を調査 |

| `routing error` / `unexpected backend error` | ログを保全し開発担当者へエスカレーション（§6） |

#### 4.4.2 GW_ERR（invalid request body / invalid IMSI format ほか）— リクエスト不正・未実装接続方式

**症状:** Vector Gatewayのログに `GW_ERR`（WARN）が以下のmsgで出力される。

| msg | 応答 | 内容 |
|-----|------|------|
| `invalid request body` | 400（detail `Invalid request body`） | リクエストJSON不正 |
| `invalid IMSI format` | 400（detail `IMSI must be 15 digits`） | IMSI形式不正 |
| `backend not implemented` | 501 | 未実装・未設定の接続方式ID |
| `backend returned error` | バックエンドの4xxをそのまま返却 | 404は加入者未登録（Auth Serverは `VECTOR_IMSI_NOT_FOUND`） |

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments

# WARNレベルのGW_ERRを確認
docker compose logs --tail 100 vector-gateway | grep '"event_id":"GW_ERR"' | grep -E '"msg":"(invalid request body|invalid IMSI format|backend not implemented|backend returned error)"'
```

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| IMSI形式エラー（`invalid IMSI format`） | Auth Serverからのリクエスト内容を確認。加入者データのIMSI登録値を確認 |
| Auth Serverのバグ（`invalid request body`） | ログを保全し開発担当者へエスカレーション（§6） |
| 未実装・未設定の接続方式（`backend not implemented`） | `.env` の `VECTOR_GATEWAY_PLMN_MAP` と接続方式01の設定を確認（§4.4.4） |
| バックエンドの4xx（`backend returned error`、`http_status=404`） | 加入者未登録。接続方式00はAdmin TUIで、接続方式01はaka-only-serverに加入者を登録 |

> **参考:** D-06 §3.3（Vector Gatewayエラー処理）

#### 4.4.3 aka-only-server 接続（接続方式01）— 確認ポイント

`VECTOR_GATEWAY_PLMN_MAP` で `01` に向けた PLMN の認証ベクターは、Vector Gateway が外部の aka-only-server から取得する。この経路の障害は、まず以下のログで切り分ける。

| ノード | ログ | 見る項目 |
|-------|------|---------|
| Vector Gateway | `BACKEND_EXTERNAL_ERR`（WARN: aka-only-server が 4xx で拒否 / ERROR: 通信失敗・5xx・不正応答） | `http_status`（応答なしは `0`）、`cause`（aka-only-server のエラー原因）、`error`（4xx は detail を含む） |
| Vector Gateway | `BACKEND_EXTERNAL_CALL`（INFO: 成功）、`GW_ROUTE`（`backend_id` が `01` か） | 振り分け先と成否 |
| Auth Server | `VECTOR_IMSI_NOT_FOUND`、`VECTOR_API_ERR`（`http_status`） | Vector Gateway から返ったステータス |
| aka-only-server | aka-only-server のコンテナログ | `client_id`、`imsi`、時刻 |

```bash
cd ~/eapaka-radius-server-poc/deployments

# Vector Gateway: aka-only-server 呼び出しのエラー
docker compose logs --tail 50 vector-gateway | grep BACKEND_EXTERNAL_ERR

# Auth Server: Vector Gateway からのエラー応答
docker compose logs --tail 50 auth-server | grep -E "VECTOR_IMSI_NOT_FOUND|VECTOR_API_ERR"

# aka-only-server のログ（aka-only-server 側の compose ディレクトリで実行）
docker compose logs --tail 50 aka-only-server
```

aka-only-server の応答と、Vector Gateway・Auth Server での見え方の対応は以下のとおり。

| aka-only-server の応答 | `cause` | Vector Gateway のログ | Auth Server への応答 | Auth Server のログ | CB の失敗回数 |
|----------------------|---------|---------------------|-------------------|-------------------|-------------|
| 404 | `USER_NOT_FOUND` | WARN | 404 | `VECTOR_IMSI_NOT_FOUND` | 数えない |
| 403 | `AUTHENTICATION_REJECTED` | WARN | 403 | `VECTOR_API_ERR`（`http_status=403`） | 数えない |
| 400 | `INVALID_MSG_FORMAT` ほか | WARN | 400 | `VECTOR_API_ERR`（`http_status=400`） | 数えない |
| 501 / 5xx | `AUTH_TYPE_NOT_SUPPORTED` / `SYSTEM_FAILURE` | ERROR | 502 | `VECTOR_API_ERR`（`http_status=502`） | **数える** |
| 応答なし（タイムアウト・接続失敗・TLSハンドシェイク失敗） | （空、`http_status=0`） | ERROR | 502 | 同上 | **数える** |
| aka-only-server 形式でない 4xx（URL誤りによる `404 page not found` 等）、想定外のステータス、不正な200応答 | （空） | ERROR | 502 | 同上 | **数える** |

**ログの突き合わせ:** aka-only-server は Trace ID を記録せず、IMSI をマスクしない。`trace_id` で aka-only-server のログを検索することはできないため、Vector Gateway のログ（`trace_id`、時刻、マスク済み IMSI）と aka-only-server のログ（`client_id`、`imsi`、時刻）を、**時刻・IMSI・client_id** で突き合わせる。aka-only-server のログは IMSI がマスクされていないため、保全・共有の際は取り扱いに注意する。

**フォールバックしない:** aka-only-server が失敗しても、内部Vector API（`00`）に切り替えて再試行することはない（SQN が競合するため）。復旧は aka-only-server 側の障害を取り除くことで行う。

> **参考:** D-12（接続方式01のエラー変換）、O-05（ログ解析）

#### 4.4.4 特定 PLMN の加入者だけ Access-Reject になる

**症状:** `01` に向けた PLMN の加入者だけ Access-Reject になり、他の PLMN（`00`）の加入者は正常に認証できる。

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments

# 該当 PLMN が 01 に向いているか
grep -E "VECTOR_GATEWAY_(MODE|PLMN_MAP|AKAONLY_URL)" .env

# 振り分け先と aka-only-server の応答
docker compose logs --tail 100 vector-gateway | grep -E "GW_ROUTE|GW_ERR|BACKEND_EXTERNAL_ERR"
```

**主な原因と対処:**

| ログの内容 | 原因 | 対処 |
|-----------|------|------|
| `http_status=404`、`cause=USER_NOT_FOUND` | aka-only-server に加入者が未登録（Admin TUI にだけ登録した等） | aka-only-server に加入者を登録（O-01 §3.5） |
| `http_status=403`、`error` に `client is not allowed for this subscriber`（mTLS 接続時） | 加入者の許可クライアントに `radius-gw` が含まれていない | aka-only-server で該当加入者の許可クライアントに `radius-gw` を追加 |
| 同上（平文HTTP 接続時: URL が `http://`） | 加入者の平文HTTP 許可が立っていない（または許可クライアント外） | aka-only-server で該当加入者の平文HTTP 許可を立てる、または mTLS 接続に戻す |
| `http_status=403`、`error` に `AUTS verification failed` | 再同期時の AUTS 検証失敗（aka-only-server 側の Ki/OPc が SIM と不一致等）。内部Vector APIでは 400（`SQN_RESYNC_MAC_ERR`）だった事象 | aka-only-server 側の Ki/OPc を確認 |
| `BACKEND_EXTERNAL_CALL` は成功、Auth Server に `AUTH_RES_MISMATCH` / `AUTH_MAC_INVALID` | aka-only-server 側の Ki/OPc/AMF が SIM と不一致 | aka-only-server 側の加入者情報を確認 |
| `BACKEND_EXTERNAL_CALL` は成功、Auth Server に `AUTH_POLICY_NOT_FOUND` | Admin TUI に認可ポリシーが未登録 | Admin TUI でポリシーを登録（O-01 §5、O-02） |
| `GW_ERR`（`backend not implemented`、`backend_id=01`） | `VECTOR_GATEWAY_AKAONLY_URL` が未設定のまま PLMN を `01` に向けている（Auth Server には 501） | `.env` の接続設定を確認し、vector-gateway を再起動（§4.4.6） |
| `GW_ROUTE` の `backend_id` が `00` | PLMN マップの誤り、または `VECTOR_GATEWAY_MODE=passthrough` | `.env` を修正し vector-gateway を再起動。`00` に向いている場合は Admin TUI 側の加入者登録を確認 |

> **参考:** O-01 §3.5（aka-only-server に向けた PLMN の加入者）

#### 4.4.5 全認証が停止する（aka-only-server 通信障害による CB オープン）

**症状:** Auth Server のログに `CB_OPEN` が出力され、PLMN に関係なく全ての認証が Access-Reject になる。その直前に Vector Gateway の `BACKEND_EXTERNAL_ERR`（ERROR）が連続している。

aka-only-server との通信失敗（502）は Auth Server の Circuit Breaker の失敗回数に数えられる。Circuit Breaker は接続方式ごとに分かれていないため、Open になると内部Vector API（`00`）向けの認証も止まる。

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments

# 通信失敗の内容（http_status=0 の error を確認）
docker compose logs --tail 100 vector-gateway | grep BACKEND_EXTERNAL_ERR

# Circuit Breaker の状態遷移
docker compose logs auth-server | grep -E "CB_OPEN|CB_HALF_OPEN|CB_CLOSE" | tail -10
```

**主な原因と対処:**

| `error` の内容 | 原因 | 対処 |
|---------------|------|------|
| `connection refused` / `no such host` | aka-only-server の停止、共有ネットワークへの未参加（オーバーレイ `docker-compose.aka-av.yml` を重ねずに起動した、aka-only-server より先に起動した）、URL の誤り | aka-only-server の稼働を確認し、オーバーレイを重ねて vector-gateway を起動し直す（§5.2 の注意参照）。URL を確認 |
| タイムアウト（`Timeout exceeded` / `deadline exceeded` を含むエラー） | aka-only-server の応答遅延、ネットワーク障害 | aka-only-server の状態とホスト間の疎通を確認 |
| `tls: failed to verify certificate` | aka-only-server のサーバー証明書が `av-server.pem` と一致しない、または URL のホスト名がサーバー証明書の SAN に含まれていない | §4.4.7 |
| `remote error: tls: bad certificate` など | クライアント証明書が aka-only-server に未登録・無効化・期限切れ | §4.4.7 |
| `http_status` が 5xx（`cause=SYSTEM_FAILURE` 等） | aka-only-server の内部エラー | aka-only-server 側のログを確認し、aka-only-server の管理者へ連絡 |
| `http_status=404`、`cause` が空 | URL のパス誤り（aka-only-server 以外が応答している） | `VECTOR_GATEWAY_AKAONLY_URL` を確認（ベースURLのみを指定する） |

原因を取り除いた後、§5.4 の手順で Circuit Breaker の復旧（`CB_CLOSE`）を確認する。aka-only-server が復旧するまでは、`01` の PLMN の認証要求があるたびに失敗が数えられ、Circuit Breaker が再び Open になりうる。早期に復旧できない場合は開発担当者へエスカレーションする（§6）。

> **参考:** D-06 §4.3（Circuit Breaker設定）

#### 4.4.6 vector-gateway が起動しない（再起動ループ）

**症状:** `docker compose ps` で vector-gateway が `Restarting` を繰り返す。

**確認手順:**

```bash
cd ~/eapaka-radius-server-poc/deployments
docker compose logs --tail 20 vector-gateway | grep -E "failed to load config|failed to initialize backends|failed to parse PLMN map"
```

**主な原因と対処:**

| ログの内容 | 原因 | 対処 |
|-----------|------|------|
| `failed to load config`: `VECTOR_GATEWAY_AKAONLY_URL must start with http:// or https://` | URL のスキームがない・誤り | `.env` の URL を `https://` または `http://` で始める |
| `failed to load config`: `VECTOR_GATEWAY_AKAONLY_CLIENT_CERT is required for https` / `..._SERVER_CERT is required for https` | `https://` なのに証明書の指定がない | `.env` に `CLIENT_CERT` と `SERVER_CERT`（コンテナ内パス `/certs/...`）を設定 |
| `failed to load config`: `VECTOR_GATEWAY_AKAONLY_TIMEOUT must be positive` | タイムアウトが 0 以下 | 正の値（例 `5s`）を設定 |
| `failed to initialize backends`: `failed to read client certificate` / `failed to read server certificate` | 証明書ファイルが `deployments/certs/` にない、パスの誤り | PEM を `deployments/certs/` に置き、`.env` のパスを確認 |
| `failed to initialize backends`: `failed to parse client certificate and key` / `no valid certificate found` | PEM の内容不正、証明書と秘密鍵の不一致 | aka-only-server 側で証明書を取り直す（B-02 の接続手順） |
| `failed to parse PLMN map` | `VECTOR_GATEWAY_PLMN_MAP` の書式誤り | `PLMN:ID`（PLMN 5〜6桁、ID 2桁）のカンマ区切りに修正 |

`.env` を修正した後は vector-gateway を作り直す（§5.2 の注意のとおり、同一ホスト構成ではオーバーレイを重ねる。別ホスト構成では `-f` の指定は不要）。

```bash
docker compose -f docker-compose.yml -f docker-compose.aka-av.yml up -d vector-gateway
```

#### 4.4.7 証明書関連（mTLS）

**症状:** `BACKEND_EXTERNAL_ERR`（ERROR、`http_status=0`）の `error` に TLS 関連のエラーが出て、`01` の PLMN の認証が失敗する（Auth Server には 502）。

**主な原因と対処:**

| 原因 | 対処 |
|------|------|
| aka-only-server の AV 用サーバー証明書を作り直した（`tls: failed to verify certificate`） | aka-only-server 側で `av-cert` を実行して `av-server.pem` を取り直し、`deployments/certs/` に置いて vector-gateway を再起動する（`docker compose restart vector-gateway`。証明書は起動時にだけ読み込まれる） |
| URL のホスト名がサーバー証明書の SAN に含まれていない（同上） | URL のホスト名を確認する。別ホスト構成では、そのアドレスを aka-only-server 側の `AKA_AV_TLS_HOSTS` に入れて証明書を作り直し、`av-server.pem` を取り直す |
| クライアント証明書の期限切れ（既定 825 日） | aka-only-server 側でクライアント証明書を作り直して登録し（B-02 の接続手順）、`av-client.pem` を差し替えて vector-gateway を再起動する。新しいクライアントとして登録した場合はクライアントIDが変わるため、加入者の許可クライアントも更新する |
| クライアント証明書が aka-only-server に未登録・無効化されている（`remote error: tls: bad certificate` など） | aka-only-server が TLS ハンドシェイクで拒否するため、通信失敗（502）に見える。aka-only-server 側でクライアントの登録・有効状態を確認する |

**注意:** 証明書不備による失敗は全て 502 となり、Auth Server の Circuit Breaker の失敗回数に数えられる。放置すると Circuit Breaker が Open になり `00` の認証も止まる（§4.4.5）。

### 4.5 Vector API障害

#### 4.5.1 SQN_CONFLICT_ERR — SQN競合エラー（設計済み・未実装）

> **注記（現行では出力されない）:** SQN更新の競合制御（WATCH/MULTI による CAS 更新、`SQN_CONFLICT_RETRY` / `SQN_CONFLICT_ERR`、HTTP 409）はD-11 §13.6で設計されているが、現行のVector APIは単純なHSETでSQNを書き戻すため未実装である。**現行実装では `SQN_CONFLICT_RETRY` / `SQN_CONFLICT_ERR` は出力されず、409も返さない。** 以下の手順は競合制御の実装後に適用する。

**症状（実装後）:** Vector APIのログに `SQN_CONFLICT_ERR` が出力される。SQN更新のリトライが上限を超過した。

**現行での確認方法:** 競合を直接示すログはない。同一加入者への同時認証によるSQN更新の競合が疑われる場合は、同一IMSIの `CALC_OK` が短時間に複数出力されていないかを確認する（O-05 §8.3）。

```bash
cd ~/eapaka-radius-server-poc/deployments
docker compose logs vector-api | grep '"event_id":"CALC_OK"' | grep -F '<対象IMSI（マスク済み。例: 440101********0）>' | tail -20
```

**主な原因と対処（実装後）:**

| 原因 | 対処 |
|------|------|
| 同一加入者への同時認証リクエスト | 通常は `SQN_CONFLICT_RETRY` でリトライ成功する。ERRが頻発する場合は負荷状況を確認 |
| Valkeyの応答遅延 | §4.1の手順でValkey状態を確認 |

> **参考:** D-11 §13.6（SQN競合制御の設計）、O-05 §8.3（SQN再同期の調査）

## 5. 復旧手順

### 5.1 個別コンテナ再起動

特定のサービスのみ再起動する場合。

```bash
cd ~/eapaka-radius-server-poc/deployments

# 対象サービスの再起動
docker compose restart <サービス名>

# 再起動後の状態確認
docker compose ps <サービス名>

# ログで正常起動を確認
docker compose logs --tail 10 <サービス名>
```

サービス名の一覧: `auth-server`, `acct-server`, `vector-gateway`, `vector-api`, `valkey`, `fluent-bit`

### 5.2 全サービス再起動

全サービスを停止・再起動する場合。

```bash
cd ~/eapaka-radius-server-poc/deployments

# 全サービスの停止
docker compose down

# 全サービスの起動
docker compose up -d

# 全コンテナの状態確認
docker compose ps

# ヘルスチェック（全サービスが healthy になるまで待機）
sleep 30
docker compose ps
```

> **注意:** `docker compose down` はコンテナを削除するが、Valkeyのデータボリュームは保持される。

> **注意（aka-only-server を同一ホストで使う場合）:** vector-gateway を aka-only-server の共有ネットワークに参加させるため、起動時はオーバーレイを重ねる。重ねずに起動すると vector-gateway が aka-only-server に届かなくなる（`no such host`）。共有ネットワークは aka-only-server 側が作るため、aka-only-server を先に起動しておく。
>
> ```bash
> docker compose -f docker-compose.yml -f docker-compose.aka-av.yml up -d
> ```

### 5.3 Valkeyデータ復旧（バックアップリストア）

D-08 §2.4に基づくバックアップからのリストア手順。

```bash
cd ~/eapaka-radius-server-poc/deployments

# 1. 全サービスの停止
docker compose down

# 2. 現在のValkeyデータボリュームを削除
docker volume rm deployments_valkey-data

# 3. バックアップファイルの確認（最新のバックアップを選択）
ls -lt ~/eapaka-radius-server-poc/backups/valkey/

# 4. Valkeyのみ起動してリストア
docker compose up -d valkey
sleep 5

# 5. バックアップからリストア（ファイル名は実際のバックアップに合わせる）
docker compose exec -T valkey valkey-cli -a "${VALKEY_PASSWORD}" --pipe < ~/eapaka-radius-server-poc/backups/valkey/<バックアップファイル名>

# 6. リストア結果の確認
docker compose exec valkey valkey-cli -a "${VALKEY_PASSWORD}" dbsize

# 7. 全サービスの起動
docker compose up -d

# 8. 状態確認
docker compose ps
```

> **参考:** D-08 §2.4（バックアップ・リストア手順）

### 5.4 Circuit Breaker復旧確認

Circuit BreakerがOpen状態になった後、Vector Gateway/APIの復旧により自動的にClose状態に戻ることを確認する。

```bash
cd ~/eapaka-radius-server-poc/deployments

# 1. Vector Gateway/APIの状態確認
curl -fsS http://localhost:8080/health
curl -fsS http://localhost:8081/health

# 2. Circuit Breaker状態遷移をログで確認
docker compose logs auth-server | grep -E "CB_OPEN|CB_HALF_OPEN|CB_CLOSE" | tail -10
```

復旧フロー:
1. Vector Gateway/API（接続方式01 が原因の場合は aka-only-server 接続）復旧後、30秒でHalf-Open状態に自動遷移（`CB_HALF_OPEN`）
2. Half-Open状態で2回成功するとClose状態に復帰（`CB_CLOSE`）
3. `CB_CLOSE` がログに出力されれば復旧完了

> **参考:** D-06 §4.3（Circuit Breaker設定）

### 5.5 SQNリセット手順（Admin TUI経由）

特定加入者のSQN値をリセットする場合、Admin TUIを使用する。

```bash
# Admin TUIの起動
cd ~/eapaka-radius-server-poc/deployments
docker compose exec -it admin-tui /app/admin-tui
```

Admin TUI操作手順:
1. メインメニューから「Subscriber Management」を選択
2. 対象加入者を一覧から選択
3. 加入者の編集画面でSQN値を `000000000000`（初期値）にリセット
4. 保存を実行

**注意:** 接続方式01（aka-only-server）に向けた PLMN の加入者の SQN は aka-only-server が管理しているため、Admin TUI では変更できない。SQN の不整合は通常、再同期で自動的に追従する。リセットが必要な場合は aka-only-server 側で行う。

> **参考:** O-01 §3.3（加入者の編集）、O-01 §3.5（aka-only-server に向けた PLMN の加入者）

## 6. エスカレーション

### 6.1 対応体制

| 役割 | 担当 | 対応範囲 |
|------|------|---------|
| **一次対応者**（運用担当者） | 運用チーム | ヘルスチェック、サービス再起動、ログ確認、定型復旧作業 |
| **二次対応者**（開発担当者） | 開発チーム | ログ分析、設定修正、コード修正、非定型障害の調査 |

### 6.2 エスカレーション判断基準

以下のいずれかに該当する場合、二次対応者（開発担当者）へエスカレーションする。

| 条件 | 具体例 |
|------|--------|
| 再起動で復旧しない | コンテナ再起動を2回実施しても同じエラーが再発 |
| プロセスの異常終了・`SYS_ERR` が発生した | Auth Server等のpanicによる異常終了（§4.2.6）、Acct Serverの `SYS_ERR` |
| 原因が特定できない | ログを確認しても障害の原因が判断できない |
| データ不整合の疑い | Valkeyのデータが不正な状態と推測される |
| 全加入者に影響する障害 | `AUTH_RES_MISMATCH` 等が全加入者で発生 |
| セキュリティ懸念 | 不正なアクセスパターンの検出 |

### 6.3 ログエビデンスの保全方法

エスカレーション時には、障害発生時のログを保全して開発担当者に提供する。

```bash
# 障害発生時刻前後のログをバックアップ
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
mkdir -p ~/eapaka-radius-server-poc/incident_logs/${TIMESTAMP}

# 全サービスのログをコピー
cp ~/eapaka-radius-server-poc/deployments/logs_on_host/*.log \
   ~/eapaka-radius-server-poc/incident_logs/${TIMESTAMP}/

# docker compose psの出力を保存
cd ~/eapaka-radius-server-poc/deployments
docker compose ps > ~/eapaka-radius-server-poc/incident_logs/${TIMESTAMP}/container_status.txt

# docker statsの出力を保存
docker stats --no-stream > ~/eapaka-radius-server-poc/incident_logs/${TIMESTAMP}/resource_usage.txt

# Valkeyの情報を保存
docker compose exec valkey valkey-cli -a "${VALKEY_PASSWORD}" info \
   > ~/eapaka-radius-server-poc/incident_logs/${TIMESTAMP}/valkey_info.txt 2>/dev/null
```

接続方式01（aka-only-server）が関係する障害では、aka-only-server 側のログも同じ時間帯で保全する（aka-only-server 側の compose ディレクトリで `docker compose logs aka-only-server > aka-only-server.log`）。aka-only-server のログは IMSI がマスクされていないため、取り扱いに注意する。

> **参考:** O-05 §10.4（テスト結果のログエビデンス保全）

## 7. 障害対応チェックリスト

障害対応時に使用するチェックリスト。対応完了後に確認する。

### 初動確認

- [ ] `docker compose ps` で全コンテナの状態を確認した
- [ ] 障害の影響範囲（全体/特定サービス/特定加入者）を特定した
- [ ] 障害レベル（Critical/Error/Warning）を判定した

### 切り分け・復旧

- [ ] §3のフローチャートに従い、障害コンポーネントを特定した
- [ ] §4の該当セクションの手順に従い対処を実施した
- [ ] 復旧後、`docker compose ps` で全サービスの正常稼働を確認した
- [ ] ヘルスチェック（§2.4）で全エンドポイントの応答を確認した

### 復旧後確認

- [ ] 認証リクエスト（Access-Request）が正常に処理されることを確認した
- [ ] 課金リクエスト（Accounting-Request）が正常に処理されることを確認した
- [ ] ログ出力が正常に行われていることを確認した
- [ ] Circuit Breakerの状態が `CB_CLOSE`（正常）であることを確認した

### 記録・報告

- [ ] 障害発生時のログエビデンスを保全した（§6.3）。接続方式01 が関係する場合は aka-only-server のログも保全した
- [ ] エスカレーションが必要な場合、障害報告を作成した（§6.4）
- [ ] 再発防止に必要な対応（設定変更等）を記録した
