# D-04 ログ仕様設計書 (r30)

## 1. ログアーキテクチャ概要

- **生成:** Go標準ライブラリ `log/slog` による構造化ログ (JSON) 出力。
- **収集:** コンテナ標準出力 (stdout) を Docker Log Driver (fluentd) がキャプチャ。
- **集約:** Fluent Bit がタグ付けしてホストOS上のファイルへ転送。ヘルスチェックログ（Vector API/Gatewayの `/health`）は `rewrite_tag` フィルタにより `healthcheck.*` タグへリタグされ、`others.log` に分離出力される（D-08 §3.2参照）。
- **解析:** ホストOS上の **`lnav`** を用いて、フィルタリング・SQL分析・監視を行う。

## 2. 共通仕様 (Common Schema)

全てのノードは以下のフィールドを含む JSON 形式で出力する（Go `log/slog` の `JSONHandler`。`app` はロガー初期化時に `With("app", ...)` で付与）。

| **フィールド名** | **型** | **説明**                             | **例**                          |
| ---------------- | ------ | ------------------------------------ | ------------------------------- |
| **`time`**       | String | タイムスタンプ (RFC3339Nano)。Admin TUIの監査ログのみ RFC3339（秒精度・UTC） | `"2026-02-23T14:23:40.210276945+09:00"` |
| **`level`**      | String | ログレベル                           | `"INFO"`, `"WARN"`, `"ERROR"`   |
| **`app`**        | String | アプリケーション名                   | `"auth-server"`, `"acct-server"`, `"vector-gateway"`, `"vector-api"`, `"admin-tui"` |
| **`msg`**        | String | 人間可読なメッセージ（Auth Server / Acct Serverの一部は日本語） | `"認証成功"`, `"vector forwarded"` |
| **`trace_id`**   | String | リクエスト追跡ID。Auth Serverの認証フローでは **EAP Context UUIDと一致**（例外は§4.1参照） | `"550e8400-e29b..."`            |
| **`event_id`**   | String | **機械可読なイベント識別子**。起動・停止・リクエスト完了等のシステムログは `event_id` を持たない（各ノードの「システムログ」節参照） | `"AUTH_SUCCESS"`, `"ACCT_START"` |
| **`src`**        | String | ソースコード位置。**現行実装では出力しない**（`slog.HandlerOptions.AddSource` 未設定） | -                 |

### 2.1 データ型の厳格化ルール

`lnav` でのSQL集計と、パケットキャプチャとの突合容易性を両立するため、以下の型ルールを厳守する。下記は現行実装が出力する属性である。

- **数値型 (Number/Int64):** 集計・統計・大小比較を行う項目。
  - `latency_ms`, `session_time`, `input_octets`, `output_octets`, `http_status`, `failure_count`, `resync_count`, `attempt`（Vector APIの `SQN_CONFLICT_RETRY`。§3.4.7）, `record_count` / `result_count`（Admin TUIの監査ログ。§3.5）
  - 実装が数値で出力しているコード値: `code`（RADIUS Code）, `acct_status_type`（Acct-Status-Type）, `subtype`（EAP-AKA Subtype）, `eap_type`（`23`=EAP-AKA / `50`=EAP-AKA'）
- **文字列型 (String):** 識別子、ビット列、Hex表記に意味があるもの。
  - `imsi`, `sqn_old` / `sqn_new` / `sqn_ms` (Hex), `src_ip`, `remote_addr`, `user_name`, `stage`, `reason`, `session_id`, `acct_session_id`, `class_uuid`, `nas_ip_address`, `nas_identifier`, `cb_name`, `method`, `path`, `backend_id`, `backend_name`, `plmn`, `cause`, `external_endpoint`, `error`
- **真偽型 (Boolean):** 有無のみを表す項目。
  - `resync`, `akaonly_enabled`, `test_mode`, `radius_secret_fallback`（Auth Server / Acct Serverの起動ログ。§3.1.8、§3.2.5）

> **`cause` について:** 接続方式01（aka-only-server）が返す ProblemDetails の `cause`（例: `USER_NOT_FOUND`, `AUTHENTICATION_REJECTED`, `INVALID_MSG_FORMAT`, `SYSTEM_FAILURE`）。内部IF（D-03）には含まれないため、Vector Gatewayのログでのみ確認できる。

## 3. ノード別詳細仕様

各表の「出力箇所」は `apps/<アプリ>/` からの相対パス。`imsi` は特記がない限り `logging.MaskIMSI`（`LOG_MASK_IMSI` に従う）でマスク済みの値である。

### 3.1 Auth Server (認証サーバー)

認証フローの中核。Trace IDの発行源となる。

> **注記:** `internal/eap/statemachine.go` の状態遷移イベント定数（`PERMANENT_IDENTITY`, `PSEUDONYM_IDENTITY`, `UNSUPPORTED_IDENTITY`, `INVALID_IDENTITY`, `VECTOR_REQUEST`, `VECTOR_SUCCESS`, `VECTOR_ERROR`, `CHALLENGE_SENT`, `CHALLENGE_OK`, `CHALLENGE_FAIL`, `SYNC_FAILURE`, `RESYNC_LIMIT`, `AUTH_REJECT`, `CLIENT_ERROR`, `RESYNC_SUCCESS`, `RESYNC_ERROR`）は状態遷移検証用であり、ログの `event_id` としては出力しない。

#### 3.1.1 システム・通信エラー

| **Level** | **event_id** | **msg** | **内容・条件** | **必須属性 (Key)** | **出力箇所** |
| --------- | ------------ | ------- | -------------- | ------------------ | ------------ |
| **ERROR** | `VALKEY_CONN_ERR` | `Valkey接続失敗` | 起動時のValkey接続失敗（プロセスは終了する） | `error` | `main.go` |
| **ERROR** | `VECTOR_API_ERR` | `vector api error` | Vector Gatewayが200以外を返した（HTTPクライアント層。非200応答ごとに1行） | `error`, `http_status` (Int), `latency_ms` (Int)（`trace_id`・`imsi` は持たない） | `internal/vector/client.go` |

| **ERROR** | `VECTOR_CONN_ERR` | `Vector接続エラー` | Vector Gatewayへの接続失敗・タイムアウト（認証フロー層） | `trace_id`, `imsi`, `error` | `internal/engine/engine.go`（`logVectorError`） |

> **注記（Vector Gateway呼び出しエラーのログ）:**
> - `VECTOR_API_ERR` は2つの層から出力されるため、`msg` で区別する。HTTPクライアント層は `"vector api error"`（`trace_id` なし）、認証フロー層は `"Vector APIエラー"`（`trace_id` あり）。
> - Vector Gatewayが404を返した場合は、HTTPクライアント層の `VECTOR_API_ERR` と認証フロー層の `VECTOR_IMSI_NOT_FOUND`（§3.1.5）の2行が出力される。404以外の非200応答では `VECTOR_API_ERR` が2行（両層から1行ずつ）出力される。
> - 接続失敗・タイムアウトはHTTPクライアント層ではログを出力せず、認証フロー層の `VECTOR_CONN_ERR` のみ出力される。
> - いずれの場合もAuth ServerはAccess-Reject（EAP-Failure付き）を返す。
> - Valkeyの実行時エラー専用のevent_idはない。実行時のValkey障害は、処理箇所に応じて `RADIUS_SECRET_ERR`（§3.1.3）、`EAP_CTX_NOT_FOUND` / `AUTH_POLICY_NOT_FOUND`（§3.1.5）、`EAP_CTX_CREATE_ERR` / `EAP_CTX_UPDATE_ERR` / `SESSION_CREATE_ERR` / `SESSION_INDEX_ERR`（§3.1.7）として `error` 属性付きで出力される。Valkey接続の復旧検知ログは出力しない（§4.3参照）。

### 3.3 Vector Gateway (ルーティングノード)

Auth Serverから受信したリクエストを適切なバックエンドにルーティングする。Trace IDの中継点となる。

#### 3.3.1 ルーティング・リクエスト処理イベント

ハンドラー（`internal/handler/vector.go`）が出力するevent_idは `GW_ROUTE` / `GW_OK` / `GW_ERR` の3種類である。`GW_ERR` は複数の状況で共通のため、`msg` で区別する。

| **Level** | **event_id** | **msg** | **内容・条件** | **必須属性 (Key)** |
| --------- | ------------ | ------- | -------------- | ------------------ |
| **INFO**  | `GW_ROUTE` | `backend selected` | バックエンド選択（PLMN一致・未一致・passthroughを問わず毎リクエスト1行） | `trace_id`, `imsi`（マスク済み）, `backend_id`, `backend_name` |
| **INFO**  | `GW_OK` | `vector forwarded` | ベクター取得成功（200返却） | `trace_id`, `imsi`（マスク済み）, `backend_id`, `http_status` (Int, `200`) |
| **WARN**  | `GW_ERR` | `invalid request body` | リクエストJSON不正（400返却） | `trace_id`, `error` |
| **WARN**  | `GW_ERR` | `invalid IMSI format` | IMSI形式不正（15桁の数字でない。400返却） | `trace_id`, `imsi`（マスク済み）, `error` |
| **WARN**  | `GW_ERR` | `backend not implemented` | 未実装・未設定の接続方式IDが選択された（501返却） | `trace_id`, `imsi`（マスク済み）, `backend_id` |
| **ERROR** | `GW_ERR` | `routing error` | ルーティングの想定外エラー（500返却） | `trace_id`, `imsi`（マスク済み）, `error` |
| **WARN**  | `GW_ERR` | `backend returned error` | バックエンドが4xxを返した（ステータスとProblemDetailをそのまま返却） | `trace_id`, `imsi`（マスク済み）, `http_status` (Int) |
| **ERROR** | `GW_ERR` | `backend communication error` | バックエンドとの通信エラー・5xx応答・応答パース失敗等（502返却） | `trace_id`, `imsi`（マスク済み）, `error` |
| **ERROR** | `GW_ERR` | `unexpected backend error` | 上記以外のバックエンドエラー（500返却） | `trace_id`, `imsi`（マスク済み）, `error` |

> **注記:**
> - PLMN一致／未一致を区別するログ（DEBUGを含む）は出力しない。選択結果は `GW_ROUTE` の `backend_id` で判断する。
> - 内部Vector API（接続方式00）の呼び出し専用ログはない。00の失敗は `GW_ERR`（`backend returned error` / `backend communication error`）で判断する。
> - `GW_OK` は `latency_ms` を持たない。リクエスト全体の処理時間は §3.3.3 の `request completed` の `latency_ms` で確認する。
> - `X-Trace-ID` ヘッダがないリクエストでは `trace_id` は `"no-trace-id"` となる。

バックエンド呼び出し専用のログは接続方式01（aka-only-server）のみ出力する。内部Vector API（接続方式00）の呼び出し専用ログはない（§3.3.1の注記参照）。

> - aka-only-server 呼び出し1回につき、`BACKEND_EXTERNAL_CALL` または `BACKEND_EXTERNAL_ERR` のどちらか1行を出力する。`msg` はそれぞれ `"aka-only-server call succeeded"` / `"aka-only-server rejected request"`（WARN） / `"aka-only-server call failed"`（ERROR）。

> - エラー変換の詳細はD-06を参照。

#### 3.3.4 ログ解析時の区別方法

`GW_ERR` は状況ごとに `msg` が異なるため、lnavでは `event_id` と `log_body`（`msg` に対応）を組み合わせて絞り込む。

```sql
;SELECT log_time, trace_id, imsi, log_body
 FROM aka_radius_log
 WHERE event_id = 'GW_ERR' AND log_body = 'backend communication error'
 ORDER BY log_time DESC
 LIMIT 10
```

> **タイムアウトのWARNについて:** gateway のバックエンド向けタイムアウト（既定 `3s`）が auth-server のタイムアウト（5秒）以上だと、バックエンド（vector-api / aka-only-server）障害時に gateway が 502 を返す前に auth-server がタイムアウトし、auth-server のログが `VECTOR_API_ERR`（`http_status`=502）ではなく `VECTOR_CONN_ERR` になることがある（D-12 §5.3）。

### 3.4 Vector API (計算ノード)

Auth Server（またはVector Gateway）から伝搬されたTrace IDを記録する。ハンドラー（`internal/handler/vector.go`）のログに加え、ユースケース層（`internal/usecase/vector.go`）が出力するログ `SQN_RESYNC`（§3.4.3）と `SQN_CONFLICT_RETRY`（§3.4.7）も `trace_id` を持つ（ハンドラーが `usecase.ContextWithTraceID` でTrace IDを context に載せ、ユースケースが取り出す）。この2つ以外のログは、ハンドラーとミドルウェア（`request completed`）から出力される。

ハンドラーはユースケースが返した定義済みエラー（`internal/usecase/error.go` の `ProblemError`）を、エラーごとの `msg` と `event_id` で1行出力する（`slog.Log`。属性は `trace_id`, `imsi`, `http_status`, `error`）。ログレベルはHTTPステータスで決まる（5xx=ERROR、404=INFO、その他=WARN）。`error` 属性は原因を含むエラー文で、原因（Valkeyのエラー、SQN値等）がある場合は `<定義済みエラーの detail>: <原因>` の形になる（例: `Database connection error: <Valkeyのエラー>`、`SQN difference exceeds allowed range: sqn_ms=xxxxxxxxxxxx sqn_he=xxxxxxxxxxxx: <原因>`）。原因がない場合は定義済みエラーの detail と同じ文になる（例: `IMSI does not exist in subscriber DB`）。HTTP応答の `detail` は従来どおり定義済みエラーの detail のみで、原因は含めない。

> **注記（`SQN_RESYNC` の msg）:**
> - `SQN resync successful`: 通常の再同期。`sqn_new` = `sqn_ms` + 32（0x20）。
> - `SQN resync already applied by another request`: SQN競合（§3.4.7）でやり直した2回目以降の試行で、読み直したSQN_HE（`sqn_old`）がSQN_MS以上だった場合。別のリクエスト（同じ再同期の再送など）が先に同期済みとみなし、デルタ検証をせずに `sqn_new` = `sqn_old` + 32 とする。1回目の試行でSQN_MSがSQN_HE以下の場合は従来どおり `SQN_RESYNC_DELTA_ERR`（400）となる。
> - r27 までは再同期の検証直後（SQNの書き戻し前）に出力していた。現行は書き換えに成功した後に出力するため、書き換えに失敗した（Valkeyエラー・競合上限超過）リクエストでは出力されない。

> **注記:** SQN差分超過時のログは `SQN_RESYNC_DELTA_ERR` の1行のみ（r23 まではユースケース層の `SQN delta validation failed`（`sqn_ms` / `sqn_he` 属性）とハンドラー層の2行だった）。SQN_MS・SQN_HEの値は `error` 属性の文中（`sqn_ms=` / `sqn_he=`、12桁Hex）で確認する。

#### 3.4.7 SQN競合制御

Vector API は `sub:{IMSI}` の `sqn` を Lua スクリプトで比較・置き換え（CAS）し、読んだ値から変わっていた（他のリクエストが先に書き換えた）場合は、1〜10ms のランダムな時間待ってから加入者の読み出しからやり直す（最大3回試行。D-02 §2.A、D-11 §7.5・§13.6）。

| **Level** | **event_id** | **msg** | **内容・条件** | **必須属性 (Key)** | **出力箇所** |
| --------- | ------------ | ------- | -------------- | ------------------ | ------------ |
| **WARN**  | `SQN_CONFLICT_RETRY` | `SQN update conflict, retrying` | SQNの書き換えが競合し、やり直す（ユースケース層。競合するたびに出力し、1リクエストにつき最大2回。3回目の試行で競合した場合は出力せず `SQN_CONFLICT_ERR` となる） | `trace_id`, `imsi`, `attempt` (Int。競合した試行の回数: `1` または `2`) | `internal/usecase/vector.go` |
| **WARN**  | `SQN_CONFLICT_ERR` | `SQN update conflict exceeded retry limit` | 3回とも競合した、またはやり直し前の待機中にリクエストの期限切れ・キャンセルとなった（409返却。ベクターは返さない） | `trace_id`, `imsi`, `http_status` (Int, `409`), `error`（3回とも競合: `SQN update conflict: conflicted 3 times`、待機中の期限切れ等: `SQN update conflict: retry aborted after N attempts: <contextのエラー>`） | `internal/handler/vector.go`（定義: `internal/usecase/error.go`） |

> **注記:**
> - 比較するのは `sqn` フィールドだけである。Admin TUI が `ki` / `opc` / `amf` だけを変更しても競合とはならない。Admin TUI の加入者編集は、SQN を変更していなければ `sqn` を書き換えない（`ki` / `opc` / `amf` だけを更新する）。SQN を変更した場合は、編集開始時に読んだ値と一致するときだけ `sqn` を書き換え、その保存が Vector API の読み出しから書き換えまでの間に行われた場合は競合として検出される。逆に、編集中に認証で `sqn` が進んでいた場合は Admin TUI 側が保存をやめてエラーを表示する（Admin TUI はこの失敗をログに出力しない。§3.5）。r28 までは、Admin TUI の加入者編集が SQN を変更していなくても `sqn` をフォームの値で上書きしていた（D-02 §2.A）。
> - やり直しで加入者が削除されていた場合は `CALC_ERR`（INFO、`subscriber not found`、404）、Valkeyエラーの場合は `VALKEY_CONN_ERR`（ERROR、500）となる（その前に `SQN_CONFLICT_RETRY` が出力されている）。
> - 409 は Auth Server の Circuit Breaker の失敗回数に数えない（D-06 §3.1.1）。Auth Server は `VECTOR_API_ERR`（`http_status`=409）を出力して Access-Reject を返す。
> - r10〜r18 では設計（WATCH/MULTI による CAS）に基づいて旧 §3.4.5 に記載し、r19〜r27 では未実装のため本表から除外していた。event_id・Level・HTTPステータスは設計と同じだが、`SQN_CONFLICT_ERR` の属性は設計の `retry_count` ではなく、他の定義済みエラーと同じ `http_status` / `error` である。

## 4. 実装要件 (Go Implementation)

### 4.1 Trace ID の統合と伝搬 (Unified Tracing)

ログの `trace_id`、Valkey上のEAP Context Key、RADIUS State属性を一致させる。

1. **Auth Server:**
   - ハンドラー（`internal/server/handler.go` の `resolveTraceID`）がRADIUSパケットごとにTrace IDを決める。
     - Access-RequestにUUID形式のState属性がある場合（2回目以降のAccess-Request。Access-Challengeへの応答）は、State属性の値（=EAP Context UUID）を正規化せずにそのままTrace IDとして使う。
     - State属性がない場合（初回 `Access-Request` (Identity)）、State属性がUUID形式でない場合、およびAccess-Request以外（Status-Server等）は、`uuid.New()` で新しいUUIDを生成する。State属性のない初回 `Access-Request` で生成したUUIDがEAP Context UUIDとなる。
   - **Log:** ロガーに `trace_id` を束縛せず（`slog.With` は使わない）、各ログ呼び出しで `"trace_id", traceID` を明示的に渡す。
   - **DB:** `eap:{UUID}` キーとしてValkeyへ保存し、RADIUS State属性にも同じUUIDを設定する。
   - **2回目以降のAccess-Request:** ハンドラー層のログ（`PKT_RECV`, `PKT_MA_INVALID`, `PKT_NO_EAP`, `PKT_SEND_ERR`, `PKT_DROP`）と、State属性の値を `trace_id` として出力するEAPエンジン（`internal/engine/engine.go`）のログ（`EAP_*`, `AUTH_*`, `VECTOR_*` 等）は、同じ `trace_id`（EAP Context UUID）になる。このため、1回の認証フローのAuth Serverのログ（各パケットの `PKT_RECV` を含む）を1つの `trace_id` で追跡できる。
   - **例外:** State属性がUUID形式でない場合は、ハンドラー層のログは新しく生成したUUID、エンジンのログ（`EAP_CTX_NOT_FOUND`）はState属性の値を `trace_id` とするため、両者は一致しない（このようなStateに対応するEAPコンテキストは存在しないため、Rejectとなる）。
   - **API Call:** Vector Gateway コール時（初回のベクター取得・再同期時のベクター取得とも）、HTTPヘッダ `X-Trace-ID` にEAP Context UUIDをセット。
2. **Vector Gateway:**
   - Middlewareで `X-Trace-ID` ヘッダを読み取る（ない場合は `"no-trace-id"`）。
   - 読み取ったIDを gin のコンテキストに保持し、ハンドラー・バックエンドのログに `trace_id` として出力する。
   - 内部Vector APIコール時、同一の `X-Trace-ID` をヘッダに付与して伝搬する。
   - 接続方式01（aka-only-server）コール時も `X-Trace-ID` をベストエフォートで付与するが、aka-only-server はこれを記録せず、IMSIもマスクしない。aka-only-server 側のログとの突き合わせは、Vector Gatewayの `BACKEND_EXTERNAL_CALL` / `BACKEND_EXTERNAL_ERR`（`trace_id`、時刻）と aka-only-server のログ（`client_id`、`imsi`、時刻）を時刻で照合して行う。
3. **Vector API:**
   - Middlewareで `X-Trace-ID` ヘッダを読み取る（ない場合は `"no-trace-id"`）。
   - 読み取ったIDを gin のコンテキストに保持し、ハンドラー・ミドルウェアのログに `trace_id` として出力する。ハンドラーは `usecase.ContextWithTraceID` でTrace IDを context に載せてユースケースを呼び出し、ユースケース層のログ（`SQN_RESYNC`）も同じ `trace_id` を出力する。このため、1リクエストのVector APIのログはすべて同じ `trace_id` で追跡できる。
4. **Acct Server:**
   - パケット受信ごとにUUIDを生成して `trace_id` とする。Auth ServerのTrace IDとは関連しない（認証セッションとの対応はClass属性のセッションUUID（`class_uuid`）で行う）。

### 4.2 Circuit Breaker ログ実装

`sony/gobreaker` のフック機能を利用し、状態変化を確実に記録する。

```go
// Auth Server実装（apps/auth-server/internal/vector/client.go）
OnStateChange: func(name string, from, to gobreaker.State) {
    switch to {
    case gobreaker.StateOpen:
        slog.Warn("circuit breaker opened",
            "event_id", "CB_OPEN",
            "cb_name", name,
            "failure_count", 0, // countsは取得不可
        )
    case gobreaker.StateHalfOpen:
        slog.Info("circuit breaker half-open",
            "event_id", "CB_HALF_OPEN",
            "cb_name", name,
        )
    case gobreaker.StateClosed:
        slog.Info("circuit breaker closed",
            "event_id", "CB_CLOSE",
            "cb_name", name,
        )
    }
}
```

### 4.3 Valkey接続エラーの記録

Valkey接続の復旧検知（復旧時の停止時間 `downtime_ms` の記録）は実装していない。Valkey障害は、発生した処理ごとに次のログで記録される。

| ノード | 起動時の接続失敗 | 実行時のValkeyエラー |
|--------|------------------|----------------------|
| Auth Server | `VALKEY_CONN_ERR`（ERROR。プロセス終了） | 専用のevent_idなし。`RADIUS_SECRET_ERR`, `EAP_CTX_NOT_FOUND`, `AUTH_POLICY_NOT_FOUND`, `EAP_CTX_CREATE_ERR`, `EAP_CTX_UPDATE_ERR`, `SESSION_CREATE_ERR`, `SESSION_INDEX_ERR` の `error` 属性で確認する（§3.1） |
| Acct Server | `VALKEY_CONN_ERR`（ERROR。プロセス終了） | `VALKEY_CONN_ERR`（読み取り系）、`DB_WRITE_ERR`（書き込み系）、`RADIUS_SECRET_ERR`（§3.2） |
| Vector API | `failed to connect to Valkey`（event_idなし。プロセス終了） | `VALKEY_CONN_ERR`（500返却。`error` 属性にValkeyのエラーを含む。テストベクターモードも同じ。§3.4） |

いずれのノードもValkeyクライアント（go-redis）のコネクションプールが次のコマンド実行時に接続を張り直すため、復旧はこれらのエラーログの出力が止まったことで判断する。

### 4.4 IMSIマスキング設定

セキュリティ上、ログに出力するIMSIは中央部分をマスクする。

#### 4.4.1 環境変数による制御

| 環境変数 | デフォルト | 対象コンポーネント | 説明 |
|---------|-----------|------------------|------|
| `LOG_MASK_IMSI` | `true` | Auth Server, Acct Server, Vector Gateway, Vector API | `false` でマスキング無効化（デバッグ用） |

**Admin TUIはIMSIマスキング対象外:**
- Admin TUIは `LOG_MASK_IMSI` 環境変数の設定にかかわらず、IMSIをマスキングしない
- 画面表示・監査ログともIMSIを常に生値で表示/記録する
- 理由: 管理操作や監査証跡でIMSIを確実に識別できる運用を優先

**設定の一元管理:**
- 4コンポーネントで同一の環境変数名を使用
- Docker Composeの `.env` ファイルで一括設定可能
- 詳細は D-08「インフラ設定・運用設計書」を参照

**用途:**
- **本番環境**: `LOG_MASK_IMSI=true`（デフォルト）でプライバシー保護
- **開発・デバッグ環境**: `LOG_MASK_IMSI=false` で問題調査時にIMSI全桁を確認可能

#### 4.4.2 マスキング仕様

| 設定値 | 動作 | 出力例（入力: `440101234567890`） |
|--------|------|--------------------------------|
| `true`（デフォルト） | 先頭6桁 + マスク + 末尾1桁 | `440101********0` |
| `false` | マスクなし（全桁表示） | `440101234567890` |

**User-Name（EAP Identity）のマスク規則（`logging.MaskUserName`）:**

`user_name` 属性や、Acct Serverの課金ログでUser-NameからIMSIを抽出できない場合の `imsi` 代替値など、EAP Identity形式の値（IMSIを含みうる）は `logging.MaskUserName` でマスクする。`"@"` より前（ローカル部）だけを対象とし、realm（`"@"` 以降）はそのまま残す。

| ローカル部の形式 | 動作（`LOG_MASK_IMSI=true`） | 出力例 |
|------------------|------------------------------|--------|
| 種別1文字＋IMSI 15桁（16桁の数字。例: EAP-AKA `0`、EAP-AKA' `6`、EAP-SIM `1`） | 種別文字を残し、IMSI部分に `MaskIMSI` を適用 | `0440101234567890@realm` → `0440101********0@realm` |
| IMSI 15桁のみ | `MaskIMSI` を適用 | `440101234567890` → `440101********0` |
| 上記以外（仮名・再認証ID・不正形式） | 先頭7文字と末尾1文字を残してマスク（7+1文字以下はそのまま） | `2some-pseudonym@example` → `2some-p*******m@example` |

`LOG_MASK_IMSI=false` の場合はマスクせずそのまま出力する。

#### 4.4.3 実装例

```go
// 全コンポーネント共通実装イメージ
type Config struct {
    LogMaskIMSI bool `envconfig:"LOG_MASK_IMSI" default:"true"`
}

// pkg/logging（共有パッケージ）
func MaskIMSI(imsi string, enabled bool) string {
    if !enabled {
        return imsi
    }
    return MaskPartial(imsi, 6, 1, '*') // 先頭6桁 + マスク + 末尾1桁
}

// User-Name（EAP Identity）用。"@"より前だけをマスクし、realmは残す（§4.4.2）
func MaskUserName(userName string, enabled bool) string

// 使用例（Vector Gateway: apps/vector-gateway/internal/handler/vector.go）
slog.Info("backend selected",
    "trace_id", traceID,
    "event_id", "GW_ROUTE",
    "imsi", logging.MaskIMSI(req.IMSI, h.cfg.LogMaskIMSI),
    "backend_id", b.ID(),
    "backend_name", b.Name(),
)
```

#### 4.4.4 注意事項

**セキュリティ:**
- `LOG_MASK_IMSI=false` の設定は、ログファイルへのアクセス制御が適切に行われている環境でのみ使用すること
- デバッグ目的でマスキングを無効化した場合、調査完了後は速やかに `true` に戻すこと

**Auth Serverの適用範囲:**
- Auth Serverでは、IMSIは認証フロー全体（Identity受信、Vector Gateway呼び出し、ポリシー評価、セッション作成）で使用される
- 詳細な適用箇所は D-09「Auth Server詳細設計書」セクション3.5を参照

**Acct Serverの適用範囲:**

- Acct Serverでは、IMSIは課金ログ（ACCT_START, ACCT_INTERIM, ACCT_STOP）で使用される
- 詳細な適用箇所は D-10「Acct Server詳細設計書」を参照

**lnav運用への影響:**

- IMSIマスキング有効時（デフォルト）、lnavでの特定IMSI絞り込み検索が不可能になる
  - 例: `;SELECT * FROM aka_radius_log WHERE imsi = '440101234567890'` は機能しない
  - マスク後の値（`440101********0`）での検索は可能だが、同一プレフィックスの加入者を区別できない
- **代替手段:**
  - `trace_id` による認証フロー追跡を推奨
  - 特定IMSIの調査が必要な場合は、開発/ステージング環境で `LOG_MASK_IMSI=false` に設定して再現
- 詳細は O-05「ログ解析ガイド」（実装完了後に作成予定）を参照

**Admin TUIの除外:**
- Admin TUIはIMSIマスキングの対象外であり、`LOG_MASK_IMSI` 環境変数は参照しない
- 管理画面では常にIMSI全桁を表示し、監査ログ（`AUDIT_LOG`）にもIMSI生値を出力する
- これにより、管理者が加入者を一意に識別でき、監査証跡として機能する

### 4.5 セキュリティ要件 (Security)

以下の機密情報は、**いかなるログレベルであっても絶対に出力してはならない**。

- Ki (秘密鍵)
- OPc
- Radius Shared Secret
- Session Keys (CK, IK, MS-MPPE-*-Key)
- 完全なIMSI（`LOG_MASK_IMSI=true` 時は全コンポーネントでマスク）

> **注記（IMSIを含みうる `imsi` 以外の値）:** EAP Identity（User-Name）はEAP-SIMの永続ID等でIMSIを含むため、次の出力は `logging.MaskUserName`（§4.4.2）でマスクする。
> - Auth Server: `EAP_UNSUPPORTED_TYPE` / `EAP_IDENTITY_INVALID` の `user_name`（§3.1）
> - Acct Server: 課金ログ（`ACCT_START` / `ACCT_INTERIM` / `ACCT_STOP`）でUser-NameからIMSIを抽出できない場合に `imsi` に出力するUser-Name（§3.2.4）
>
> Admin TUIはマスキング対象外（§4.4.1）であり、idx:userクリーンアップ失敗時の `log.Printf` 出力（§3.5.1）もIMSI生値を含む。

### 4.6 ログレベル設定（LOG_LEVEL）

| 環境変数 | デフォルト | 対象コンポーネント | 説明 |
|---------|-----------|------------------|------|
| `LOG_LEVEL` | `INFO` | Auth Server, Acct Server, Vector Gateway, Vector API | 出力する最低ログレベル（`DEBUG` / `INFO` / `WARN` / `ERROR`）。大文字小文字を区別しない。未知の値・空文字は `INFO` |

- Docker Composeでは `.env` の `LOG_LEVEL` を上記4コンポーネントに渡す（`LOG_LEVEL: ${LOG_LEVEL:-INFO}`。D-08 §4.1）。
- 4コンポーネントとも共通ライブラリの `pkg/logging.ParseLevel`（E-03）で変換する（前後の空白を除去し、`WARNING` も `WARN` として扱う）。Auth Server / Acct Serverは `main.go` のロガー初期化で、Vector Gateway / Vector APIは各 `main.go` の `initLogger` から呼び出す。
- 起動ログ（Auth Serverの `auth-server起動開始`、Acct Serverの `acct-server起動開始`、Vector Gateway / Vector APIの起動ログ）の `log_level` 属性に設定値が出力される。
- Admin TUIの監査ログは対象外。
- 現行実装で `DEBUG` にしたときだけ出力されるログは、Auth Serverの `vector api success`（§3.1.8 注記）のみである（Acct Server / Vector Gateway / Vector APIには DEBUG ログがない）。運用時は `INFO`（既定）とする。
