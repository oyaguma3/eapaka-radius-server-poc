### 2.2 環境変数

テスト実行に必要な主要環境変数（`deployments/.env` で設定）:

| 変数 | テスト時の値 | 説明 |
|:----|:-----------|:----|
| `TEST_VECTOR_ENABLED` | `true` | テストベクターモード有効化 |
| `TEST_VECTOR_IMSI_PREFIX` | `00101` | テストベクター対象IMSIプレフィックス |
| `LOG_MASK_IMSI` | `false` | IMSI全桁表示（テスト時） |
| `RADIUS_SECRET` | `testing123` | RADIUS共有秘密（フォールバック用） |

> **注意（r8追記）: `TEST_VECTOR_ENABLED` / `TEST_VECTOR_IMSI_PREFIX` の受け渡し**
> `deployments/docker-compose.yml` は vector-api の `environment` で `TEST_VECTOR_ENABLED: ${TEST_VECTOR_ENABLED:-false}` と `TEST_VECTOR_IMSI_PREFIX: ${TEST_VECTOR_IMSI_PREFIX:-00101}` を渡すため、`.env` に `TEST_VECTOR_ENABLED=true` を設定すればテストベクターモードが有効になる（`.env` 変更後は `docker compose up -d` で vector-api を作り直す）。反映は `docker compose exec vector-api env | grep TEST_VECTOR` で確認する。以前の compose はこの2変数を渡しておらず `.env` の設定が効かなかったため、2026-10-04 の G10 実施時は検証用のオーバーライドファイルで渡したが、その後 compose を修正したので現在はオーバーライドは不要である。

> **テストベクターモードの動作（r8追記、r9改訂。実装: `apps/vector-api/internal/usecase/vector.go`, `internal/testmode/testvector.go`）**
> - IMSI が `TEST_VECTOR_IMSI_PREFIX`（既定 `00101`）で始まると、Vector API は Ki / OPc / AMF を固定値（3GPP TS 35.208 Test Set 1、**AMF `B9B9`**）にして Milenage 計算する。`sub:{IMSI}` の `ki` / `opc` / `amf` は使わない（IMSI 003 の `amf` = `8000` もテストベクターモードでは効かない）。RAND は毎回乱数。
> - それ以外は通常モードと同じである。`sub:{IMSI}` を取得し、`sqn` を +32 して書き戻す（再同期（AUTS）時は SQN_MS+32）。**テストベクター対象の IMSI でも `sub:{IMSI}` の登録が必要**で、未登録なら 404（Vector API の `CALC_ERR` "subscriber not found" → Auth Server の `VECTOR_IMSI_NOT_FOUND`）で Reject になる。Valkey エラーや SQN の書き戻し失敗は 500、`sqn` が解析できない場合も 500 になる。テスト用加入者はセクション3 の事前準備（[test_subscriber_data_scripts.md](subdocs/test_subscriber_data_scripts.md)）で登録する。
> - r8 時点の実装では、テストベクター対象の IMSI は未登録でも既定 SQN `FF9BB4D0B607` から計算され（`TEST_SQN_FALLBACK` ログ）、`sub:{IMSI}` に `sqn` だけが書き込まれていた。この動作は廃止した（2026-10-04 の実装修正）。旧実装で作られた `sqn` だけの `sub:{IMSI}`（例 `sub:001019999999999`）が残っていると登録済みとして扱われるため、DEL で削除しておく。
> - テストベクター対象外の IMSI（例 `001029999999999`、`440100123456789`）は `sub:{IMSI}` の Ki/OPc/AMF で計算し、未登録なら同じく 404 になる。
> - r7 以前の結合テスト（〜2026-02）は、compose が `TEST_VECTOR_ENABLED` を vector-api に渡していなかったため、実際には実計算モード（`sub:{IMSI}` の Ki/OPc/AMF を使用）で実行されていたと考えられる。IMSI 003 用に AMF `8000` の config を使っていたのはこのためである。

> **Secret体系**: Valkeyにクライアント登録されたIPからのリクエストは登録Secret（`TESTSECRET123`等）を使用する。未登録IPの場合のみ `RADIUS_SECRET` 環境変数にフォールバックする。ホスト上の radclient / eapaka_test から `127.0.0.1:1812` / `1813`（compose の公開ポート）に送ると、コンテナから見た送信元IPは compose ネットワーク（`deployments_default`）のゲートウェイIPになるため、そのIPを `client:{IP}`（Secret: `TESTSECRET123`）として登録し、radclient/eapaka_testでは `TESTSECRET123` を使用する。ゲートウェイIPは環境によって異なる（例: 本書作成時の環境では `172.19.0.1`、2026-10-04 の検証環境では `172.18.0.1`）ので、次のコマンドで確認して登録する（r8追記）。
>
> ```bash
> cd deployments
> set -a; . ./.env; set +a   # VALKEY_PASSWORD をシェル変数に読み込む
> GW_IP=$(docker network inspect deployments_default -f '{{(index .IPAM.Config 0).Gateway}}')
> echo "$GW_IP"
> docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET "client:$GW_IP" \
>   secret "TESTSECRET123" name "DockerGateway" vendor "generic"
> ```
>
> 実際の送信元IPは Auth Server の `PKT_RECV` ログ（`src_ip`）でも確認できる。

#### eapaka_test設定ファイル

| 設定ファイル | 対象IMSI | AMF | 用途 |
|:------------|:--------|:----|:-----|
| `config_testvector.yaml` | `001010000000000`（デフォルト） | `B9B9` | テストベクターモード（`TEST_VECTOR_ENABLED=true`）の全シナリオ（IMSI 003 を使う INT-AUTH-AKA-007、INT-POLICY-003〜005 を含む） |

### 5.3 G3: SQN再同期

**目的**: SQN不整合時の再同期フロー（AUTS → SQN更新 → 再Challenge → Accept）を検証する。

| ID | シナリオ名 | ツール | テストケース | PASS条件 |
|:---|:---------|:------|:-----------|:--------|
| INT-003-01 | EAP-AKA SQN再同期 | eapaka_test | `resync_aka_testvector.yaml` | Access-Accept |
| INT-003-02 | EAP-AKA' SQN再同期 | eapaka_test | `resync_aka_prime_testvector.yaml` | Access-Accept |
| INT-006-03 | X-Trace-ID (再同期時) | ログ検証 | INT-003-01 実行後のログ確認 | 再同期時もtrace_id伝搬（同一trace_idの `request completed` が2件、Vector APIの `SQN_RESYNC` も同一trace_id、Auth Serverの `PKT_RECV` も全パケット同一） |

**前提（r2更新）**: Valkey-backed SQN対応により、テストベクターモードでもSQN再同期テストが実行可能。サーバー側SQNをクライアント側より低い値に設定することで、AUTSベースの再同期フローを発生させる。

> **注意（r4追記）: `sqn.reset: true` と Resync 発動条件**
> テストケースの `sqn.reset: true` はクライアント側SQNをリセット（初期値に戻す）するが、これによりクライアントSQN < サーバーSQNとなり、USIM は AUTN 内の SQN を「fresh」と判定する（3GPP TS 33.102）。そのため **Resync は発動せず**、通常の認証フローで成功する。Resync を明示的に発動させるには、サーバー側SQNをクライアント側より小さい値に設定する必要がある（例: サーバーSQN=`000000000001` に対しクライアントが蓄積済みSQN > サーバーSQN）。`sqn.reset: true` を使用したテストケースでは、「SQN不整合を許容した正常認証」が検証されるが、AUTS再同期フロー自体の検証にはならない点に留意すること。

> **注意（r8追記）: eapaka_test の SQN は IND ごとに管理される**
> eapaka_test はクライアント側 SQN を IND（SQN の下位5ビット）ごとの配列で管理し、受信した AUTN の SQN と**同じ IND スロット**の値を比較して fresh 判定する。Vector API（+32 固定）は IND を変えずに SQN を進めるため、サーバー側 SQN の IND と `sqn_initial_hex` の IND が異なると、再同期は起きずに Accept になる（例: `sqn_initial_hex` = `FF9BB4D0B607` は IND=7、サーバー SQN `000000000001` は IND=1）。この場合テストは PASS するが AUTS 再同期は検証できていない。本グループの手順は変更しないが、再同期が実際に走ったかは Step 4/5 の `EAP_RESYNC_CHALLENGE` / `SQN_RESYNC` ログの有無で必ず判定すること。なお 2026-10-04 にテストベクターモード（`TEST_VECTOR_ENABLED=true`）で `config_testvector.yaml` を使って実施した際は、INT-003-01/02 とも再同期が発生した（`SQN_RESYNC` / `EAP_RESYNC_CHALLENGE` を確認）。aka-only-server（IND=0 固定）を相手にする G10 の再同期とは事情が異なるので混同しないこと。再同期を確実に起こす設定例は G10（INT-GW-AKAONLY-003）および S-01 セクション6.5 を参照。

#### 実行手順

```bash
# Step 1: サーバー側SQNを低い値にリセット（再同期フロー発生条件の作成）
docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000000 sqn "000000000001"

# Step 2: EAP-AKA SQN再同期（sqn.reset=true でクライアントSQN=0、サーバーSQN=1で不整合発生）
$EAPAKA_TEST/eapaka_test -c $CONFIG run $CASES/resync_aka_testvector.yaml

# Step 3: EAP-AKA' SQN再同期
docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000000 sqn "000000000001"
$EAPAKA_TEST/eapaka_test -c $CONFIG run $CASES/resync_aka_prime_testvector.yaml

# Step 4: Auth Serverログで再同期イベント確認
docker compose logs auth-server --since=5m | grep -E "EAP_RESYNC_CHALLENGE|trace_id"

# Step 5: Vector APIログでSQN更新確認（SQN_RESYNC は trace_id・マスク済み imsi を持ち、EAP_RESYNC_CHALLENGE と同じ trace_id）
docker compose logs vector-api --since=5m | grep -E "SQN_RESYNC|sqn_old|sqn_new"

# Step 6: Valkey SQN更新確認
docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HGET sub:001010000000000 sqn
```

**詳細手順・ログ検証ポイント**: [T-03_INT-003_SQN_resync_flow_scenario.md](subdocs/T-03_INT-003_SQN_resync_flow_scenario.md) を参照。

### 5.4 G4: 認証異常系

**目的**: 認証失敗が発生するケースでの Access-Reject 応答とログ出力を検証する。

| ID | シナリオ名 | ツール | テストケース | PASS条件 |

#### 実行手順

```bash

$EAPAKA_TEST/eapaka_test -c $CONFIG run $CASES/mismatch_strict_fail.yaml

# INT-AUTH-AKA-005: Ki/OPc不正（XRES不一致）
# 注意: テストベクターモードでは固定 Ki/OPc（Test Set 1）で計算するため、
# このシナリオはテストベクター非対象のIMSI（Valkey登録済み、Ki不一致）が必要。
# T-01の INT-004（XRES不一致）は、テストベクターモードでは再現困難なため、
# ユニットテスト（engine_test.go TestEngine_RESMismatch_Reject）で補完済み。

# INT-AUTH-AKA-006: 未登録IMSI（テストベクター対象外の IMSI 001029999999999）
$EAPAKA_TEST/eapaka_test -c $CONFIG run $CASES/reject_imsi_not_found.yaml

# ログ確認
docker compose logs auth-server --since=5m | grep -E "AUTH_RES_MISMATCH|AUTH_POLICY_DENIED|VECTOR_IMSI_NOT_FOUND"
docker compose logs vector-api --since=5m | grep -E "CALC_ERR|subscriber not found"
```

> **注意 (INT-AUTH-AKA-004, r8追記)**: `mismatch_strict_fail.yaml` は eapaka_test 側を `method_mismatch_policy: "strict"` にし、サーバーが identity と異なる EAP 方式を選んだら Reject を期待するケースである。しかし Auth Server は identity の先頭文字（`0` = EAP-AKA、`6` = EAP-AKA'）で方式を選ぶため、現実装ではこの経路で方式ミスマッチは起きない。実際には identity の IMSI `440100123456789`（テストベクター対象外、Valkey 未登録）が Vector API で 404 になり、`VECTOR_IMSI_NOT_FOUND` で Reject される（2026-10-04 に確認）。ケースは `reject_hint_check_presence: false` のため Reject 理由の文言（`method mismatch`）を検証せず、結果は PASS になるが、**方式ミスマッチ拒否は現実装では検証できていない**。PASS 条件は Access-Reject とし、ログは `VECTOR_IMSI_NOT_FOUND` を確認する。

> **注意 (INT-AUTH-AKA-005)**: テストベクターモードではVector APIが3GPP TS 35.208 Test Set 1 の固定 Ki/OPc でベクターを計算するため、eapaka_testが同一パラメータで計算するとXRESは常に一致する。XRES不一致の結合テストは、テストベクターモード無効のSIM環境または`engine_test.go`のユニットテストで代替する。

> **注意 (INT-AUTH-AKA-006, r8改訂、r9改訂)**: 未登録IMSIには、テストベクター対象外の IMSI `001029999999999`（identity `0001029999999999@wlan.mnc002.mcc001.3gppnetwork.org`）を使う。PLMN `00102` は PLMN マップに未登録のため BackendID `00`（内部 Vector API）に回り、Vector API が 404（`CALC_ERR` "subscriber not found"）を返して Auth Server が `VECTOR_IMSI_NOT_FOUND` で Reject する。現行実装ではテストベクター対象の IMSI（`00101` 始まり）も未登録なら同じく 404 → `VECTOR_IMSI_NOT_FOUND` になるが、本ケースは引き続きテストベクター対象外の IMSI で実行する。r8 時点の実装では、以前使っていた IMSI `001019999999999`（テストベクター対象）は Valkey 未登録でもベクターが生成され（`TEST_SQN_FALLBACK`）、`AUTH_POLICY_NOT_FOUND`（ポリシー未登録）で Reject されていた（Reject だが理由が違う）。このとき `sub:001019999999999` に `sqn` だけが書き込まれたため、旧ケースを旧実装で実行した環境では `docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning DEL sub:001019999999999` で削除しておく（INT-VALKEY-001 の加入者件数がずれるため。また、残っているとテストベクターモードでは登録済みとして扱われる）。

> **注意 (INT-AUTH-AKA-007, r3追記、r8改訂)**: IMSI 003 は Valkey に AMF=8000 で登録されているが、テストベクターモードでは AMF が固定値 `B9B9` になるため、`config_testvector.yaml`（AMF=B9B9）を使う。`config_testvector_imsi003.yaml`（AMF=8000）を使うと eapaka_test が AMF ミスマッチで中断する（セクション2.3）。

### 5.8 G8: PLMNルーティング

**目的**: Vector GatewayのPLMNマップによるルーティング動作を検証する。gatewayモードでIMSIからPLMNを抽出し、PLMNマップに基づいて適切なバックエンドにルーティングされることを確認する。

| INT-GW-PLMN-009 | PLMNマップ一致（内部API） | eapaka_test | `success_aka_testvector.yaml` | Accept（BackendID 00 経由） |

> **注意（r8更新）: INT-GW-PLMN-010 の未実装ID**

### 5.9 G9: 障害系 + タイムアウト

**目的**: コンポーネント停止時の縮退動作、Circuit Breaker動作、EAPコンテキストTTL超過時の動作を検証する。

> **重要: 人間介在が必要なグループ。** `docker compose stop/start` による障害注入およびValkey直接操作を含む。AIエージェントでの自動実行時は、各ステップで操作承認が求められる。

| ID | シナリオ名 | ツール | PASS条件 |
|:---|:---------|:------|:--------|
| INT-FAULT-001 | Vector API停止 | eapaka_test + docker compose | Reject（`VECTOR_API_ERR`（http_status=502）。※3）→ 復旧後Accept |
| INT-FAULT-002 | Valkey停止（認証） | eapaka_test + docker compose | 無応答（`RADIUS_SECRET_ERR`）→ 復旧後Accept（※1） |
| INT-FAULT-003 | Valkey停止（課金） | radclient + docker compose | 無応答（`RADIUS_SECRET_ERR`）→ 復旧後Response（※1） |
| INT-FAULT-004 | Vector Gateway停止 | eapaka_test + docker compose | Reject（`VECTOR_CONN_ERR`。※3）→ 復旧後Accept |
| INT-FAULT-005 | Circuit Breaker動作 | eapaka_test + docker compose | CB Open/Half-Open/Closed遷移ログ確認（※2） |
| INT-TIMEOUT-001 | 疑似タイムアウト（不正State） | radclient + redis-cli | Reject, `EAP_CTX_NOT_FOUND` ログ |
| INT-TIMEOUT-002 | Valkey TTL短縮方式 | redis-cli | キー消滅確認、Reject |
| INT-VALKEY-005 | インデックスクリーンアップ | redis-cli | 孤立インデックス検出可能 |

> **※1 Valkey停止時の挙動（r3追記、r4補足）**: Valkey停止中はRADIUSクライアントのSecret検索が不可能なため（`RADIUS_SECRET_ERR`イベント）、サーバーはReject/Responseパケットを構築できず**無応答（タイムアウト）**となる。これはRejectよりも安全な障害動作であり、PASS判定とする。復旧後はValkeyのAOF永続化により通常データは自動復旧するが、テストデータが消失している場合は再投入が必要。ログ確認時は `VALKEY_CONN_ERR` ではなく `RADIUS_SECRET_ERR` を検索すること（障害はRADIUSプロトコル層のSecret検索段階で顕在化する）。
>
> **※2 Circuit Breaker テスト時の注意（r4追記）**: CBFailureThreshold=5、CBInterval=10秒の設定に対し、Vector API停止中の各リクエストは失敗までに最大で約3秒（vector-gateway の内部Vector API呼び出しタイムアウト `VECTOR_GATEWAY_INTERNAL_TIMEOUT`、既定3秒。停止したコンテナ名の名前解決に時間がかかる環境ではこのタイムアウトに達してから 502 になる）かかる場合があるため、**逐次実行では10秒ウィンドウ内に5失敗を蓄積できない**（r13改訂。r12 以前は Auth Server のリクエストタイムアウトにより約4〜5秒）。5プロセスを並列実行（バックグラウンド実行 + `wait`）することで10秒以内に5失敗を蓄積し、CB Open遷移を発生させる。CB Half-Open遷移は CBTimeout=30秒後に発生するため、待機後にリクエストを送信して確認する。

> **※3 Vector API停止とVector Gateway停止のevent_id（r8追記、r13改訂。実装: `apps/auth-server/internal/vector/client.go`, `internal/engine/engine.go` の `logVectorError`、`apps/vector-gateway/internal/backend/internal.go`, `internal/handler/vector.go`, `internal/config/config.go`, `main.go`）**
> - **Vector API停止（INT-FAULT-001）**: vector-gateway は vector-api に接続できず、`GW_ERR`（ERROR, msg `backend communication error`）を出して **502** を返す。Auth Server はこれを `VECTOR_API_ERR`（`http_status`=502）として記録する（HTTPクライアント層の msg `vector api error` と認証フロー層の msg `Vector APIエラー` の2行）。停止したコンテナ名の名前解決が失敗するまでの時間は環境（Docker の埋め込みDNSが問い合わせる上位DNS）に依存するが、vector-gateway の内部Vector API呼び出しタイムアウト（`VECTOR_GATEWAY_INTERNAL_TIMEOUT`、既定3秒）は Auth Server のリクエストタイムアウト（5秒）より短いため、名前解決に時間がかかる環境でも vector-gateway が3秒で打ち切って 502 を返し、`VECTOR_API_ERR` になる。このため PASS 条件は `VECTOR_API_ERR`（`http_status`=502）とする。`VECTOR_CONN_ERR`（msg `Vector接続エラー`）が出た場合は、`.env` で `VECTOR_GATEWAY_INTERNAL_TIMEOUT` を5秒以上にしていないか確認する（その場合 vector-gateway は起動時に WARN `backend timeout should be shorter than the auth-server timeout; auth-server may time out before receiving 502` を出す）。経緯: 以前は既定値が両方とも5秒だったため、名前解決に5秒以上かかる環境では Auth Server 側が先にタイムアウトして `VECTOR_CONN_ERR` になっていた（2026-02-21 の実施では `VECTOR_CONN_ERR` が記録され、2026-10-04 に WSL2 上の Docker で確認したところ停止中コンテナ名の名前解決の失敗まで約7秒かかった）。r12 までは PASS 条件をどちらの event_id も可としていたが、vector-gateway の既定値を3秒に変更したため r13 で `VECTOR_API_ERR` のみとした。
> - **Vector Gateway停止（INT-FAULT-004）**: Auth Server が vector-gateway に接続できない（名前解決失敗・接続拒否・タイムアウト）ため、HTTP応答はなく、常に `VECTOR_CONN_ERR` になる。
> - どちらも Circuit Breaker の失敗回数に数えられる（5xx は 501 を除き失敗、接続失敗・タイムアウトも失敗）。

#### 事前準備

**(1) aka-only-server の起動（同一ホスト）**

aka-only-server のリポジトリで compose 起動する。aka-only-server の compose が共有ネットワーク（既定名 `aka-av`）を作るため、PoC より先に起動する。INT-GW-AKAONLY-010/011 のため、aka-only-server 側で `AKA_AV_PLAIN_ADDR=:8080` を設定しておく（平文HTTP は同一ホスト内に限る）。公開ポートはループバックに限定することを推奨する。

**(2) 証明書の発行とクライアント・加入者の登録（aka-only-server 側で実行）**

```bash
# クライアント radius-gw（ID 1 を想定）と other-client（ID 2 を想定）
docker compose exec -T aka-only-server /aka-only-server client gen-cert -name radius-gw > av-client.pem
docker compose exec -T aka-only-server /aka-only-server client add -name radius-gw -cert - < av-client.pem
docker compose exec -T aka-only-server /aka-only-server client gen-cert -name other-client > other-client.pem
docker compose exec -T aka-only-server /aka-only-server client add -name other-client -cert - < other-client.pem
# INT-GW-AKAONLY-013 用（client add しない）
docker compose exec -T aka-only-server /aka-only-server client gen-cert -name unregistered > av-client-unregistered.pem
# AV 用サーバー証明書
docker compose exec -T aka-only-server /aka-only-server av-cert > av-server.pem

# 加入者（3GPP TS 35.208 Test Set 1、AMF 8000・SQN 000000000000・inc32 は既定値）
KI=465B5CE8B199B49FAA5F0A2EE238A6BC
OPC=CD63CB71954A9F4E48A5994E37A02BAF
docker compose exec -T aka-only-server /aka-only-server subscriber add -imsi 440100000000001 -ki $KI -opc $OPC -clients 1
docker compose exec -T aka-only-server /aka-only-server subscriber add -imsi 440100000000002 -ki $KI -opc $OPC -clients 2
docker compose exec -T aka-only-server /aka-only-server subscriber add -imsi 440100000000003 -ki $KI -opc $OPC -clients 1 -allow-plain
# 440100000000099 は登録しない（INT-GW-AKAONLY-006）
```

`client add` は `client 1 added (name=radius-gw fingerprint=... not-after=...)` のように発番されたIDを表示する。IDが想定と異なる場合は `-clients` の値を読み替える。加入者・クライアントの登録は Web GUI（https://github.com/oyaguma3/web-gui-for-aka-only-server）からでもよい。

`av-client.pem` / `av-server.pem`（および INT-GW-AKAONLY-012/013 用の証明書）を `deployments/certs/` に置き（`.gitignore` で除外済み）、`.env` を設定する。

**(5) eapaka_test の設定例**

supplement 配下には置かず、実施時に作業ディレクトリへ作成する。

```yaml
# config_akaonly.yaml（通常認証用）
radius:
  server_addr: "127.0.0.1:1812"
  secret: "TESTSECRET123"
  timeout_ms: 3000
  retries: 3
radius_attrs:
  nas_ip_address: "192.168.10.1"
  nas_identifier: "Customer01"
  called_station_id: "00-10-A4-23-19-C0:TESTSSID-01"
  calling_station_id: "00-22-FA-94-68-58"
eap:
  method_mismatch_policy: "warn"
  outer_identity_update_on_permanent_req: true
  permanent_id_policy: "always"
  aka_prime:
    net_name: "WLAN"        # サーバーが送る AT_KDF_INPUT が優先される（auth-server の EAP_AKA_PRIME_NETWORK_NAME、既定 "WLAN"）
identity:
  realm: "wlan.mnc010.mcc440.3gppnetwork.org"
sim:
  imsi: "440100000000001"
  ki: "465B5CE8B199B49FAA5F0A2EE238A6BC"   # 3GPP TS 35.208 Test Set 1
  opc: "CD63CB71954A9F4E48A5994E37A02BAF"
  amf: "8000"
  sqn_initial_hex: "000000000000"
sqn_store:
  mode: "file"
  path: "/tmp/eapaka_test-sqn-akaonly.json"
```

- **再同期用 config**（`config_akaonly_resync.yaml`）: 上記の `sim.sqn_initial_hex` を **`FF9BB4D0B600`**、`sqn_store.path` を別ファイル（例 `/tmp/eapaka_test-sqn-akaonly-resync.json`）にする。
- **IMSI ごとの config**: eapaka_test の SQN ストアは config の `sim.imsi` をキーにするため、`440100000000003` / `440200000000001` などは `sim.imsi` と `sqn_store.path` を変えた config を IMSI ごとに用意する（`440200000000001` は `identity.realm` を `wlan.mnc020.mcc440.3gppnetwork.org` にする）。以下の手順では `config_akaonly_003.yaml` / `config_akaonly_resync_003.yaml` / `config_akaonly_44020.yaml` と表記する。
- **テストケース**: 既存の `success_aka_testvector.yaml` / `success_aka_prime_testvector.yaml` / `resync_aka_testvector.yaml` / `resync_aka_prime_testvector.yaml` をコピーし、`identity` を対象 IMSI に書き換える（EAP-AKA は先頭 `0`、EAP-AKA' は先頭 `6`。例 `0440100000000001@wlan.mnc010.mcc440.3gppnetwork.org`）。AKA' の `eap.aka_prime.net_name` は削除してよい。Reject を期待するシナリオは `expect.result: reject` とし `mppe` を外す。以下の手順ではファイル名を `{success|resync|reject}_{aka|aka_prime}_{IMSI}.yaml` と表記する。

> **再同期用に `FF9BB4D0B600` を使う理由**: eapaka_test はクライアント側 SQN を IND（下位5ビット）ごとの配列で管理し、受信 SQN と同じ IND スロットの値と比較する。aka-only-server（SQN 増加タイプ inc32）の SQN は IND=0 のまま増えるため、再同期を起こすには IND=0 のスロットを高い値にする必要がある。`FF9BB4D0B600` は IND=0 の高値で、`sqn.reset: true` でこの値にリセットすると、aka-only-server の SQN が古いと判定され AUTS による再同期が起きる。既存 config の `FF9BB4D0B607` は IND=7 で別スロットのため、再同期が起きずに Accept になる（PASS するが再同期を検証できていない）。

### 7.2 AI自動実行時の注意事項

1. **Session UUID取得**: G6・G7ではAuth Serverログから`AUTH_SUCCESS`イベントのsession_idを抽出する必要がある。ログ出力タイミングに依存するため、認証実行後に数秒待機してからログを確認すること。

2. **SQN状態の影響**: 複数グループを順次実行するとSQNがインクリメントされる。G3（SQN再同期）はG2の後に実行すること。異なるIMSIを使用するグループ間では影響なし。

3. **Valkeyデータのリセット**: グループ間でデータ状態がクリーンであることを保証するため、必要に応じてセッション・重複検出データを手動削除する。
   ```bash
   docker compose exec -T valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning KEYS "sess:*" | xargs -r docker compose exec -T valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning DEL
   docker compose exec -T valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning KEYS "acct:seen:*" | xargs -r docker compose exec -T valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning DEL
   ```

4. **docker compose操作（G9）**: Claude Codeでの`docker compose stop`/`start`は権限承認ダイアログが表示される。自動実行する場合は事前に許可設定を行うか、人間が各ステップで承認する。

5. **ログのタイムスタンプ**: `--since` パラメータで対象期間を適切に絞ること。長時間実行時は前のグループのログと混在する可能性がある。

6. **IMSI別eapaka_test設定の使い分け（r3追記、r8改訂）**: テストベクターモード（`TEST_VECTOR_ENABLED=true`）では、IMSI 003 を使うシナリオ（INT-AUTH-AKA-007, INT-POLICY-003, INT-POLICY-004, INT-POLICY-005）も含めて全シナリオで `config_testvector.yaml`（AMF=B9B9）を使う。テストベクター対象 IMSI は AMF が固定値 `B9B9` になるためで、`config_testvector_imsi003.yaml`（AMF=8000）を使うと AMF ミスマッチで中断する（ERROR、終了コード2）。`config_testvector_imsi003.yaml` は実計算モード（`TEST_VECTOR_ENABLED=false`。`sub:001010000000003` の AMF=8000 で計算）専用である。

7. **SQN初期値とリセット運用（r3追記、r5補足）**: テストベクターモードではSQN increment step = 0x20（32進）であり、テストを繰り返すとSQNが急速に増加する。高SQN値（例: `FF9BB4D0B607`）ではVector APIの「SQN difference exceeds allowed range」チェックに抵触し認証が失敗する場合がある。**SQNリセット時は、eapaka_test設定ファイルの`sqn_initial_hex`の値に応じた適切な値を設定すること。**
   - **configのプライマリIMSI（例: IMSI 000）**: テストケースの`identity`でオーバーライドされないIMSI。SQNストアファイルで直接管理されるため、低値（`000000000001`）へのリセットでよい。
   - **identityオーバーライドIMSI（例: IMSI 001, 002, 003, 006, 007）**: eapaka_testはSQNストアに未登録のIMSIに対して`sqn_initial_hex`（例: `FF9BB4D0B607`）を初期SQNとして使用する。そのため、**サーバー側SQNも`sqn_initial_hex`と同等の値に設定する必要がある**。低値にリセットするとクライアント側SQNとの差が大きくなり、「SQN difference exceeds allowed range」エラーが発生する。
   ```bash
   # SQNリセット例（全テストベクターIMSI）
   # プライマリIMSI（IMSI 000）: 低値でOK
   docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000000 sqn "000000000001"
   # identityオーバーライドIMSI: sqn_initial_hex に合わせる
   docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000001 sqn "FF9BB4D0B607"
   docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000002 sqn "FF9BB4D0B607"
   docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000006 sqn "FF9BB4D0B607"
   docker compose exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning HSET sub:001010000000007 sqn "FF9BB4D0B607"
   ```

8. **radclient属性入力方式（r3追記）**: radclientへの属性入力にechoパイプ（`echo -e '...' | radclient`）を使用すると、シェル環境によっては属性名解析エラーが発生する場合がある。一時ファイルに属性を書き出してからリダイレクトで入力する方式を推奨する。
   ```bash
   # 推奨方式
   printf 'Message-Authenticator = 0x00\n' > /tmp/status.attrs
   radclient -x -r 1 -t 3 127.0.0.1:1812 status TESTSECRET123 < /tmp/status.attrs

   # 非推奨（環境依存で失敗する可能性あり）
   echo -e 'Message-Authenticator = 0x00' | radclient -x 127.0.0.1:1812 status TESTSECRET123
   ```

9. **Valkey停止テスト後のデータ再投入（r3追記、r4補足）**: INT-FAULT-002/003でValkeyを停止・再起動した際、AOF永続化が有効であればデータは自動復旧する。ただし`FLUSHDB`が実行された場合やAOFファイルが破損した場合はデータが消失する。復旧後の認証テスト（Accept確認）の前に、テストデータ（加入者・クライアント・ポリシー）が残存しているか `DBSIZE` コマンド等で確認し、必要に応じて再投入すること。

10. **Valkey停止時のログイベントID（r4追記）**: Valkey停止時のエラーは `VALKEY_CONN_ERR` ではなく **`RADIUS_SECRET_ERR`** として記録される。これはRADIUSプロトコル層でクライアントSecret検索（Valkey参照）に失敗するためであり、認証/課金の処理ロジックに到達する前にパケットが破棄される。ログ検索時は `grep -E "RADIUS_SECRET_ERR"` を使用すること。

11. **Vector API停止 vs Vector Gateway停止のログイベント（r4追記、r8改訂、r13改訂）**: Vector API単体停止時はVector Gatewayが502 Bad Gatewayを返すため `VECTOR_API_ERR`（`http_status`=502）が記録される。Vector Gateway の内部Vector API呼び出しタイムアウト（既定3秒）は Auth Server のリクエストタイムアウト（5秒）より短いため、停止コンテナ名の名前解決に時間がかかる環境でも Auth Server より先に 502 を返す（r12 まではどちらも5秒で、名前解決に5秒以上かかる環境では `VECTOR_CONN_ERR` になっていた。2026-02-21 の実施はこちら）。一方、Vector Gateway自体を停止した場合はDNS解決失敗・コネクション拒否・タイムアウトのいずれでも `VECTOR_CONN_ERR` が記録される。詳細はセクション5.9 の※3。ログ検索は `grep -E "VECTOR_API_ERR|VECTOR_CONN_ERR"` で両方を拾うこと（Vector API停止で `VECTOR_CONN_ERR` が出た場合はタイムアウト設定を確認する）。

12. **Circuit Breaker テストの並列実行（r4追記）**: INT-FAULT-005（CB動作確認）では、CBInterval=10秒以内にCBFailureThreshold=5回の失敗を蓄積する必要がある。各リクエストの失敗まで最大で約3秒（r12 以前は約4秒）かかるため逐次実行では不可能。以下のように並列実行する:
    ```bash
    # Vector API停止後、5プロセス並列でCB Open遷移を発生させる
    for i in $(seq 1 5); do
      eapaka_test -c $CONFIG run $CASES/success_aka_testvector.yaml &
    done
    wait
    # auth-serverログで CB_OPEN を確認
    docker compose logs auth-server --since=1m | grep CB_OPEN
    ```

13. **依存ライブラリ更新時のDockerイメージ再ビルド（r5追記）**: go-eapaka等の外部パッケージを更新した場合、`go.mod`の変更だけではDocker コンテナに反映されない。**必ず`docker compose build <service>`でイメージを再ビルドし、`docker compose up -d`でコンテナを再作成すること。** 古いイメージのまま実行すると、サーバーとテストツール間で暗号処理（PRF、鍵導出等）の不一致が発生し、AT_MAC検証失敗やAuthentication-Rejectとなる。
    ```bash
    # 例: auth-server の依存ライブラリ更新後
    docker compose -f deployments/docker-compose.yml build auth-server
    docker compose -f deployments/docker-compose.yml up -d auth-server
    # healthy 状態を確認
    docker compose -f deployments/docker-compose.yml ps
    ```

14. **eapaka_test SQNストアファイルのIMSI間干渉（r4追記）**: eapaka_testのSQNストアファイルは `sim.imsi` をキーにSQNを管理するが、設定ファイルのIMSIとテストケースのIMSIが異なる場合、設定ファイルのIMSI（デフォルト: `001010000000000`）のSQNが使用される。異なるIMSI（例: `001010000000007`）のテスト実行後にIMSI 000のサーバー側SQNとの不整合が発生する場合がある。テストケース切替時にはSQNストアファイルの削除を推奨する。
