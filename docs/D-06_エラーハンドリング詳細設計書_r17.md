# D-06 エラーハンドリング詳細設計書 (r17)

## 1. 概要

### 1.1 目的

本ドキュメントは、EAP-AKA RADIUS PoC環境を構成する各コンポーネントにおける異常系の検出・対処・復旧方針を定義し、システム全体の耐障害性と運用性を確保することを目的とする。

### 1.2 対象範囲

本書で扱うコンポーネント：

| コンポーネント | 役割 | 主な異常系 |
|---------------|------|-----------|
| **Auth Server** | RADIUS認証、EAP-AKA/AKA'制御 | Vector Gateway障害、Valkey障害、不正パケット、認証失敗 |
| **Acct Server** | RADIUS課金 | Valkey障害、不正パケット、セッション不整合 |
| **Vector Gateway** | ルーティング、ベクター取得先振分け | Vector API障害、aka-only-server障害（接続方式01）、ルーティングエラー、リクエスト不正、起動時設定エラー |
| **Vector API** | 認証ベクター計算 | Valkey障害、計算エラー、IMSI不在 |
| **Admin TUI** | 管理コンソール | Valkey障害、入力エラー、インポートエラー |

**注記：** Valkey、Fluent Bit、Docker Compose、ホストOS（UFW等）のインフラ層設定については「インフラ設定・運用設計書」で別途定義する。

### 1.3 PoC対象外機能

本PoCでは以下の機能は実装対象外とする：

| 機能 | 説明 | 受信時の対処 |
|------|------|-------------|
| 仮名認証 | Pseudonym IDによる認証 | フル認証へ誘導 |
| 高速再認証 | Fast Re-authentication | フル認証へ誘導 |
| EAP-Notification | 通知メッセージ送信 | 使用しない |
| 外部API接続方式（`02`〜`99`） | Vector Gatewayからの外部API連携（接続方式01: aka-only-server は実装済み） | 501 Not Implemented返却 |

## 2. エラー分類と重大度

### 2.1 エラーカテゴリ定義

| カテゴリ | 説明 | 例 |
|---------|------|-----|
| **通信エラー (COMM)** | 外部システムとの接続・通信障害 | Valkey接続断、Vector Gateway/APIタイムアウト |
| **プロトコルエラー (PROTO)** | RADIUS/EAPプロトコル違反 | 不正パケット形式、未知のEAPタイプ |
| **ルーティングエラー (ROUTE)** | ルーティング処理の失敗 | 未実装バックエンド、PLMN不正 |
| **データエラー (DATA)** | データの不整合・不在 | IMSI未登録、ポリシー未設定、SQN不整合 |
| **認証エラー (AUTH)** | 認証処理の失敗 | RES不一致、MAC検証失敗 |
| **システムエラー (SYS)** | 内部的な予期せぬ障害 | メモリ不足、Panic |

### 2.2 重大度レベル定義

| レベル | 定義 | ログレベル | 対応方針 |
|--------|------|-----------|---------|
| **Critical** | サービス継続不可 | ERROR | 即座に運用者通知、復旧優先 |
| **Error** | 個別リクエスト失敗 | ERROR/WARN | ログ記録、リクエスト拒否 |
| **Warning** | 潜在的問題 | WARN | ログ記録、監視対象 |
| **Info** | 正常範囲内の注目イベント | INFO | ログ記録 |

## 3. コンポーネント別エラー処理

### 3.1 Auth Server

#### 3.1.1 通信エラー

##### Vector Gateway接続エラー

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| 接続失敗 | TCP接続エラー | Circuit Breaker カウント | EAP-Failure + Access-Reject | ERROR: `VECTOR_CONN_ERR` |
| タイムアウト | 応答なし（5秒超過） | Circuit Breaker カウント | EAP-Failure + Access-Reject | ERROR: `VECTOR_CONN_ERR` |
| HTTPエラー（404） | IMSI未登録 | Circuit Breaker カウント対象外 | EAP-Failure + Access-Reject | ERROR: `VECTOR_API_ERR`（HTTPクライアント層）＋ `VECTOR_IMSI_NOT_FOUND` |
| HTTPエラー（4xx、404以外） | ステータスコード400番台（400/403/409等） | Circuit Breaker カウント対象外 | EAP-Failure + Access-Reject | ERROR: `VECTOR_API_ERR`（HTTPクライアント層・認証エンジンの2行） |
| HTTPエラー（5xx、501以外） | ステータスコード500番台（500/502等） | Circuit Breaker カウント | EAP-Failure + Access-Reject | ERROR: `VECTOR_API_ERR`（HTTPクライアント層・認証エンジンの2行） |
| HTTPエラー（501） | 未実装バックエンド | Circuit Breaker カウント対象外 | EAP-Failure + Access-Reject | ERROR: `VECTOR_API_ERR`（HTTPクライアント層・認証エンジンの2行） |
| Circuit Breaker Open | CB状態がOpen | API呼び出しスキップ | EAP-Failure + Access-Reject | ERROR: `VECTOR_CB_OPEN`（リクエストごと）、WARN: `CB_OPEN`（状態遷移時） |
| その他 | 応答本文の不正等 | - | EAP-Failure + Access-Reject | ERROR: `VECTOR_UNKNOWN_ERR` |

> **注記：** Auth ServerからはVector Gatewayに対して接続する。Vector Gatewayが501 Not Implementedを返却した場合は、未実装の接続方式IDが使用されたことを意味する。
>
> **注記（ログ出力箇所）：** HTTPエラー応答（200以外）のときは、HTTPクライアント層（`internal/vector/client.go`）が `VECTOR_API_ERR`（msg `vector api error`、`error`, `http_status`, `latency_ms`。`trace_id` なし）を出力し、続いて認証エンジン（`internal/engine/engine.go` の `logVectorError`）が `VECTOR_API_ERR` または `VECTOR_IMSI_NOT_FOUND`（msg `Vector APIエラー`、`trace_id`, `imsi`, `http_status`, `error`）を出力するため、1件のエラーで2行出力される。接続失敗・タイムアウト（`VECTOR_CONN_ERR`）、Circuit Breaker Open（`VECTOR_CB_OPEN`）、その他（`VECTOR_UNKNOWN_ERR`）は認証エンジンのみが出力する。いずれの場合も Access-Reject を返す。
>
> **注記（バックエンド障害時のevent_id）：** Vector Gateway のバックエンド向けタイムアウト（既定 3秒。§3.3.1、§4.1）は Auth Server のリクエストタイムアウト（5秒）より短いため、バックエンド（Vector API / aka-only-server）の停止・無応答時は Vector Gateway が先に 502 を返し、Auth Server のログは `VECTOR_API_ERR`（`http_status`=502）になる。`VECTOR_CONN_ERR` は Vector Gateway 自体に接続できない・応答しない場合に出る。Vector Gateway のタイムアウトを 5秒以上に設定すると、バックエンド障害時にも Auth Server が先にタイムアウトして `VECTOR_CONN_ERR` になることがある（Vector Gateway は起動時に WARN を出す。§3.3.4）。
>
> **注記（409 Conflict）：** Vector API は、同一IMSIへの並行リクエストでSQNの書き換えが3回とも競合した場合に 409 Conflict を返す（§3.4.3）。Vector Gateway はこれをそのまま中継し（§3.3.1）、Auth Server は他の4xxと同様に Circuit Breaker の失敗回数に数えず、`VECTOR_API_ERR`（`http_status`=409。HTTPクライアント層・認証エンジンの2行）を出力して EAP-Failure + Access-Reject を返す（D-09 §7.8.1）。端末は認証をやり直す。
>
> **注記（接続方式01）：** 接続方式01（aka-only-server）経由では、4xxとして新たに 403 Forbidden が返る場合がある（D-03参照）。Auth Server は200以外の4xxを Circuit Breaker 対象外の APIError として Access-Reject とするため、403 も 404/400 と同様に扱われ、Auth Server 側の変更は不要（ログ: 403 → `VECTOR_API_ERR`（`http_status`=403）、404 → `VECTOR_IMSI_NOT_FOUND`）。

##### Valkey接続エラー

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| 接続失敗（起動時） | TCP接続エラー | 起動時エラー終了 | - | ERROR: `VALKEY_CONN_ERR` |
| 認証失敗（起動時） | AUTH失敗 | 起動時エラー終了 | - | ERROR: `VALKEY_CONN_ERR`（起動時の接続失敗に含まれる。認証失敗専用のevent_idはない） |
| 接続失敗（実行時） | TCP接続エラー | リトライ（2回、指数バックオフ） | EAP-Failure + Access-Reject | 専用のevent_idなし（下記注記） |
| コマンドタイムアウト（実行時） | 応答なし（2秒超過） | リトライ | EAP-Failure + Access-Reject | 専用のevent_idなし（下記注記） |

> **注記（実行時のValkeyエラーのログ）：** Auth Serverには実行時のValkeyエラー専用のevent_idはない。処理箇所に応じて `RADIUS_SECRET_ERR`（Shared Secret解決時）、`EAP_CTX_NOT_FOUND`（EAPコンテキスト取得時）、`AUTH_POLICY_NOT_FOUND`（ポリシー取得時）、`EAP_CTX_CREATE_ERR` / `EAP_CTX_UPDATE_ERR`（EAPコンテキスト保存・更新時）、`SESSION_CREATE_ERR` / `SESSION_INDEX_ERR`（セッション作成時）の `error` 属性で記録される（D-04 §3.1、§4.3）。Valkey接続の復旧検知ログは出力しない（§4.4.2参照）。

#### 3.1.2 プロトコルエラー

##### RADIUSレイヤー

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| パケットパース失敗 | 不正なRADIUS形式（20バイト未満、長さ・属性の不整合等。形の壊れたパケット） | パケット破棄（`layeh.com/radius` がデコードに失敗し、ハンドラーに渡さない） | なし（応答しない） | WARN: `RADIUS_LIB_ERR`（`error` にライブラリのメッセージ。`src_ip` なし） |
| Shared Secret不一致 | Message-Authenticator検証失敗 | パケット破棄 | なし（応答しない） | WARN: `PKT_MA_INVALID`（Status-Serverの場合は `RADIUS_STATUS_AUTH_FAIL`） |
| Shared Secret不明 | client:{IP}不在かつ環境変数未設定 | パケット破棄 | なし（応答しない） | WARN: `RADIUS_NO_SECRET`（ライブラリの DEBUG `RADIUS_LIB_ERR` も出る） |
| 未知のRADIUSコード | Access-Request / Status-Server 以外のCode値（Accounting-Request、未知のCode等。共有シークレットの正否を問わない） | パケット破棄 | なし（応答しない） | WARN: `PKT_UNKNOWN_CODE` |
| EAP-Message属性なし | Access-RequestにEAP-Messageがない | パケット破棄 | なし（応答しない） | WARN: `PKT_NO_EAP` |

**理由：** RADIUSレイヤーの不正パケットは「信頼できない送信元」の可能性があるため、RFC 2865に準拠し応答しない。

> **注記（パケットの認証とライブラリのエラー）：** パケットの認証はライブラリ（`PacketServer`）では行わず（`InsecureSkipVerify: true`）、ハンドラーで検証して、失敗したら送信元IP付きのログを出して破棄する（D-09 §4.3）。ライブラリのエラー（デコード失敗、受信エラー等）は `PacketServer.ErrorLog` 経由で `RADIUS_LIB_ERR`（JSON）として出力する。ライブラリは共有シークレットの解決→デコードの順に処理するため、シークレットが決まらない送信元からの形の壊れたパケットは `RADIUS_NO_SECRET` になる（D-04 §3.1.3）。

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| EAPパケットパース失敗 | 不正なEAP形式 | EAP-Failure送信 | Access-Reject | WARN: `EAP_PARSE_ERR` |
| 初回パケットがIdentityでない | State無しの初回EAP-AKA/AKA'パケットのSubtypeがAKA-Identity以外 | パケット破棄 | なし（応答しない） | WARN: `EAP_NOT_IDENTITY`（続いて INFO: `PKT_DROP`） |
| 未知のEAPサブタイプ | 後続パケットのSubtypeが未知 | EAP-Failure送信 | Access-Reject | WARN: `EAP_UNKNOWN_SUBTYPE` |
| 非対応EAP方式 | EAP-SIM等 | EAP-Failure送信 | Access-Reject | WARN: `EAP_UNSUPPORTED_TYPE` |
| Identity形式不正 | IMSI抽出失敗、永続ID要求への応答が仮名/再認証ID | EAP-Failure送信 | Access-Reject | WARN: `EAP_IDENTITY_INVALID` |

| 不正なタイミングのIdentity | `WAITING_IDENTITY` 以外でAKA-Identityを受信 | EAP-Failure送信 | Access-Reject | WARN: `EAP_UNEXPECTED_IDENTITY` |

##### フル認証への誘導（仮名/高速再認証受信時）

仮名(2,7)または高速再認証ID(4,8)を含むIdentityを受信した場合、永続識別子による再認証を要求する。RFC 4187 Section 4.1.4 に基づき、`AT_PERMANENT_ID_REQ` を使用する。

```
[Client]                              [Auth Server]
    |                                      |
    |  EAP-Response/Identity               |
    |  (Identity: 2<pseudonym>@realm)      |
    |------------------------------------->|
    |                                      |
    |  EAP-Request/AKA-Identity            |
    |  (AT_PERMANENT_ID_REQ)               |
    |<-------------------------------------|
    |                                      |
    |  EAP-Response/AKA-Identity           |
    |  (AT_IDENTITY: 0<IMSI>@realm)        |
    |------------------------------------->|
    |                                      |
    |  (通常のフル認証フローへ継続)          |
```

**注記：**
- EAP-AKA の場合: `EAP-Request/AKA-Identity` に `AT_PERMANENT_ID_REQ` を含めて送信
- EAP-AKA' の場合: `EAP-Request/AKA'-Identity` に `AT_PERMANENT_ID_REQ` を含めて送信
- クライアントは永続識別子（IMSI）を `AT_IDENTITY` に格納して応答する
- フル認証誘導時の専用ログは出力しない（初回の EAP-Response/Identity 受信時の `EAP_IDENTITY_RECEIVED` のみ）

##### EAP-AKA/AKA'固有エラー

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| AKA-Client-Error受信 | AT_CLIENT_ERROR_CODE含む | ログ記録（エラーコードは記録しない） | EAP-Failure + Access-Reject | WARN: `EAP_CLIENT_ERROR` |
| AKA-Authentication-Reject受信 | クライアントがAUTN検証失敗 | ログ記録 | EAP-Failure + Access-Reject | WARN: `EAP_AUTH_REJECT` |
| AKA-Synchronization-Failure受信 | SQN不整合 | Vector Gateway再同期呼び出し | （再同期後に再Challenge） | INFO: `EAP_RESYNC_CHALLENGE`（Vector API側では INFO: `SQN_RESYNC`） |
| 再同期連続失敗 | 同一セッションで再同期32回超過 | 認証失敗 | EAP-Failure + Access-Reject | WARN: `AUTH_RESYNC_LIMIT` |

**再同期リトライ上限について：**
- 上限値: 32回
- 根拠: SQN の IND (Index) フィールドが5ビット（0-31）であり、1サイクル分の試行を許容
- 32回を超えた場合は、SIM側またはネットワーク側に深刻な問題があると判断し、認証を拒否

### 3.2 Acct Server

#### 3.2.1 通信エラー

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| Valkey接続失敗 | TCP接続エラー | リトライ（3回） | Accounting-Response（ベストエフォート） | ERROR: `VALKEY_CONN_ERR` |
| Valkeyコマンドタイムアウト | 応答なし（2秒超過） | リトライ | Accounting-Response | ERROR: `VALKEY_CONN_ERR` |

**注記：** Valkey障害時も課金パケットにはAccounting-Responseを返す（クライアントの再送を防ぐため）。データ欠損はログから追跡可能とする。`VALKEY_CONN_ERR` は起動時の接続失敗（プロセス終了）と、実行時の読み取り系エラー（重複チェック、セッション存在確認、Start受信有無確認）で出力される。実行時の書き込み失敗は ERROR: `DB_WRITE_ERR`、Shared Secret解決時のValkeyエラーは WARN: `RADIUS_SECRET_ERR` となる。Valkey接続の復旧検知ログは出力しない。

#### 3.2.2 プロトコルエラー

| エラー種別 | 検出条件 | 対処 | RADIUS応答 | ログ |
|-----------|---------|------|-----------|------|
| パケットパース失敗 | 不正なRADIUS形式（形の壊れたパケット） | パケット破棄（`layeh.com/radius` がデコードに失敗し、ハンドラーに渡さない） | なし | WARN: `RADIUS_LIB_ERR`（`error`。`src_ip` なし） |

### 3.3 Vector Gateway

#### 3.3.1 通信エラー

##### Vector API接続エラー

| エラー種別 | 検出条件 | 対処 | HTTP応答 | ログ |
|-----------|---------|------|---------|------|
| 接続失敗 | TCP接続エラー | - | 502 Bad Gateway | ERROR: `GW_ERR`（`backend communication error`） |
| タイムアウト | 応答なし（`VECTOR_GATEWAY_INTERNAL_TIMEOUT` 超過。既定 3秒） | - | 502 Bad Gateway | ERROR: `GW_ERR`（`backend communication error`） |
| HTTPエラー（4xx） | ステータスコード400番台（400/404/409） | エラー透過 | 元のステータスコードを返却 | WARN: `GW_ERR`（`backend returned error`） |
| HTTPエラー（5xx） | ステータスコード500番台 | - | 502 Bad Gateway | ERROR: `GW_ERR`（`backend communication error`） |

>
> **注記（ログ）：** ログ列の括弧内はログの `msg`。`GW_ERR` は複数の状況で共通のため、ログ解析では `msg` で区別する。内部Vector API（接続方式00）の呼び出し専用のログはなく、00 の失敗はハンドラーの `GW_ERR`（`backend returned error` / `backend communication error`）で判断する（D-04参照）。

##### aka-only-server接続エラー（接続方式01）

接続方式01では、aka-only-server（Nudm_UEAU GenerateAv ベース）の応答を以下のとおり変換する。aka-only-server のエラー本文は `application/problem+json`（title/status/detail/cause、type なし）である。

| aka-only-server の応答 | cause | Gateway内エラー | HTTP応答（Auth Server向け） | ログ |
|-----------------------|-------|----------------|---------------------------|------|
| 404 Not Found | `USER_NOT_FOUND` | `BackendResponseError` | 404 Not Found | WARN: `BACKEND_EXTERNAL_ERR` |
| 403 Forbidden | `AUTHENTICATION_REJECTED` | `BackendResponseError` | 403 Forbidden | WARN: `BACKEND_EXTERNAL_ERR` |
| 400 Bad Request | `INVALID_MSG_FORMAT` ほか | `BackendResponseError` | 400 Bad Request | WARN: `BACKEND_EXTERNAL_ERR` |
| 501 Not Implemented | `AUTH_TYPE_NOT_SUPPORTED` | `BackendCommunicationError` | 502 Bad Gateway | ERROR: `BACKEND_EXTERNAL_ERR` |
| 5xx | `SYSTEM_FAILURE` | `BackendCommunicationError` | 502 Bad Gateway | ERROR: `BACKEND_EXTERNAL_ERR` |
| タイムアウト・接続失敗・TLSハンドシェイク失敗（未登録/無効なクライアント証明書、信頼しないサーバー証明書、ホスト名不一致） | — | `BackendCommunicationError` | 502 Bad Gateway | ERROR: `BACKEND_EXTERNAL_ERR`（`http_status`=0） |
| 4xxだが aka-only-server の ProblemDetails でない（JSONでない、cause が空。例: URL誤りによる `404 page not found`） | — | `BackendCommunicationError` | 502 Bad Gateway | ERROR: `BACKEND_EXTERNAL_ERR` |
| 200 応答の不正（壊れたJSON、ベクター配列が空、必須フィールド欠落、本文64KiB超過） | — | `BackendCommunicationError` | 502 Bad Gateway | ERROR: `BACKEND_EXTERNAL_ERR` |
| 200/4xx/5xx 以外（例: 204） | — | `BackendCommunicationError` | 502 Bad Gateway | ERROR: `BACKEND_EXTERNAL_ERR` |

**変換ルール：**
- 4xx（`BackendResponseError`）は `httputil.ProblemDetail`（`type: about:blank`）に詰め替え、title/status/detail を引き継ぐ（title が空ならHTTPステータス文言で補完）。`cause` は内部IFにないため、Vector Gatewayのログ（`BACKEND_EXTERNAL_ERR` の `cause`）にのみ出力する。
- 403 は次の3ケースで返り、`detail` で区別する: (1) 許可クライアント外 `client is not allowed for this subscriber`、(2) 再同期のAUTS検証失敗 `AUTS verification failed`（接続方式00では400）、(3) 平文HTTPで加入者の平文HTTP許可なし（detailは(1)と同じ）。
- 通信エラーのメッセージからは URL（パスに生IMSIを含む）を除去してログに出す。
- ハンドラー側の既存ログ（`GW_ERR`）も従来どおり出力される。

**ProblemDetails でない4xxを通信エラー扱いとする理由：**
URL誤り（パス違い）などで aka-only-server 以外が返した `404 page not found` 等をそのまま404として透過すると、Auth Server では「加入者未登録」と区別できず、設定ミスが加入者起因の Reject に見えてしまう。aka-only-server 由来の4xxは必ず `cause` を持つため、`cause` を持つ ProblemDetails のみを加入者・クライアント起因（4xx透過）とし、それ以外は502として Circuit Breaker の失敗にも数え、設定・通信系の障害として検出できるようにする。

**タイムアウト：**
- `VECTOR_GATEWAY_AKAONLY_TIMEOUT`（既定 3s）。超過時は 502。リトライは行わない（§4.1、§4.2参照）。
- Auth Server のリクエストタイムアウト（5秒）より短くする。同じか長いと、aka-only-server 障害時に Vector Gateway が 502 を返す前に Auth Server がタイムアウトし、`VECTOR_API_ERR`（502）ではなく `VECTOR_CONN_ERR` として記録されることがある（§3.3.4 の起動時 WARN）。

**Circuit Breaker との関係：**
- 502 は Auth Server の Circuit Breaker の失敗回数に数えられる。4xx（400/403/404）は数えない。
- Circuit Breaker は Auth Server → Vector Gateway 間に1つで、接続方式ごとに分かれていない。接続方式01向けの通信失敗（証明書不備、aka-only-server 停止等）が続いて Open になると、接続方式00向けの認証も停止する。
- 接続方式01の失敗時に接続方式00へのフォールバックは行わない（Vector API と aka-only-server でSQNが競合するため）。

#### 3.3.2 ルーティングエラー

| エラー種別 | 検出条件 | 対処 | HTTP応答 | ログ |
|-----------|---------|------|---------|------|
| 未実装バックエンド | 接続方式ID `02`〜`99`、または `VECTOR_GATEWAY_AKAONLY_URL` 未設定時の `01` | - | 501 Not Implemented | WARN: `GW_ERR`（`backend not implemented`） |
| PLMNマップ未登録 | IMSIのPLMNがマップにない | デフォルト（Vector API）へ | - | INFO: `GW_ROUTE`（`backend selected`、`backend_id`=`00`） |
| ルーティングの想定外エラー | 未実装以外の理由でバックエンド選択に失敗 | - | 500 Internal Server Error | ERROR: `GW_ERR`（`routing error`） |

> **注記：** PLMN一致/未一致を区別するログはない（DEBUGログもない）。バックエンド選択時は、PLMN一致・未一致・passthroughを問わず毎リクエスト `GW_ROUTE`（`backend selected`）を出力するため、`backend_id` で判断する。

##### 未実装バックエンドエラーについて

接続方式ID `00`（内部Vector API）と `01`（aka-only-server）が実装済みである。`01` は `VECTOR_GATEWAY_AKAONLY_URL` が設定されている場合のみ登録される。PLMNマップで未登録の接続方式ID（`02`〜`99`、URL未設定時の `01`）が指定された場合は、501 Not Implementedを返却する。この場合、起動時にもWARN（`PLMN map refers to a backend that is not configured; requests will fail with 501`）を出力する（passthroughモードを除く）。

**501返却時の処理フロー：**
```
Auth Server → Vector Gateway
                    │
                    ├── PLMNマップ照合
                    │       ↓ マッチ（未登録ID）
                    ├── バックエンド検索
                    │       ↓ 未実装
                    ├── 501 Not Implemented 返却
                    │
Auth Server ← 501応答
      │
      ↓
EAP-Failure + Access-Reject
```

**設計意図：**
- 未実装IDへのルーティングは設定ミスの可能性が高い
- 404 Not Found ではなく 501 Not Implemented を使用することで、「機能未実装」を明確に示す
- Circuit Breakerの発動対象外とし、正規のトラフィック（PLMN未登録）への影響を防ぐ

#### 3.4.3 計算エラー

| エラー種別 | 検出条件 | 対処 | HTTP応答 | ログ |
|-----------|---------|------|---------|------|
| AUTS MAC検証失敗 | 再同期時のMAC不正 | - | 400 Bad Request | WARN: `SQN_RESYNC_MAC_ERR` |
| AUTS形式不正 | AUTS長不正（14バイトでない） | - | 400 Bad Request | WARN: `SQN_RESYNC_FORMAT_ERR` |
| SQN抽出失敗 | AUTSからのSQN抽出失敗 | - | 400 Bad Request | WARN: `SQN_RESYNC_MAC_ERR`（MAC検証失敗として扱う） |
| SQN差分超過 | SQN_MSとSQN_HEの差が許容範囲外 | - | 400 Bad Request | WARN: `SQN_RESYNC_DELTA_ERR`（ハンドラー層の1行。SQN値は `error` 属性の文中） |
| SQNオーバーフロー | 新SQNが48bit上限を超過 | - | 500 Internal Server Error | ERROR: `SQN_OVERFLOW_ERR` |
| SQN競合上限超過 | SQNの書き換え（Lua による比較・置き換え）が3回とも競合、またはやり直し前の待機中にリクエストの context が終了 | 競合するたびに1〜10ms待って加入者の読み出しからやり直す（最大3回試行） | 409 Conflict | WARN: `SQN_CONFLICT_RETRY`（やり直すたび。最大2回）、WARN: `SQN_CONFLICT_ERR`（上限超過時） |
| Milenage計算エラー | 予期せぬ例外 | - | 500 Internal Server Error | ERROR: `CALC_ERR`（SQNの書き換え後に計算するため、SQNは進んだままとなる） |

> **注記（SQN競合制御）：**
> - Vector API は、`sub:{IMSI}` の `sqn` が読んだ値から変わっていないときだけ書き換える（`apps/vector-api/internal/store/subscriber.go` の `CompareAndSetSQN`。Lua スクリプトによる比較・置き換え。D-02 §2.A、D-11 §7.5・§13.6）。変わっていた（他のリクエストが先に書き換えた）場合は、1〜10ms のランダムな時間待ってから加入者の読み出し・新SQNの計算からやり直す。3回とも競合した場合は 409 Conflict（`SQN update conflict: conflicted 3 times`）を返す。待っている間にリクエストの context が終了した（呼び出し元の切断・タイムアウト等）場合は、やり直さずに 409 Conflict（`SQN update conflict: retry aborted after N attempts: <contextのエラー>`）を返す。いずれもベクターは返さない
> - ベクターは SQN の書き換えに成功した後に計算する。書き換えに失敗した（競合上限超過、Valkeyエラー）場合はベクターを計算しない。書き換え時の Valkey エラーは競合とは扱わず、500（`VALKEY_CONN_ERR`。§3.4.1）とする
> - やり直しで加入者が削除されていた場合は 404（`CALC_ERR`）となる（比較・置き換えはキーを新たに作らない）
> - 再同期のやり直しで、読み直した SQN_HE が SQN_MS 以上の場合は、別のリクエストが先に同期済みとみなし、SQN差分超過（400）とはせずに SQN_HE + 32 で応答する（D-04 §3.4.3）
> - **409 を 5xx にしない理由：** 5xx は Auth Server の Circuit Breaker の失敗回数に数えられる（§3.1.1、§4.3）。1つの IMSI への並行リクエストの競合で Circuit Breaker が開くと、全加入者の認証が止まりうるため、Circuit Breaker の対象外である 4xx の 409 Conflict とする
> - r14 までは本機能を「設計済み・未実装（単純な HSET による後勝ち）」と記載していた。D-11 r9 までの設計は WATCH/MULTI による CAS だったが、r10 で Lua による `sqn` フィールドの比較・置き換えに変更して実装した

> **注記：** 409 の `detail` も他の定義済みエラーと同じく固定文で、IMSI や競合の回数・原因は含めない（ログの `SQN_CONFLICT_ERR` の `error` 属性で確認する。§6.7）。

### 4.1 タイムアウト設定一覧

| Acct Server → Valkey | 接続タイムアウト | 3秒 | |
| Acct Server → Valkey | コマンドタイムアウト | 2秒 | |
| Vector Gateway → Vector API | HTTPリクエストタイムアウト | 3秒 | `VECTOR_GATEWAY_INTERNAL_TIMEOUT`。Auth Server のリクエストタイムアウト（5秒）より短くする（下記注記） |
| Vector Gateway → aka-only-server | HTTPリクエストタイムアウト | 3秒 | `VECTOR_GATEWAY_AKAONLY_TIMEOUT`（接続方式01）。同上 |
| Vector API → Valkey | 接続タイムアウト | 3秒 | |
| Vector API → Valkey | コマンドタイムアウト | 2秒 | |

> **注記（Vector Gateway のタイムアウト）：** Vector Gateway → バックエンドのタイムアウトは、Auth Server → Vector Gateway のリクエストタイムアウト（5秒）より短くする。バックエンド障害時に Vector Gateway が 502 を返す前に Auth Server がタイムアウトすると、Auth Server のログが `VECTOR_API_ERR`（502）になるか `VECTOR_CONN_ERR` になるかが環境（停止したコンテナ名の名前解決にかかる時間など）次第で変わるためである。設定値が 5秒以上の場合、Vector Gateway は起動時に WARN を出す（§3.3.4）。

### 4.2 リトライ戦略

| 対象 | リトライ回数 | 初回間隔 | バックオフ | 備考 |
|------|------------|---------|-----------|------|
| Auth Server → Vector Gateway | 0回 | - | - | Circuit Breakerに委ねる |
| Auth Server → Valkey | 2回 | 100ms | 指数（×2） | 最大400ms待機 |
| Acct Server → Valkey | 3回 | 100ms | 指数（×2） | 最大800ms待機 |
| Vector Gateway → Vector API | 0回 | - | - | リトライなし（Auth Server側のCBに委ねる） |
| Vector Gateway → aka-only-server | 0回 | - | - | リトライ・接続方式00へのフォールバックなし（Auth Server側のCBに委ねる） |
| Vector API → Valkey | 0回（アプリ独自） | - | - | アプリ独自のリトライなし。go-redis v9 の既定の自動リトライ（最大3回、8ms〜512ms）の後もエラーなら500（D-11 §8.3） |
| Vector API（SQN書き換えの競合） | 2回（最大3回試行） | 1〜10ms（ランダム） | なし（毎回ランダム） | Valkeyエラーではなく、SQNの比較・置き換えで競合した場合のやり直し（加入者の読み出しから）。上限超過で409（§3.4.3） |
| Admin TUI → Valkey | 0回（手動） | - | - | ユーザーに再試行を促す |

#### リトライ実装例

```go
func withRetry(ctx context.Context, maxRetries int, baseInterval time.Duration, fn func() error) error {
    var lastErr error
    for i := 0; i <= maxRetries; i++ {
        if err := fn(); err != nil {
            lastErr = err
            if i < maxRetries {
                interval := baseInterval * time.Duration(1<<i) // 指数バックオフ
                time.Sleep(interval)
                continue
            }
        }
        return nil
    }
    return lastErr
}
```

### 4.3 Circuit Breaker設定

Auth Server → Vector Gateway 間の通信に適用。

| 項目 | 値 | 説明 |
|------|-----|------|
| 失敗閾値 | 5回 | Closed → Open 遷移条件 |
| 計測ウィンドウ | 10秒 | 失敗カウントのリセット間隔 |
| Open状態維持時間 | 30秒 | Half-Open へ遷移するまでの時間 |
| Half-Open許可リクエスト数 | 3回 | 試行成功で Closed 復帰 |
| 成功閾値 | 2回 | Half-Open → Closed 遷移条件 |

> **注記：** r3でAuth Server → Vector API をAuth Server → Vector Gatewayに変更。Vector Gatewayは透過的に動作するため、Circuit Breaker設定自体に変更はない。
>
> **注記（接続方式01）：** Circuit Breakerは接続方式共通である。接続方式01由来の502も失敗回数に数えられ、Openになると接続方式00向けの認証も停止する（§3.3.1参照）。

#### 状態遷移図

```
                    失敗 5回/10秒
        ┌─────────────────────────────────┐
        │                                 ▼
    ┌───────┐                        ┌────────┐
    │Closed │                        │  Open  │
    └───┬───┘                        └────┬───┘
        ▲                                 │
        │ 成功 2回                        │ 30秒経過
        │                                 ▼
        │                           ┌──────────┐
        └───────────────────────────┤Half-Open │
                                    └──────────┘
                                          │
                                          │ 失敗
                                          ▼
                                       [Open へ戻る]
```

#### 実装例（gobreaker使用）

```go
import "github.com/sony/gobreaker"

var cb *gobreaker.CircuitBreaker

func init() {
    settings := gobreaker.Settings{
        Name:        "vector-gateway",  // 変更: vector-api → vector-gateway
        MaxRequests: 3,                      // Half-Open時の許可数
        Interval:    10 * time.Second,       // 計測ウィンドウ
        Timeout:     30 * time.Second,       // Open維持時間
        ReadyToTrip: func(counts gobreaker.Counts) bool {
            return counts.ConsecutiveFailures >= 5
        },
        OnStateChange: func(name string, from, to gobreaker.State) {
            switch to {
            case gobreaker.StateOpen:
                slog.Warn("circuit breaker opened",
                    "event_id", "CB_OPEN",
                    "cb_name", name,
                    "failure_count", 0) // 状態遷移フックでは失敗件数を取得できないため常に0（D-04 §4.2）
            case gobreaker.StateHalfOpen:
                slog.Info("circuit breaker half-open",
                    "event_id", "CB_HALF_OPEN",
                    "cb_name", name)
            case gobreaker.StateClosed:
                slog.Info("circuit breaker closed",
                    "event_id", "CB_CLOSE",
                    "cb_name", name)
            }
        },
    }
    cb = gobreaker.NewCircuitBreaker(settings)
}
```

### 4.4 Graceful Degradation

#### 4.4.1 Valkey接続断時の動作

| コンポーネント | 動作 | 備考 |
|---------------|------|------|
| **Auth Server** | `RADIUS_SECRET`（フォールバック）が空（推奨）なら無応答。NASのSecretがフォールバックと一致すれば全認証リクエストを Access-Reject | ログ出力継続。下記詳細参照 |
| **Acct Server** | NASのSecretがフォールバック（`RADIUS_SECRET`）と一致すればAccounting-Response返却・データ欠損をログ記録。一致しなければ（フォールバックが空（推奨）の場合を含む）無応答 | ベストエフォート。下記詳細参照 |
| **Vector Gateway** | 正常動作（Valkey未使用） | PoC段階ではValkey接続なし |
| **Vector API** | 500エラー応答 | |
| **Admin TUI** | エラー画面表示、再接続ボタン | |

**各コンポーネントのValkey停止時詳細動作:**

- **Auth Server:** Valkey停止中は送信元IPに対応するSecret（`client:{IP}`）を引けないため `RADIUS_SECRET_ERR`（WARN）を出力し、環境変数 `RADIUS_SECRET`（フォールバック）でパケットを検証する。挙動はフォールバックとNASのSecretによって分かれる。
  - フォールバックが空の場合（推奨。D-09 §3.1）: パケットを破棄し、応答しない。NASは再送し、Valkey復旧後に処理を継続する。
  - NASのSecretがフォールバックと一致する場合: EAPコンテキスト（`eap:{UUID}`）の保存/取得が不可となるため、新規認証は即座にAccess-Rejectとなり、進行中の認証はEAPコンテキストTTL（60秒）超過により自動的に失敗する。
  - 一致しない場合: Message-Authenticatorの検証に失敗して応答しない（`PKT_MA_INVALID`）。
- **Acct Server:** Valkey停止中はセッション情報（`sess:{UUID}`）の記録/更新が不可となる。また、送信元IPに対応するSecret（`client:{IP}`）を引けないため `RADIUS_SECRET_ERR`（WARN）を出力し、環境変数 `RADIUS_SECRET`（フォールバック）でパケットを検証する。挙動はNASのSecretによって分かれる。
  - NASのSecretがフォールバックと一致する場合: パケットは受け付けられ、Valkeyへの書き込み失敗をログ（`VALKEY_CONN_ERR` / `DB_WRITE_ERR`）に記録したうえでAccounting-Responseを返す。NASは再送しないため、停止中の課金データは失われる（ログから追跡する）。
  - フォールバックが空の場合（推奨。D-10 §3.1）: パケットを破棄し、応答しない。NASが再送し、Valkey復旧後に再送されたパケットで処理を継続する。
  - 一致しない場合: ハンドラーでのRequest Authenticatorの検証に失敗して応答しない（`RADIUS_AUTH_ERR`。`src_ip` 付き）。NASが再送し、Valkey復旧後に再送されたパケットで処理を継続する。
- **Vector API:** Valkey停止中は加入者データ（`sub:{IMSI}`）の取得が不可となる。500 Internal Server Errorを返却し、Auth Server側のCircuit Breakerが発動する。
- **Admin TUI:** 起動時にValkey接続失敗の場合はエラー画面を表示する。操作中にValkey接続が断絶した場合はステータスバーにエラーメッセージを表示する。

#### 4.4.2 Valkey再接続方針

| 項目 | 方針 |
|------|------|
| 再接続主体 | go-redisクライアントの自動再接続機能を利用 |
| 接続プール | 有効（デフォルト設定） |
| ヘルスチェック | go-redisの自動ヘルスチェックに依存 |
| 復旧検知 | 実装しない（復旧検知ログは出力しない） |

> **注記（復旧の判断）：** Valkey接続の復旧検知（復旧時の停止時間 `downtime_ms` の記録）は実装していない。go-redisのコネクションプールが次のコマンド実行時に接続を張り直すため、復旧は各ノードのValkey関連エラーログ（Auth Server: `EAP_CTX_NOT_FOUND` / `EAP_CTX_CREATE_ERR` 等の `error` 属性、Acct Server: `VALKEY_CONN_ERR` / `DB_WRITE_ERR`、Vector API: `VALKEY_CONN_ERR`）の出力が止まったことで判断する（D-04 §4.3）。

#### 4.4.3 Vector Gateway障害時の動作（Auth Server）

| Circuit Breaker状態 | 動作 | レイテンシ影響 |
|---------------------|------|---------------|
| **Closed** | 通常処理、失敗時はカウント | 通常 |
| **Open** | 即座にAccess-Reject、Gateway呼び出しスキップ | 最小（即時応答） |
| **Half-Open** | 限定的に試行 | 試行時は通常、それ以外は最小 |

#### エラーハンドリングの一貫性

ハンドラー層でエラーを分類し、適切な応答を返す。

```go
func handleAuthRequest(ctx context.Context, req *radius.Packet) *radius.Packet {
    traceID := extractTraceID(req)
    maskedIMSI := logging.MaskIMSI(extractIMSI(req), cfg.LogMaskIMSI)
    result, err := processAuth(ctx, req)
    if err != nil {
        // エラー種別に応じた応答とログ出力
        var apiErr *vector.APIError
        switch {
        case errors.As(err, &apiErr) && apiErr.IsNotFound():
            // Vector Gateway が404を返した（IMSI未登録）
            // 実装: apps/auth-server/internal/engine/engine.go の logVectorError
            slog.Error("Vector APIエラー",
                "event_id", "VECTOR_IMSI_NOT_FOUND",
                "trace_id", traceID,
                "imsi", maskedIMSI,
                "http_status", apiErr.StatusCode,
                "error", apiErr.Error())
            return buildReject(req, eap.Failure)
            
        case errors.As(err, &apiErr):
            // 404以外の4xx/5xx（400, 403, 501, 502 など）
            slog.Error("Vector APIエラー",
                "event_id", "VECTOR_API_ERR",
                "trace_id", traceID,
                "imsi", maskedIMSI,
                "http_status", apiErr.StatusCode,
                "error", apiErr.Error())
            return buildReject(req, eap.Failure)
            
        case errors.Is(err, apperr.ErrPolicyNotFound):
            // ポリシー未設定・JSONパース失敗・Valkeyエラーのいずれも同じevent_id
            slog.Warn("ポリシー取得失敗",
                "event_id", "AUTH_POLICY_NOT_FOUND",
                "trace_id", traceID,
                "imsi", maskedIMSI,
                "error", err)
            return buildReject(req, eap.Failure)
            
        case errors.Is(err, apperr.ErrAuthResMismatch):
            slog.Warn("Challenge応答検証失敗",
                "event_id", "AUTH_RES_MISMATCH",
                "trace_id", traceID,
                "imsi", maskedIMSI,
                "error", err)
            return buildReject(req, eap.Failure)
            
        // Auth Serverには実行時のValkeyエラー専用のevent_idはない。
        // 処理箇所ごとのevent_id（EAP_CTX_NOT_FOUND, EAP_CTX_CREATE_ERR 等）の error 属性で記録する（§3.1.1）
            
        default:
            // その他の内部エラー（Valkey保存失敗・パケット構築失敗等）も、処理箇所ごとの
            // event_id（EAP_CTX_CREATE_ERR 等。D-04 §3.1.7）でログに記録して Reject に変換する
            return buildReject(req, eap.Failure)
        }
    }
    return result
}
```

> **注記：** 実装では上記の分類とログ出力をEAPエンジン（`apps/auth-server/internal/engine/engine.go`）内で行い、エラーはすべてReject（またはDrop）の結果に変換する。エンジンのインターフェース `eap.EAPProcessor` の `Process(ctx, req) *Result` は error を返さないため、RADIUSハンドラー（`apps/auth-server/internal/server/handler.go`）にはエンジンエラーの分岐（旧 `EAP_ENGINE_ERR`）はない。

#### Vector Gatewayのエラーハンドリング

実装: `apps/vector-gateway/internal/handler/vector.go`（抜粋。`imsi` は `logging.MaskIMSI` でマスクして出力する）

```go
// Vector Gatewayのハンドラー層
func (h *VectorHandler) HandleVector(c *gin.Context) {
    traceID, _ := c.Get(TraceIDKey)

    var req backend.VectorRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        slog.Warn("invalid request body",
            "trace_id", traceID,
            "event_id", "GW_ERR",
            "error", err.Error())
        c.JSON(http.StatusBadRequest, httputil.NewProblemDetail(
            http.StatusBadRequest, "Bad Request", "Invalid request body"))
        return
    }
    // IMSI検証（失敗時は GW_ERR / "invalid IMSI format" で 400 "IMSI must be 15 digits"）
    // ...

    b, err := h.router.SelectBackend(req.IMSI)
    if err != nil {
        h.handleRoutingError(c, traceID, req.IMSI, err)
        return
    }
    slog.Info("backend selected",
        "trace_id", traceID,
        "event_id", "GW_ROUTE",
        "imsi", logging.MaskIMSI(req.IMSI, h.cfg.LogMaskIMSI),
        "backend_id", b.ID(),
        "backend_name", b.Name())

    resp, err := b.GetVector(ctx, &req)
    if err != nil {
        h.handleBackendError(c, traceID, req.IMSI, err)
        return
    }
    slog.Info("vector forwarded",
        "trace_id", traceID,
        "event_id", "GW_OK",
        "imsi", logging.MaskIMSI(req.IMSI, h.cfg.LogMaskIMSI),
        "backend_id", b.ID(),
        "http_status", http.StatusOK)
    c.JSON(http.StatusOK, resp)
}

func (h *VectorHandler) handleRoutingError(c *gin.Context, traceID any, imsi string, err error) {
    var notImpl *backend.BackendNotImplementedError
    if errors.As(err, &notImpl) {
        slog.Warn("backend not implemented",
            "trace_id", traceID,
            "event_id", "GW_ERR",
            "imsi", logging.MaskIMSI(imsi, h.cfg.LogMaskIMSI),
            "backend_id", notImpl.ID)
        c.JSON(http.StatusNotImplemented, httputil.NewProblemDetail(
            http.StatusNotImplemented, "Not Implemented",
            fmt.Sprintf("Backend %q is not implemented", notImpl.ID)))
        return
    }
    // その他: ERROR GW_ERR / "routing error" で 500 "An unexpected error occurred"
    // ...
}

func (h *VectorHandler) handleBackendError(c *gin.Context, traceID any, imsi string, err error) {
    // 4xx: そのまま返却
    var respErr *backend.BackendResponseError
    if errors.As(err, &respErr) {
        slog.Warn("backend returned error",
            "trace_id", traceID,
            "event_id", "GW_ERR",
            "imsi", logging.MaskIMSI(imsi, h.cfg.LogMaskIMSI),
            "http_status", respErr.StatusCode)
        c.JSON(respErr.StatusCode, respErr.Problem)
        return
    }

    // 通信エラー・5xx・不正応答: 502
    var commErr *backend.BackendCommunicationError
    if errors.As(err, &commErr) {
        slog.Error("backend communication error",
            "trace_id", traceID,
            "event_id", "GW_ERR",
            "imsi", logging.MaskIMSI(imsi, h.cfg.LogMaskIMSI),
            "error", commErr.Error())
        c.JSON(http.StatusBadGateway, httputil.NewProblemDetail(
            http.StatusBadGateway, "Bad Gateway",
            "Failed to communicate with backend service"))
        return
    }

    // その他: 500
    slog.Error("unexpected backend error",
        "trace_id", traceID,
        "event_id", "GW_ERR",
        "imsi", logging.MaskIMSI(imsi, h.cfg.LogMaskIMSI),
        "error", err.Error())
    c.JSON(http.StatusInternalServerError, httputil.NewProblemDetail(
        http.StatusInternalServerError, "Internal Server Error",
        "An unexpected error occurred"))
}
```
