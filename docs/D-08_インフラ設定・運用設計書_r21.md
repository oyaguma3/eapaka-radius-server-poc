## 2. Valkey設定

### 2.1 設定概要

| 項目 | 設定値 | 備考 |
|------|-------|------|
| 永続化方式 | AOF（Append Only File） | RDB スナップショット（`dump.rdb`）も Valkey 既定の `save` 設定（`3600 1 300 100 60 10000`）で作られる。起動時は AOF が優先して読み込まれる |
| AOF fsync | `everysec` | 1秒ごとにディスク同期（デフォルト） |
| メモリ上限 | 512MB | PoC規模では十分 |
| メモリ超過ポリシー | `noeviction` | 超過時は書き込みエラー |
| ACL | 単一ユーザー（default） | パスワード認証のみ |
| 接続元制限 | 127.0.0.1のみ（TUI用） + Dockerネットワーク内 | 外部からのアクセス不可 |

### 2.2 Valkey起動オプション

docker-compose.ymlでの設定：

```yaml
valkey:
  image: valkey/valkey:9.0
  ports:
    - "127.0.0.1:6379:6379"
  volumes:
    - valkey_data:/data
  command: >
    valkey-server
    --appendonly yes
    --appendfsync everysec
    --maxmemory 512mb
    --maxmemory-policy noeviction
    --requirepass ${VALKEY_PASSWORD}
  environment:
    - TZ=Asia/Tokyo
  restart: always
```

### 2.3 永続化データの保存場所

| 項目 | パス | 説明 |
|------|------|------|
| Dockerボリューム | `valkey_data` | 名前付きボリューム |
| ホスト上の実体 | `/var/lib/docker/volumes/プロジェクト名_valkey_data/_data`（プロジェクト名は compose を置いたディレクトリ名で、既定は `deployments_valkey_data`） | AOFファイル格納 |
| AOFファイル | `appendonlydir/appendonly.aof.*` | 実際のデータファイル |

### 2.4 バックアップ・リストア

#### バックアップ実行手順

```bash
# バックアップディレクトリ確認
ls -la ~/backups/valkey/

# 手動バックアップ実行
~/scripts/backup_valkey.sh

# バックアップ確認
ls -la ~/backups/valkey/
```

#### リストア手順

Valkey を止め、`docker compose run` で valkey サービスのボリューム（`/data`）の中身をバックアップと入れ替える。ボリューム名（プロジェクト名に依存し、既定は `deployments_valkey_data`）を指定する必要はない。手順の詳細と確認方法は O-04 §4.2 を参照。

```bash
cd ~/eapaka-radius-server-poc/deployments
set -a; . ./.env; set +a          # VALKEY_PASSWORD を読み込む
BACKUP=backup_YYYYMMDD_HHMMSS.tar.gz   # 戻すバックアップ（ls ~/backups/valkey/ で確認）

# 1. バックアップファイルの整合性確認
tar tzf ~/backups/valkey/${BACKUP} > /dev/null && echo OK

# 2. Valkey 停止
docker compose stop valkey

# 3. ボリュームの中身をバックアップと入れ替える
docker compose run --rm --no-deps -T \
  -v "${HOME}/backups/valkey:/backup:ro" \
  --entrypoint sh valkey \
  -c "find /data -mindepth 1 -delete && tar xzf /backup/${BACKUP} -C /data --strip-components=1"

# 4. Valkey 起動
docker compose start valkey

# 5. データ確認
docker compose exec valkey valkey-cli -a "${VALKEY_PASSWORD}" --no-auth-warning dbsize
```

> **注記（r20）:** r19 までの手順（`docker compose stop valkey` の後に `docker volume rm eapaka-radius-server-poc_valkey_data` → `volume create` → alpine コンテナで展開）は、(1) 実際のボリューム名が `deployments_valkey_data`（compose のプロジェクト名はディレクトリ名 `deployments`）であり、(2) 停止しただけのコンテナもボリュームを参照しているため `volume rm` が「volume is in use」で失敗するため、そのままでは実行できなかった（2026-10-04 に simwifi 実機で確認）。

#### バックアップスクリプト内容

**ファイルパス:** `~/scripts/backup_valkey.sh`

```bash
#!/bin/bash
set -euo pipefail

# バックアップには Ki / OPc を含む加入者データが入るので、本人だけが読めるようにする
umask 077

BACKUP_DIR="${HOME}/backups/valkey"
RETENTION_DAYS=7
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/backup_${TIMESTAMP}.tar.gz"

# バックアップディレクトリ作成
mkdir -p "${BACKUP_DIR}"

# 失敗したときに書きかけの一時ファイルを残さない
trap 'rm -f "${BACKUP_FILE}.tmp"' EXIT

# バックアップ実行（一時ファイルに書き、壊れていないことを確かめてから正式な名前にする）
cd ~/eapaka-radius-server-poc/deployments
docker compose exec -T valkey sh -c 'tar czf - /data' > "${BACKUP_FILE}.tmp"
tar tzf "${BACKUP_FILE}.tmp" > /dev/null
mv "${BACKUP_FILE}.tmp" "${BACKUP_FILE}"

# 古いバックアップの削除
find "${BACKUP_DIR}" -name "backup_*.tar.gz" -mtime +${RETENTION_DAYS} -delete

echo "Backup completed: backup_${TIMESTAMP}.tar.gz"
```

> **注記:** スクリプトの初回配置およびcrontab設定はデプロイ手順書（B-02）を参照。
>
> **注記（r20）:** スクリプトを次のように改めた。
> - `set -euo pipefail` と、一時ファイル（`.tmp`）に書いて `tar tzf` で壊れていないことを確かめてから正式な名前にする方式にした。r19 までは、Valkey が停止しているなどで `docker compose exec` が失敗すると、0バイトのバックアップファイルが残り、最新のバックアップに見えてしまっていた。
> - `umask 077` で、バックアップファイル（600）と新しく作るディレクトリ（700）を本人だけが読めるようにした。バックアップには Ki / OPc を含む加入者データが入る。
> - バックアップは同じディスクにしか残らないので、ホストの故障に備えて、定期的にホストの外へコピーすることを推奨する（O-04 §2.3）。

## 3. Fluent Bit設定

### 3.1 設定概要

| 項目 | 設定値 | 備考 |
|------|-------|------|
| 入力 | Fluentdプロトコル（forward） | Docker log driver経由 |
| 出力 | ファイル（アプリ別分割） | `/output_logs/{app}.log` |
| ローテーション | 日次 | logrotate連携 |
| 保持期間 | 30日 | |
| バッファ | メモリ 5MB | `Mem_Buf_Limit` |

### 3.1.1 Fluent Bitイメージ方針

**統一イメージ:** `fluent/fluent-bit:4.2`

| 項目           | 内容                                                  |
| -------------- | ----------------------------------------------------- |
| 採用理由       | AWS固有機能は不要、公式イメージで十分                 |
| 非採用         | `amazon/aws-for-fluent-bit`（AWS CloudWatch連携不要） |
| バージョン固定 | `4.2` を明示（latest回避）                            |
| ベースイメージ | Distrolessベース（v4.x系のデフォルト）                |

> **注記:** D-01のdocker-compose.ymlも同一イメージを使用すること。

> **注記:** Fluent Bit v4.x系のデフォルトイメージはDistrolessベースのため、`docker exec` でシェルに入ることができない。デバッグ時は `-debug` タグ付きイメージ（`fluent/fluent-bit:4.2-debug`）を使用すること。

### 3.2 設定ファイル

**ファイルパス:** `configs/fluent-bit/fluent-bit.yaml`

Fluent Bit v4.x系ではYAML形式の設定ファイルを使用する。Classic config形式（`.conf`）は2026年末に廃止予定のため、YAML形式に移行済み。パーサー設定もYAMLファイル内に統合されている。

```yaml
service:
  flush: 1
  daemon: false
  log_level: info

parsers:
  - name: json
    format: json
    time_key: false

pipeline:
  inputs:
    - name: forward
      listen: 0.0.0.0
      port: 24224
      mem_buf_limit: 5MB

  filters:
    - name: parser
      match: "app.*"
      key_name: log
      parser: json
      reserve_data: false

    # ヘルスチェックログをリタグしてアプリ専用ログから除外
    - name: rewrite_tag
      match: "app.vector-api"
      rule: $path ^/health$ healthcheck.vector-api false
      emitter_name: re_emitted_vector_api

    - name: rewrite_tag
      match: "app.vector-gateway"
      rule: $path ^/health$ healthcheck.vector-gateway false
      emitter_name: re_emitted_vector_gw

  outputs:
    - name: file
      match: app.auth-server
      path: /output_logs
      file: auth-server.log
      format: plain

    - name: file
      match: app.acct-server
      path: /output_logs
      file: acct-server.log
      format: plain

    - name: file
      match: app.vector-gateway
      path: /output_logs
      file: vector-gateway.log
      format: plain

    - name: file
      match: app.vector-api
      path: /output_logs
      file: vector-api.log
      format: plain

    - name: file
      match: app.valkey
      path: /output_logs
      file: valkey.log
      format: plain

    # ヘルスチェックログ → others.log
    # （rewrite_tagでapp.*からhealthcheck.*にリタグされたログを収集）
    - name: file
      match: "healthcheck.*"
      path: /output_logs
      file: others.log
      format: plain
```

> **注記:** forward 入力の `listen: 0.0.0.0` はコンテナ内での待ち受けである。ホスト側への公開は compose で `127.0.0.1:24224`（tcp・udp）に限っており、外部からは接続できない（§4.1）。

#### 3.2.1 rewrite_tagフィルタによるヘルスチェックログ分離

Vector-API / Vector-GatewayのDockerヘルスチェック（`GET /health`、30秒間隔）が生成するログを、`rewrite_tag` フィルタでアプリ専用ログファイルから除外し、`others.log` に集約する。

**動作原理:**

1. `parser` フィルタでJSONパース後、`path` フィールドが参照可能になる
2. `rewrite_tag` フィルタが `path` の値を正規表現 `^/health$` で評価
3. マッチしたログのタグを `app.*` → `healthcheck.*` に変更
4. リタグされたログはアプリ専用出力ルール（`match: app.*`）にマッチしなくなる

**パラメータ詳細:**

| パラメータ | 値 | 説明 |
|---|---|---|
| `match` | `app.vector-api` / `app.vector-gateway` | ヘルスチェック対象サービスのタグ |
| `rule` | `$path ^/health$ healthcheck.{サービス名} false` | path="/health" のログをリタグ。`false` で元タグのレコードを保持しない |
| `emitter_name` | `re_emitted_vector_api` 等 | リタグ後のレコード再送出用内部入力名（一意であること） |

#### 3.2.2 キャッチオール出力の廃止とログ重複出力の解消

従来の `match: "*"` キャッチオール出力を廃止し、`match: "healthcheck.*"` に変更した。

| 項目 | 変更前 | 変更後 |
|---|---|---|
| マッチ条件 | `match: "*"` | `match: "healthcheck.*"` |
| 効果 | 全タグにマッチ（重複出力あり） | `healthcheck.*` タグのみマッチ（重複なし） |

`match: "*"` は全タグにマッチするため、アプリ専用出力で既に出力されたログが `others.log` にも重複出力されていた。`match: "healthcheck.*"` に限定することで、ヘルスチェックログのみが `others.log` に出力される。

> **注記:** Fluent Bit の `match_regex` は否定先読み（`(?!...)`）をサポートしないため、正規表現による `app.*` 除外ではなくグロブパターンでの明示的マッチを採用した。本PoC環境では `app.*` 以外のタグは `healthcheck.*`（rewrite_tagによるリタグ）のみであり、この方式で要件を満たす。

### 3.3 パーサー設定

パーサー設定は `fluent-bit.yaml` の `parsers` セクションに統合されている（§3.2を参照）。従来の個別ファイル（`parsers.conf`）は廃止済み。

`time_key: false` を指定し、Fluent Bitによるタイムスタンプ解析を無効化している。アプリケーション側のJSON出力に含まれるタイムスタンプをそのまま保持する。

        fluentd-async: "true"
        fluentd-buffer-limit: "1048576"
        tag: "app.vector-api"

  # ==========================================================================
  # Data Layer
  # ==========================================================================
  valkey:
    image: valkey/valkey:9.0
    ports:
      - "127.0.0.1:6379:6379"
    volumes:
      - valkey_data:/data
    command: >
      valkey-server
      --appendonly yes
      --appendfsync everysec
      --maxmemory 512mb
      --maxmemory-policy noeviction
      --requirepass ${VALKEY_PASSWORD}
    environment:
      <<: *timezone
    healthcheck:
      test: ["CMD", "valkey-cli", "-a", "${VALKEY_PASSWORD}", "ping"]
      interval: 10s
      timeout: 3s

      start_period: 5s
    restart: always
    logging:
      <<: *fluent-bit-logging
      options:
        fluentd-address: localhost:24224
        fluentd-async: "true"
        fluentd-buffer-limit: "1048576"
        tag: "app.valkey"

  # Logging Layer
  # ==========================================================================
  fluent-bit:
    image: fluent/fluent-bit:4.2
    command: ["/fluent-bit/bin/fluent-bit", "-c", "/fluent-bit/etc/fluent-bit.yaml"]

> **注記:** Fluent Bit 4.x系のデフォルトコマンドは `-c /fluent-bit/etc/fluent-bit.conf`（Classic config）を指定しているため、YAML設定ファイルを使用する場合は `command` で明示的に `-c /fluent-bit/etc/fluent-bit.yaml` を指定する必要がある。

> **注記（vector-gateway）:** `VECTOR_GATEWAY_AKAONLY_*` は接続方式01（aka-only-server）の設定である。`VECTOR_GATEWAY_AKAONLY_URL` が空（既定）の場合は01が登録されず、従来と同じ動作となる。`./certs:/certs:ro` は aka-only-server 接続用の証明書（`deployments/certs/`）をコンテナ内の `/certs` に読み取り専用でマウントする。aka-only-server を同一ホストで動かす場合は、本ファイルにオーバーレイ `docker-compose.aka-av.yml` を重ねて起動する（§4.5参照）。

> **注記（vector-gateway のタイムアウト）:** `VECTOR_GATEWAY_INTERNAL_TIMEOUT` / `VECTOR_GATEWAY_AKAONLY_TIMEOUT` の既定値 `3s` は、auth-server の Vector Gateway 呼び出しタイムアウト（5秒、コード内の定数）より短くしてある。バックエンド（vector-api / aka-only-server）障害時に vector-gateway が 502 を返す前に auth-server がタイムアウトすると、auth-server のログが `VECTOR_API_ERR`（502）になるか `VECTOR_CONN_ERR` になるかが環境次第で変わるためである。`.env` で5秒以上に設定すると、vector-gateway は起動時に WARN `backend timeout should be shorter than the auth-server timeout; auth-server may time out before receiving 502` を出す（D-12 §5.3）。

> **注記（LOG_LEVEL）:** `LOG_LEVEL: ${LOG_LEVEL:-INFO}` は、auth-server / acct-server / vector-gateway / vector-api の4サーバーに渡す（既定 `INFO`。`DEBUG` / `INFO` / `WARN` / `ERROR`）。`.env` の `LOG_LEVEL` を変更した場合は `docker compose up -d` で対象コンテナを作り直す（D-04 §4.6）。

> **注記（公開ポート）:** 外部（0.0.0.0 / [::]）に公開するのは auth-server の `1812/udp` と acct-server の `1813/udp` だけである。valkey の `6379` と fluent-bit の `24224`（tcp・udp）は `127.0.0.1` にバインドし、ホストからだけ接続できるようにしている（各サービスのログドライバーは `fluentd-address: localhost:24224` でホストの 24224 に接続するため、外部に公開する必要はない。fluent-bit の forward 入力は認証がないので、外部に公開しないこと）。vector-gateway・vector-api は `expose` のみでホストに公開しない。Docker の公開ポートは UFW を通らないため（§5.4）、内部向けのポートは必ず `127.0.0.1` にバインドすること。

> **注記（RADIUS_SECRET）:** auth-server / acct-server の `RADIUS_SECRET: ${RADIUS_SECRET:-}` は、フォールバックの共有シークレットである（任意。既定は空）。`${RADIUS_SECRET:-}` としているため、`.env` に設定がなくても compose の「variable is not set」の警告は出ない。空のときは、クライアント登録（`client:{IP}`）のない送信元IPからのパケットを破棄する（`RADIUS_NO_SECRET`）。設定すると、登録のない送信元IPのパケットもそのシークレットで受け付けるため、インターネットに公開するサーバーでは空にすること（§4.2、§5.7）。

### 4.3 ヘルスチェック設定

#### 4.3.1 ヘルスチェック方針

**HTTPエンドポイント用コマンド:** `curl -fsS http://localhost:8080/health`

| 項目 | 内容 |
|------|------|
| 採用コマンド | `curl -fsS` |
| 非採用 | `wget -q --spider`（4xx/5xxを失敗扱いにできない場合がある） |
| 理由 | `curl -fsS` はHTTP 4xx/5xxを失敗扱いにでき、より安定したヘルスチェックが可能 |

**ベースイメージ要件:**
- ランタイムベースイメージ: `debian:bookworm-slim`
- 共通必須パッケージ: `curl`, `ca-certificates`
- UDPサービス追加必須: `procps`（`pgrep`コマンド用、auth-server/acct-serverのみ）

> **注記:** すべてのGoアプリケーション（auth-server, acct-server, vector-gateway, vector-api）のDockerfileは、ランタイムステージで `debian:bookworm-slim` をベースとし、`curl` と `ca-certificates` を導入すること。

> **UDPサービスの追加要件:** auth-server および acct-server は `pgrep` によるヘルスチェックを行うため、`procps` パッケージも必須となる。

#### 4.3.2 サービス別設定

| サービス | チェック方法 | 間隔 | タイムアウト | リトライ |
|---------|-------------|------|------------|---------|
| auth-server | プロセス存在確認 (`pgrep`) | 30秒 | 5秒 | 3回 |
| acct-server | プロセス存在確認 (`pgrep`) | 30秒 | 5秒 | 3回 |
| vector-gateway | `curl -fsS http://localhost:8080/health` | 30秒 | 5秒 | 3回 |
| vector-api | `curl -fsS http://localhost:8080/health` | 30秒 | 5秒 | 3回 |
| valkey | `valkey-cli ping` | 10秒 | 3秒 | 3回 |

**UDPサービスのヘルスチェックについて：**

auth-server、acct-serverはUDPプロトコルを使用するため、TCP接続確認やHTTPエンドポイント確認ができない。PoC段階ではプロセス存在確認（`pgrep`）を採用し、アプリケーション内部状態の確認はログ監視で補完する。

**`pgrep`コマンドの依存パッケージ:**

| コマンド | 提供パッケージ | 対象サービス |
|---------|---------------|-------------|
| `pgrep` | `procps` | auth-server, acct-server |

> **重要:** `pgrep` コマンドは `procps` パッケージに含まれる。Dockerfileのランタイムステージで `procps` を導入しないと、ヘルスチェックが常時失敗（unhealthy）となる。

### 4.5 aka-only-server接続設定（接続方式01）

Vector Gateway の接続方式01（aka-only-server）を使う場合の配備設定を示す。接続方式01の仕様は Vector Gateway詳細設計書（D-12）、接続手順はデプロイ手順書（B-02）§14 を参照。01を使わない場合（`VECTOR_GATEWAY_AKAONLY_URL` が空）は本節の設定は不要であり、§4.1 の `docker-compose.yml` だけで従来どおり動作する。

#### 4.5.1 接続用環境変数

| 変数 | 既定値 | 内容 |
|------|--------|------|
| `VECTOR_GATEWAY_AKAONLY_URL` | （空） | aka-only-server のベースURL。`https://` なら mTLS、`http://` なら平文HTTP。空なら01を登録しない |
| `VECTOR_GATEWAY_AKAONLY_CLIENT_CERT` | （空） | クライアント証明書 PEM（コンテナ内パス。例: `/certs/av-client.pem`）。証明書と秘密鍵が1ファイルでよい |
| `VECTOR_GATEWAY_AKAONLY_CLIENT_KEY` | （空） | 秘密鍵 PEM。空なら `CLIENT_CERT` と同じファイルから読む |
| `VECTOR_GATEWAY_AKAONLY_SERVER_CERT` | （空） | aka-only-server の AV 用サーバー証明書（例: `/certs/av-server.pem`）。これだけを信頼する |
| `VECTOR_GATEWAY_AKAONLY_TIMEOUT` | `3s` | aka-only-server 呼び出しタイムアウト。auth-server の Vector Gateway 呼び出しタイムアウト（5秒）より短くする（§4.1 の注記） |
| `AKA_SHARED_NETWORK` | `aka-av` | 共有ネットワーク名（`docker-compose.aka-av.yml` 用。vector-gateway は参照しない） |

- `https://` の場合は `CLIENT_CERT` と `SERVER_CERT` が必須。`http://` の場合は証明書設定を無視し、起動時に平文HTTPである旨の WARN を出す。
- 設定やファイルに不備があると vector-gateway は起動しない（`restart: always` により再起動を繰り返し、ログに `failed to load config` または `failed to initialize backends` が出る）。
- 起動ログ `starting vector-gateway` の `akaonly_enabled`（true / false）と `akaonly_transport`（`mtls` / `plain` / `disabled`）で有効状態を確認できる。

#### 4.5.2 共有ネットワーク用オーバーレイ

**ファイルパス:** `deployments/docker-compose.aka-av.yml`

```yaml
services:
  vector-gateway:
    networks:
      - default
      - aka-av

networks:
  aka-av:
    external: true
    name: ${AKA_SHARED_NETWORK:-aka-av}
```

（実ファイルの先頭には用途を説明するコメントがある。）

aka-only-server の compose が作る共有ネットワーク（既定名 `aka-av`、外部ネットワーク）に **vector-gateway だけ** を参加させる。auth-server、vector-api、Valkey 等は共有ネットワークに参加しない。Web GUI リポジトリ（web-gui-for-aka-only-server）の `compose.aka-av.yaml` と同じ方式である。

**起動順:** 共有ネットワークは aka-only-server 側が作成するため、**aka-only-server を先に起動** してから PoC を起動する。ネットワークが存在しない状態で起動すると、外部ネットワークが見つからないエラーとなる。

```bash
cd ~/eapaka-radius-server-poc/deployments
docker compose -f docker-compose.yml -f docker-compose.aka-av.yml up -d
```

> **注意:** オーバーレイを重ねた環境で `-f` を付けずに `docker compose up -d` を実行すると、vector-gateway が共有ネットワークなしで作り直され、aka-only-server に届かなくなる（`no such host` 等）。systemd サービス（§5.6）も `docker compose up -d` を実行するため、オーバーレイを常用する場合は `.env` に `COMPOSE_FILE=docker-compose.yml:docker-compose.aka-av.yml` を設定し、`-f` なしでも重なるようにしておくとよい。

#### 4.5.3 同一ホスト／別ホストの違い

| 配置 | オーバーレイ | `VECTOR_GATEWAY_AKAONLY_URL` | aka-only-server 側の設定 |
|------|------------|------------------------------|------------------------|
| 同一ホスト（mTLS） | 重ねる | `https://aka-only-server:8443` | 既定の SAN（`localhost,127.0.0.1,aka-only-server`）で接続可 |
| 同一ホスト（平文HTTP） | 重ねる | `http://aka-only-server:8080` | `AKA_AV_PLAIN_ADDR=:8080` を設定し、加入者ごとに平文HTTP許可を立てる |
| 別ホスト（mTLS） | 重ねない | `https://<相手ホストのアドレス>:8443` | そのアドレスを `AKA_AV_TLS_HOSTS` に入れ、サーバー証明書の SAN に含める |

- サーバー証明書のホスト名検証は有効である。URL のホスト名がサーバー証明書の SAN に含まれていないと接続できない。
- 平文HTTP は CK/IK が暗号化されずに流れるため、同一ホスト内に限る。別ホストでは mTLS を使う。

#### 4.5.4 証明書の配置

| ホスト側パス | コンテナ内パス | 内容 |
|-------------|---------------|------|
| `deployments/certs/av-client.pem` | `/certs/av-client.pem` | クライアント証明書＋秘密鍵（aka-only-server の `client gen-cert` の出力） |
| `deployments/certs/av-server.pem` | `/certs/av-server.pem` | aka-only-server の AV 用サーバー証明書（`av-cert` の出力） |

- `deployments/certs/` はリポジトリに `.gitkeep` だけをコミットし、中身は `.gitignore`（`deployments/certs/*` と `!deployments/certs/.gitkeep`）で除外している。証明書・秘密鍵をコミットしないこと。
- ホスト側のパーミッションは秘密鍵を含む `av-client.pem` を `600` とすることを推奨する。vector-gateway コンテナは root で動作するため、`600`（所有者 admin）でも読み込める。
- 証明書は vector-gateway の起動時に1回だけ読み込む。差し替えた場合は vector-gateway の再起動が必要（§6.5）。

### 5.4 UFW設定

**設定内容:**

| ルール | 用途 |
|-------|------|
| DENY (incoming) | デフォルトポリシー |
| ALLOW (outgoing) | デフォルトポリシー |
| 10022/tcp ALLOW | SSH（カスタムポート） |
| 1812/udp ALLOW | RADIUS認証 |
| 1813/udp ALLOW | RADIUS課金 |

**確認方法:**

```bash
sudo ufw status verbose

# 期待される出力:
# Status: active
# Logging: on (low)
# Default: deny (incoming), allow (outgoing), disabled (routed)
#
# To                         Action      From
# --                         ------      ----
# 10022/tcp                  ALLOW IN    Anywhere
# 1812/udp                   ALLOW IN    Anywhere
# 1813/udp                   ALLOW IN    Anywhere
```

> **注意（Docker の公開ポートは UFW を素通りする）:** Docker は compose の `ports:` で公開したポートへの転送を iptables の DOCKER チェーンで直接許可するため、公開ポートへの通信は UFW の規則を通らない。`ufw deny` しても公開ポートには届き、`ufw allow from <IP> to any port 1812 proto udp` のように送信元を絞る規則も効かない。上表のデフォルトポリシー DENY (incoming) が効くのは、ホストのプロセスが待ち受けるポート（SSH 等）だけである。このため次のとおりとする。
> - compose で公開するポートは必要最小限にし、内部向けのポートは `127.0.0.1` にバインドする（valkey の 6379、fluent-bit の 24224。§4.1）。外部に公開するのは 1812/udp・1813/udp だけである。
> - RADIUS（1812/1813/udp）の送信元を絞りたい場合は、UFW ではなく、クラウド側のファイアウォール（VPS のネットワーク設定のファイアウォール、セキュリティグループ等）で AP の送信元（グローバル）IPだけを許可するのが確実である。ホスト側で絞る場合は、iptables の `DOCKER-USER` チェーン（Docker が公開ポートへの転送より先に評価するチェーン）に規則を置く。
> - 上表の 1812/udp・1813/udp の ALLOW は、Docker の公開ポートには実際には影響しない（RADIUS を受け付ける意図を明示する規則として残している）。

### 5.7 インターネット越しに RADIUS を受ける場合の注意

本環境は LAN 内のミニPCを前提とするが、インターネットに直接さらされるサーバー（VPS 等）に置いて、AP から RADIUS をインターネット越しに受ける場合は、次の点に注意する。

| 項目 | 内容 |
|------|------|
| 共有シークレット | RADIUS（UDP）は共有シークレットだけで守られる（パケットの認証と MPPE 鍵の暗号化）。RadSec（RADIUS over TLS）は本PoCのスコープ外である。共有シークレットは十分に長いランダムな値にする（`openssl rand -base64 24` 等で生成） |
| フォールバック | `RADIUS_SECRET`（フォールバック）は空にし、AP の送信元IPを Admin TUI のクライアント登録（`client:{IP}`）で登録する（§4.2）。空なら、登録のない送信元IPのパケットは破棄される（`RADIUS_NO_SECRET`） |
| NAT 配下の AP | NAT の内側にある AP は、サーバーから見た送信元IPがルーターのグローバルIPになる。同じ NAT の内側の複数の AP は同じ IP として扱われる（同じ共有シークレット・同じクライアント登録になる。認可ポリシーの `nas_id` 判定は NAS-Identifier 属性で行うので AP ごとに分けられる） |
| 動的IP | グローバルIPが動的に変わる回線では、変わるたびにクライアント登録をやり直す必要がある（固定IPが望ましい） |
| 送信元の制限 | クラウド側のファイアウォールで 1812/1813/udp の送信元を AP のグローバルIPに絞ることを推奨する（UFW では絞れない。§5.4） |
| 同一ホストからの試験 | 同じホスト上から 127.0.0.1 宛てに送る試験では、送信元IPが Docker ブリッジのゲートウェイIP（例: `172.18.0.1`）になるため、そのIPを `client:{IP}` に登録する |

#### 証明書の差し替え

証明書は vector-gateway の起動時に1回だけ読み込まれるため、差し替えは **vector-gateway の再起動で反映** される。

| 契機 | 作業 |
|------|------|
| aka-only-server の AV 用サーバー証明書を作り直した | aka-only-server 側で `av-cert` を再実行して `av-server.pem` を取り直し、`deployments/certs/` に上書きする |

```bash
cd ~/eapaka-radius-server-poc/deployments

# 証明書を上書きした後、vector-gateway を再起動
docker compose restart vector-gateway

# 起動ログで akaonly_enabled=true を確認し、起動失敗が出ていないことを確認
docker compose logs --tail 20 vector-gateway
```

> **注記:** `.env` の `VECTOR_GATEWAY_AKAONLY_*` を変更した場合は、環境変数を反映させるため `restart` ではなく `docker compose up -d`（オーバーレイ使用時は `-f` 指定または `COMPOSE_FILE` 設定）でコンテナを作り直す。

#### クライアント証明書の期限

aka-only-server が発行するクライアント証明書の有効期限は既定で **825日** である。期限が切れると aka-only-server は TLS ハンドシェイクで拒否し、vector-gateway からは通信失敗（502）に見える。期限は次のコマンドまたは aka-only-server の `client add` 実行時の表示（`not-after=...`）で確認し、期限前に更新すること。

```bash
openssl x509 -in ~/eapaka-radius-server-poc/deployments/certs/av-client.pem -noout -enddate
```
